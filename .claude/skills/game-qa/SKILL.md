# Game QA skill

`python3 -m game_qa` starts the game, drives it and restores the owner's files. Every verb prints one JSON object and exits 0, or 2 for a refusal, a hold or an error. A refusal says what to run next in `next`: do that, not something of your own.

## Three rules before anything else

1. **Ask the owner before launching**, unless they granted launches for this session in their own words. A grant has limits (a time, "after I leave"): keep to them. **A dated fixture's run past March 1836 (`fixture`, below) needs a grant of its own**, for that run and its hours: a grant of launches for the session does not cover it. Even with a grant the tool's gate decides: it refuses beside a game it did not start, and on a busy GPU. Never pass `--owner-confirmed-busy` unless the owner was asked about that reading and said yes.
2. **The game starts only through `start` or `fixture`** (or part 1's `launch`). Never run `victoria3.exe`, the launcher or PowerShell yourself, never end a game process by hand, and never edit, copy or delete anything in the game's user-data folder: the verbs do all of it, with checks.
3. **A hold is the owner's.** `held` in a reply means the tool could not prove that putting the files back was safe (the owner may have played since), so it stopped. Most holds change nothing but the run's playset, which goes back when no game is running. Two come later: `modified_during_restore` (a file changed under the restore; the files before it were already put back) and `retime_unverified` (everything was put back, and one file was left with the snapshot's time over bytes nobody could vouch for). The reply's `restored`, `removed` and `retimed` list what was done. Only the owner resolves a hold. Tell them which snapshot and why, and start nothing more.

## The order of verbs

```bash
python3 -m game_qa doctor                       # ready? starts nothing
python3 -m game_qa start --permission "<the owner's words, and when>" --as FRA \
        [--setup NAME=FILE]... [--playset mod_only|current] [--save NAME] [--switch-rule RULE=SETTING]... \
        [--fixture DATE]                        # a dated fixture made by `fixture`, below
python3 -m game_qa fixture --until 1900 --dry-run                  # the estimate; starts nothing
python3 -m game_qa fixture --until 1900 --permission "<the owner's grant of this run>" --max-hours H
python3 -m game_qa read "c:FRA.gdp" "root.has_technology_researched = railways"
python3 -m game_qa run-setup NAME               # a setup, run through its event
python3 -m game_qa add-setup NAME=FILE          # a new setup for the running game (the game reloads: ~70 s)
python3 -m game_qa press esc                    # one key in the game itself: a probe (shot before and after)
python3 -m game_qa console "event my_events.3"
python3 -m game_qa events                       # what is pending, with numeric ids
python3 -m game_qa pick 0 my_events.3           # option index is 0-based
python3 -m game_qa try-event my_events.3 --setup NAME --read "c:FRA.gdp" --read "..."
python3 -m game_qa enter-game ; python3 -m game_qa advance 10 ; python3 -m game_qa shot
python3 -m game_qa click 0.5 0.5                # one click at fractions of the window, then a shot
python3 -m game_qa selfchecks [--run ID]        # the mod's TE_SELF_CHECK verdicts, every BROKEN first
python3 -m game_qa stop                         # always, even after a failure
```

- **`start`** takes two to four minutes (a `--save` from late in a game can add up to ten while it loads): it snapshots, builds the overlay mod, makes a fresh save if none is cached for this build (an unattended run of its own), loads it, attaches the debugger and opens the console. `--permission` records where the go-ahead came from. Without `--save` the game sits on the fresh save's country-select screen with time stopped, which is all that reads, events and picks need. `--playset mod_only` (the default) loads only this mod's deployed folder; `current` loads the owner's playset. The build under test is whatever is in the deployed mod folder, so deploy first if the change is not there.
- **A setup** is a file holding an effect block's body, run in the played country's scope. Give the ones you know you need at `start`. **`add-setup NAME=FILE`** adds one to the running game: it rewrites the overlay's effect file, the game reloads it (about 70 seconds, live 2026-11-12, and its window does not respond at all meanwhile, so run nothing else until the verb answers), and the reply's `loaded: true` means the game logged the new revision. `not_reloaded` means it did not within five minutes: the setup is in the file, and `run-setup` and `read` look again before they run. A `game_gone` from another verb during a reload is the frozen window, not a dead game: `status` says whether `watch` has returned. A name is used once; thirty can be added in a session. Run live 2026-11-12, before and after `enter-game` (`docs/testing/game-qa-results-2026-11-12.md`).
- **The fresh save's game rules are the ones the owner last applied in a lobby**, not the defaults: an unattended new game reads `LastAppliedRules` from the user-data folder's `player/game_rules/presets.txt`. `start`'s reply lists them (`rules.settings`), and the fixture is remade when they change. Say which rules a check ran under when a row depends on one (Tax Code, culture merges, fantastical content have all been off their defaults).
- **`--switch-rule RULE=SETTING`** (repeatable, not with `--save`) loads a copy of the fresh save with that rule switched. It is a rule changed on 2 January 1836, a day after the game began, as the change-country screen changes it mid-game: what the game's setup decided under the old setting has already happened. That is the right test for "a rule switched off mid-game ends its journal entry", and not proof of how a game made under the setting starts. A rule from the first day needs the owner to apply it in a lobby first (start a New Game with it and quit): ask them, since the harness never writes their `presets.txt` (owner, 2026-11-12). No verb changes a rule in an entered game. (Run live 2026-11-12 with the Tax Code switched off: the game loaded the copy, reported the new setting, and the mod's rule-off handler ran for every country at its next monthly pulse. Other rules are untried: pair the rule's `has_game_rule` read with one that must say yes.)
- **A dated fixture** is a fresh save from later in a game: `fixture --until DATE` makes one with an unattended, AI-only run from 1836 to DATE on this build (`te_qa_fixture_<key>_dYYYYMMDD.v3`, kept and reused while the build, game, playset, DLC and rules stay the same), and `start --fixture DATE` loads it. `start` never makes one: a missing one is refused `no_fixture` with what to run, and `stale` lists that date's fixtures from other builds, which `--save NAME` loads. **A run past 31 March 1836 needs the owner's own grant for that run and its hours; a grant of launches for the session does not cover it.** It takes hours of their desktop (about 3 to 1900, 7 to 1950, 13 to 2000, from archived observer runs; past 1953 a guess) and writes quarterly autosaves into their `save games/`, which the restore puts back. Run `--dry-run` first and give the owner its `estimate_h`; then pass `--max-hours` with the hours they granted (refused `over_grant` when the estimate is more) and run the verb in the background: it answers when the run ends. `stop` cannot interrupt it; closing the game ends it early with no fixture (its exit autosave, a plain-text save dated inside the run, is the run's and is put back over). End a session with `stop`, never by closing its window: a session's exit autosave holds `not_the_runs_save`. Don't deploy while it runs (the deploy watcher runs while VS Code is open), or the reply says `build_changed`. **Tell the owner not to play on another PC meanwhile**: `save games/` syncs through OneDrive, and an autosave from there looks like the run's; the restore holds (`not_the_runs_save`) when it can tell, which is not always. A hold of `save_not_kept` means the run's save could be neither renamed nor copied: it is in `save games/` under the engine's `TEST_FAIL_…` name, and the owner moves it, and the next `restore <id>` (or `stop`) then goes ahead: the hold lasts only while that file is there. Read the reply's `save_facts` (the save's own `game_date`; `start --fixture` gives it as `fixture_game_date`, with a `date_note` when it is not the date asked), `timing` (seconds per game day by year: these set the next estimates), `lines` and `stop`. `--switch-rule` works on a dated fixture: the rule switched on its date. **Run live to 29 March 1836 only** (2026-11-13, `docs/testing/game-qa-results-2026-11-13.md`): 187 s, 0.66 s a game day where the estimate takes 0.47, so ask for a grant above the estimate; the first long run should be short (`--until 1836.7.1`).
- **`read`** evaluates triggers and values at a breakpoint in the played country's scope: `c:TAG.<value>`, `root.<value>`, a script value's name, `c:TAG.var:x`, a trigger. Write a trigger bare (`has_modifier = x`); `c:FRA.has_modifier = x` is refused by the game as an unknown trigger type. An unset variable reads 0, so read `has_variable = x` when that matters. A read that fails comes back `ok: false` with the game's words; the verb still exits 0.
- **`console`** types one command (ASCII, at most 64 characters). `event <id>` ignores the event's trigger and cooldown. There is no console `effect` or `run`: use a setup.
- **`try-event`** is the owner's first check: for each option it runs the setup, fires the event, reads, picks, reads again, and writes a table to the run folder. The options share one game, each starting from the state the one before left, so write the setup to put back what the options change, or say so when reporting. It exits 0 only when every option fired and was picked.
- **`enter-game`** makes the two clicks past the country-select screen (about a minute); **`advance N`** lets at least N days pass and pauses again. Only needed when the check needs time to pass. A variable a setup set on the country-select screen survives entering (verified 2026-11-11; laws and modifiers changed there were not read afterwards). **A setup that changes a law there stops `enter-game`**: the game's "We now have …" window covers the click (#1598). `enter-game` sees that no country got selected (it compares the lobby's side panel before and after the click) and answers `no_country_selected` before clicking Start, so the session goes on, but no verb closes that window: enter first, then run setups that change laws. The same refusal comes when the lobby's view is not on a country: leave the mouse off the screen's edges while a session runs (the map scrolls under a cursor resting there), and expect the view to move after `press`. When the panel cannot tell (the view moved between its two looks) Start is clicked all the same, and the reply is `not_entered` with "the date stayed"; that locks nothing either, since nothing moved: `enter-game` can be run again (`advance` runs it again). Any other failure after the clicks (`not_entered` with a `cause`, `left_running`, a code such as `tag_failed`; `status` then shows `left_running: true`) means the game may be in play: `advance` and `enter-game` are refused until `stop`, while `console`, `events` and `pick` still work. **`press esc`** sends one key to the game itself, for looking at what a key does (`shot` before and after); it is a probe, not a way past a window.
- **`selfchecks [--run ID]`** prints the verdicts of the mod's `TE_SELF_CHECK` lines for a run, the newest by default: `broken` names each BROKEN check once, and `checks` has a row per check and source (`name`, `verdict`, `line`, `source`), each BROKEN first, then a START whose verdict never came. `source: fixture` marks the lines of the run that made the fresh save, the only place the checks a new game logs at its setup ever appear; they are kept, with the `TE_MONUMENTS` lines, in `<backup root>/fixtures/<key>/lines.log` for as long as that save is. With a session live it flushes the game's log first (one empty read; `flushed` says whether it could, `not_flushed` why not). It needs no session, works after `stop`, and exits 0 whatever the verdicts, so read `broken`. `stop` writes the same list into `summary.md`. A line is shown as the run's only where that is proved, and the reply says what that cost: `fixture.kept: false` with a `detail` (the fresh save predates this, its run did not get as far as keeping its lines, keeping them failed, or it was made again after the run asked about); `log_not_read` (or a note at `stop`) when the game had ended by itself, or could not be proved alive after its log was read, so that the lines could not be trusted to be its own; and `session.unvouched`, with `unvouched: true` on each session row, when `watch` saw another Victoria 3 process beside the run's game, which no proof rules out. Report those with the verdicts: a missing line is not an OK, and an unvouched row is not a verdict.
- **Before calling a read BROKEN**: pair every expected "no" with a read of the same form that must say "yes"; a read with `ok: false` is a form the harness cannot evaluate, not a "no" (the forms that work are in `docs/guides/python_tools.md`, "What the first play-test runs added"); and the save is 2 January 1836, so what a system seeds at the first monthly pulse is not there until February.
- **`click X Y`** is for the engine's own tool windows (the script profiler's call graph) and the console's input line, nothing else: one left click at fractions of the client area, then a screenshot. It can press anything a player can, so take a `shot` first and aim from it. **Never aim it at the game's own menus** (save, load, settings, exit): the restore puts back only the autosaves and a `--save` file, so a manual save the click overwrote, deleted or added would stay, and `stop` would still say `restored`. A click into a tool window takes the keyboard: before the next `read` or `console`, click the console's input line, or the command never arrives (`no_stop`, `arrived: false`). It was at `click 0.1125 0.544` with the console open on the left in the owner's window on 2026-11-12; another window size or UI scale moves it, so aim from a `shot`. `click_refused` pressed nothing; `click_unknown` may have pressed, so take a `shot` before clicking again; a reply with `screenshot: null` and `screenshot_error` did click. It works under `left_running`, like `console`.
- **`stop`** ends the harness's own game, waits for its watcher, restores, removes the overlay and ends the server. Read its reply.

## Reading a stop

| Reply | Meaning | Do |
|---|---|---|
| `outcome: restored` | The owner's files are back as they were | Done. Run `doctor` to confirm nothing is left |
| `outcome: held` | The restore stopped for the owner to decide; `restored`, `removed` and `retimed` list what it had put back by then (for most holds, the playset at most) | Report the snapshot id and the reason; start nothing. After `retime_unverified`, name the file too (the journal's last `held` entry, `files`) and what to do about it (`docs/guides/python_tools.md`, the hardenings bullet) |
| `outcome: game_left_up` | The game may still be running; nothing was restored beside it | Follow `next` exactly; ask the owner to close the game if it says so |
| `outcome: refused` | The restore would not run yet | `stop` again when `next` says so; otherwise `recover`, then `remove-overlay` |
| `overlay_kept: true` | The overlay folder was left because a playset may still name it | `remove-overlay`, once `next` allows it. Never delete the folder by hand |

## After a refusal or a crash

- `no_answer`: the verb in front may still be running. `status`, wait, never start a second session.
- `watch_ended`: the game has gone or could not be proved to be the harness's own. Nothing more is typed. `stop`. A `read` that ended so after its values were evaluated carries them as `reads` (a `try-event` row keeps them too).
- `session_running`, `overlay_left`, `playset_not_restored`, an unfinished run in `doctor`: an earlier session did not finish. `stop` if its server answers; otherwise, once no Victoria 3 process runs, `recover`, then `remove-overlay`, then `doctor`.
- The session's server died: the game's watcher keeps recording by itself. Same path: no game running, `recover`, `remove-overlay`. If the game is still up, no verb ends it: ask the owner to close it, and run nothing until they have. This path has only been tested against fakes, so read each reply before the next step.
- Anything the verbs cannot finish: stop, leave the files alone, and tell the owner what `doctor` and `held` print.

## What to tell the owner afterwards

What was checked and what the game answered (attach the run folder's `summary.md`, under `<backup root>/runs/<snapshot id>/`; its Self-checks table lists every `TE_SELF_CHECK` verdict, BROKEN first), whether the stop restored or held, whether the game is closed, and anything the run changed that the restore does not cover (it covers the autosaves and a `--save` file, not the owner's other saves, and the Continue pointer, the playset, console history, settings and logs; the harness's fresh saves `te_qa_fixture_<key>.v3` and `te_qa_fixture_<key>_d<date>.v3` stay in `save games/` on purpose). Detail and the engine facts behind the verbs: `docs/guides/python_tools.md` § "Driving the game from a session" and `docs/superpowers/specs/2026-11-10-in-game-qa-harness-design.md`.
