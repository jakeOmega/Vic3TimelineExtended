# Game QA skill

`python3 -m game_qa` starts the game, drives it and restores the owner's files. Every verb prints one JSON object and exits 0, or 2 for a refusal, a hold or an error. A refusal says what to run next in `next`: do that, not something of your own.

## Three rules before anything else

1. **Ask the owner before launching**, unless they granted launches for this session in their own words. A grant has limits (a time, "after I leave"): keep to them. One standing grant (owner, 2026-11-19): a session asked to run the vanilla patch runbook may launch `script-docs` for its dump while the GPU is under 50% and no game runs; on `gpu_busy` or `other_game`, ask the owner to quit what is running, and never pass `--owner-confirmed-busy` for it. **A dated fixture's run past March 1836 (`fixture`, below) needs a grant of its own**, for that run and its hours: a grant of launches for the session does not cover it. Even with a grant the tool's gate decides: it refuses beside a game it did not start, and on a busy GPU. Never pass `--owner-confirmed-busy` unless the owner was asked about that reading and said yes.
2. **The game starts only through `start` or `fixture`** (or part 1's `launch`). Never run `victoria3.exe`, the launcher or PowerShell yourself, never end a game process by hand, and never edit, copy or delete anything in the game's user-data folder: the verbs do all of it, with checks. One exception, the owner's (2026-11-24): **a save of theirs is never loaded directly; copy it and load the copy** ("make a copy and use the copy. Please don't load my own saves directly, but they are a good source for creating new harness saves"). Copy it inside `save games/` under a name of your own that starts `te_qa_copy_` (`cp "…/save games/autosave_exit.v3" "…/save games/te_qa_copy_<what>_<yyyymmdd>.v3"`, then `cmp` the two), before `start`, and name the copy in `--save`. The `te_qa_` prefix makes the restore treat it as the harness's and not as a save of the owner's; not `te_qa_fixture_`, which `prune` deletes. Give `--playset current` when the game was played on the owner's playset, and say in the report that the copy is there (74 MB each on 2026-11-24).
3. **A hold is the owner's.** `held` in a reply means the tool could not prove that putting the files back was safe (the owner may have played since), so it stopped. Most holds change nothing but the run's playset, which goes back when no game is running. Three come later: `modified_during_restore` (a file changed under the restore; the files before it were already put back), `retime_unverified` (everything was put back, and one file was left with the snapshot's time over bytes nobody could vouch for) and `manual_save_changed` (everything was put back, but one of the owner's own saves was overwritten or deleted, and no copy of it exists). The reply's `restored`, `removed` and `retimed` list what was done. Only the owner resolves a hold. Tell them which snapshot and why, and start nothing more.

## The order of verbs

```bash
python3 -m game_qa doctor                       # ready? starts nothing
python3 -m game_qa start --permission "<the owner's words, and when>" --as FRA \
        [--setup NAME=FILE]... [--playset mod_only|current] [--save NAME] [--switch-rule RULE=SETTING]... \
        [--game-arg FLAG]... [--add-mod WINDOWS_PATH]... [--unresponsive-s S] \
        [--fixture DATE]                        # a dated fixture made by `fixture`, below
python3 -m game_qa fixture --until 1900 --dry-run                  # the estimate; starts nothing
python3 -m game_qa script-docs --permission "<the grant>" --version 1.15.2   # the mods-off engine-doc dump, then stops
python3 -m game_qa fixture --until 1900 --permission "<the owner's grant of this run>" --max-hours H
python3 -m game_qa read "c:FRA.gdp" "root.has_technology_researched = railways"
python3 -m game_qa run-setup NAME               # a setup, run through its event
python3 -m game_qa add-setup NAME=FILE          # a new setup for the running game (the game reloads: ~70 s)
python3 -m game_qa press esc                    # one key in the game itself: a probe (shot before and after)
python3 -m game_qa console "event my_events.3"
python3 -m game_qa events                       # what is pending, with numeric ids
python3 -m game_qa pick 0 my_events.3           # option index is 0-based
python3 -m game_qa try-event my_events.3 --setup NAME --read "c:FRA.gdp" --read "..."
python3 -m game_qa enter-game ; python3 -m game_qa advance 10 ; python3 -m game_qa shot
python3 -m game_qa click 0.5 0.5                # one click at fractions of the window, then a shot
python3 -m game_qa click --console              # click the console's input line: the keyboard back after a click
python3 -m game_qa profiler-roots               # the script profiler at its roots, shot, call graph cropped
python3 -m game_qa profiler-roots --as-shown    # the same crop of the window as it is, nothing typed
python3 -m game_qa gui-show TYPE [--context je:KEY] [--outlines] [--scale S] [--var K=V]
                                                # one GUI type from this checkout, alone in game, cropped
python3 -m game_qa gui-hide                     # clear a preview left up by --keep
python3 -m game_qa wheel 0.6 0.5 -3             # three notches of the wheel at a point (negative scrolls down)
python3 -m game_qa drag 0.5 0.5 0.7 0.7         # press, move, release, then a shot
python3 -m game_qa view panel:budget:te_banking  # open a view by script: keys set, panels opened, no click (#2056)
python3 -m game_qa crop 0.02 0.05 0.24 1 --settle   # a region at full resolution, shot until two shots agree
python3 -m game_qa hover 0.17 0.22              # the cursor left on a point, nothing pressed: a tooltip
python3 -m game_qa capture --permission "<the grant>" [--only ID]... [--write]   # the guide's pictures, from the manifest
python3 -m game_qa selfchecks [--run ID]        # the mod's TE_SELF_CHECK verdicts, every BROKEN first
python3 -m game_qa profile start                # clear the tick timings, script profiler on
python3 -m game_qa profile dump [LABEL]         # both dumps, copied into the run folder at once
python3 -m game_qa profile pops [LABEL]         # every pop (logging.popstats), copied as pop_stats_LABEL.csv
python3 -m game_qa profile summary [LABEL [LABEL2]] [--run ID]   # wall clock, tick tasks, script by file
python3 -m game_qa stop                         # always, even after a failure
```

- **`start`** takes two to four minutes (a `--save` from late in a game can add up to ten while it loads): it snapshots, builds the overlay mod, makes a fresh save if none is cached for this build (an unattended run of its own), loads it, attaches the debugger and opens the console. `--permission` records where the go-ahead came from. Without `--save` the game sits on the fresh save's country-select screen with time stopped, which is all that reads, events and picks need. Give `--save` the name `save games/` lists (any letter case; it is stored and put back under the listed spelling): a short 8.3 name such as `FRENCH~1`, which the drive also answers to, is refused `bad_argument`, naming the listed file. `--playset mod_only` (the default) loads only this mod's deployed folder; `current` loads the owner's playset. The build under test is whatever is in the deployed mod folder, so deploy first if the change is not there.
- **`script-docs`** takes the mods-off `script_docs` dump a vanilla bump needs (#1907; `docs/guides/vanilla_patch_runbook.md` § 0): one game on `launch --playset none` (no mod, no overlay, no save, `-no_crash_reporter`) that starts a new game by itself (`-handsoff -run_until=1836.3.31`), the console opened with `log list`, and the command typed once a line of script has run in `debug.log` (live 2026-11-19: `select_event_option list` and `script_docs` both crashed a game at its bare main menu, which has no game state; `log list` did not), the six logs of the user-data `docs/` waited for until each is rewritten, copied into the run folder (`script_docs/`) and checked there (all six, none empty, the mod's `country_add_anticolonial_ideology_to_igs_bool` absent from `modifiers.log`), then the stop, then a copy to `~/src/vic3-engine-docs/<version>/docs` (`--out DIR`: a path ending in the version, outside the Modding-Digests clone). Refused before anything starts: `version_mismatch` (`--version` is not the installed `rawVersion`), `out_exists` (`--force` replaces a folder of the six logs, nothing else: `out_not_a_dump`), `out_version`, `inside_digests`, `no_version`. Refused after the stop, keeping nothing: `no_game_state`, `stale_docs`, `docs_unsettled`, `mod_loaded`, `changed_while_copied`, `crashed` and `watch_ended`; a crash's reply names the new folder under the user data's `crashes/` (`crashes`). The reply's `dump_next` has the pin and the `vanilla_patch_diff.py docs` command; `next` is the same after a clean stop, and otherwise what the stop left to do, which comes first (a hold is the owner's, rule 3). Pinning stays the runbook's step. The owner's `docs/` keeps the new dump: it is the game's output, outside the snapshot set. `script_docs.json` in the run folder holds the reply.
- **A setup** is a file holding an effect block's body, run in the played country's scope. Give the ones you know you need at `start`. **`add-setup NAME=FILE`** adds one to the running game: it rewrites the overlay's effect file, the game reloads it (about 70 seconds, live 2026-11-12, and its window does not respond at all meanwhile, so run nothing else until the verb answers), and the reply's `loaded: true` means the game logged the new revision. `not_reloaded` means it did not within five minutes: the setup is in the file, and `run-setup` and `read` look again before they run. A `game_gone` from another verb during a reload is the frozen window, not a dead game: `status` says whether `watch` has returned. A name is used once; thirty can be added in a session. Run live 2026-11-12, before and after `enter-game` (`docs/testing/game-qa-results-2026-11-12.md`). **On a late save, give every setup at `start`**: on the June 2043 save with the owner's playset, four `add-setup` calls each answered `not_reloaded` while the game hung for about 18 minutes in all (2026-11-25, #2070). **A setup with a `$` outside a `#` comment is refused `setup_parameterized`**, naming the line: the overlay calls the setup `= yes`, and a `$` makes its effect parameterized, so the engine would skip it, logging nothing when it runs. A `$` inside a quoted string counts. Fill in every placeholder before `start`.
- **The fresh save's game rules are the ones the owner last applied in a lobby**, not the defaults: an unattended new game reads `LastAppliedRules` from the user-data folder's `player/game_rules/presets.txt`. `start`'s reply lists them (`rules.settings`), and the fixture is remade when they change. Where the save loaded holds a rule otherwise (a switched copy, or a harness fixture named with `--save`, switched or not), the reply's `rules.lobby_differs` names it; a rule only one of the two lists names is compared at its default and marked `assumed_default`. An owner's own save is not compared. A rule setting's `apply_modifier` did not follow the save in the runs of 2026-11-13; it seems to follow the last lobby (#1767). Say which rules a check ran under when a row depends on one (Tax Code, culture merges, fantastical content have all been off their defaults).
- **`--switch-rule RULE=SETTING`** (repeatable; with `--save` only when it names a fresh save of the harness's own, below) loads a copy of the fresh save with that rule switched. It is a rule changed on 2 January 1836, a day after the game began, as the change-country screen changes it mid-game: what the game's setup decided under the old setting has already happened. That is the right test for "a rule switched off mid-game ends its journal entry", and not proof of how a game made under the setting starts. A rule from the first day needs the owner to apply it in a lobby first (start a New Game with it and quit): ask them, since the harness never writes their `presets.txt` (owner, 2026-11-12). No verb changes a rule in an entered game. (Run live 2026-11-12 with the Tax Code switched off: the game loaded the copy, reported the new setting, and the mod's rule-off handler ran for every country at its next monthly pulse. Other rules are untried: pair the rule's `has_game_rule` read with one that must say yes.)
- **`--save te_qa_fixture_<key>` names one of the harness's own fresh saves**, another build's or one made under other rules (`start --fixture`'s refusal lists them as `stale`; `ls` the save folder for the rest). Type it as listed, all lower case: another letter case is taken for a save of the owner's. It opens on the country-select screen, so `enter-game` works on it, and `--switch-rule` switches a rule in a copy of it (not in a copy with a rule already switched, `…_s<8 hex>`; nothing is pruned). That is how a game made under one setting gets the other: a market game from the day before, switched to Free Market Construction Disabled, 2026-11-13. A start with no `--save` makes this build's fixture and prunes all but the two newest plain ones with their copies, so run the older one first. **A rule setting's `apply_modifier` line does not follow a switched copy, or any save loaded this way**: it did not follow the save in the runs of 2026-11-13 and seems to follow the owner's last applied rules (inferred; #1767), so a check of such a line needs the owner's lobby (`docs/testing/direct-construction-playtest.md`).
- **A dated fixture** is a fresh save from later in a game: `fixture --until DATE` makes one with an unattended, AI-only run from 1836 to DATE on this build (`te_qa_fixture_<key>_dYYYYMMDD.v3`, kept and reused while the build, game, playset, DLC and rules stay the same), and `start --fixture DATE` loads it. `start` never makes one: a missing one is refused `no_fixture` with what to run, and `stale` lists that date's fixtures from other builds, which `--save NAME` loads. **A run past 31 March 1836 needs the owner's own grant for that run and its hours; a grant of launches for the session does not cover it.** It takes hours of their desktop (about 5 to 1900, 7 to 1925, 10 to 1950, 18 to 2000: the estimate is anchored to the first long run, past 1948 a guess) and writes quarterly autosaves into their `save games/`, which the restore puts back. Run `--dry-run` first and give the owner its `estimate_h`; then pass `--max-hours` with the hours they granted (refused `over_grant` when the estimate is more) and run the verb in the background: it answers when the run ends. `stop` cannot interrupt it; closing the game ends it early with no fixture (its exit autosave, a plain-text save dated inside the run, is the run's and is put back over). End a session with `stop`, never by closing its window: a session's exit autosave holds `not_the_runs_save`. Don't deploy while it runs (the deploy watcher runs while VS Code is open), or the reply says `build_changed`. **Tell the owner not to play on another PC meanwhile**: `save games/` syncs through OneDrive, and an autosave from there looks like the run's; the restore holds (`not_the_runs_save`) when it can tell, which is not always. A hold of `save_not_kept` means the run's save could be neither renamed nor copied: it is in `save games/` under the engine's `TEST_FAIL_…` name, and the owner moves it, and the next `restore <id>` (or `stop`) then goes ahead: the hold lasts only while that file is there. Read the reply's `save_facts` (the save's own `game_date`; `start --fixture` gives it as `fixture_game_date`, with a `date_note` when it is not the date asked), `timing` (seconds per game day by year: these set the next estimates), `lines` and `stop`. `--switch-rule` works on a dated fixture: the rule switched on its date. `--add-mod` does not (`bad_argument`): a dated fixture is made without variants, so load it with `--save te_qa_fixture_<key>_d<date>` beside the variant instead. **Run live to 1925** (2026-11-16, three runs, `docs/guides/python_tools.md` § Dated fixtures): 1836 to 1925 took 6 h 46 min against the old estimate of 4.85 h, and 1836 to 1850 52 min against 0.69 h; the estimate now takes its rates from the first of those runs (#1602), but builds differ by a fifth or so, so still ask for a grant above it, and run a short one first (`--until 1836.7.1`). **To play on from a dated fixture**, use a session, since `fixture` refuses a save (`handsoff_on_a_save`): `start --as <TAG> --save te_qa_fixture_<key>_d<date>` with a small independent country at peace that sits idle, `enter-game`, then `advance N` in a loop that always ends with `stop`, inside the owner's grant of the hours. Run live 2026-11-16 from 1925 to 1948: 300 days a call, 337 to 456 s each, about seven and a half game years an hour; the run folder's `debug.log` was complete (`docs/testing/ai-probe-runbook.md` § A run from a save).
- **`read`** evaluates triggers and values at a breakpoint in the played country's scope: `c:TAG.<value>`, `root.<value>`, a script value's name, `c:TAG.var:x`, a trigger. Write a trigger bare (`has_modifier = x`); `c:FRA.has_modifier = x` is refused by the game as an unknown trigger type. An unset variable reads 0, so read `has_variable = x` when that matters. A read that fails comes back `ok: false` with the game's words; the verb still exits 0. A read whose command never reached the console (the first after `start --save` on the 1931 save, #1702) is typed once more, only when that is proved: the console history's last line was another command, a probe got through afterwards, the history has still gained no line of it, and no stop came (so a read straight after a read is never typed again). The read's step in `steps.jsonl` then says `retried: true`; otherwise `no_stop` says why not in `not_retried`. Built 2026-11-12 against the fakes, not yet seen live.
- **`console`** types one command (ASCII, at most 64 characters). `event <id>` ignores the event's trigger and cooldown. There is no console `effect` or `run`: use a setup.
- **`pick INDEX [EVENT]`** answers an option of the oldest pending instance, and the reply's `form` says which command went: `id` (`select_event_option <index> <id>`, the id as `events` listed it) for any id up to 2^31 - 1, so that only that event can be answered; for a higher id, which the console takes in no typed form (live 2026-11-13 on the 1931 save: the listed id and its signed form, id - 2^32, both answered "No matching pending event"), `select_event_option <index>` with no id, which takes the first event listed: `no_id` when the event is alone in the list (live, #1732), `oldest` when it is first and also the lowest id. Ids carry a high byte that changes between games, so the lowest id need not be the oldest. Any other high-id event is refused `id_unaddressable` with nothing sent, and the detail says what is left: answer the events listed before it, or, for one listed first, `console "select_event_option N"` unchecked, then `events`. A list line `pick` cannot read refuses the two forms with no id (`bad_reply`). `attempts` has the command and its answer. After a `not_selected`, run `events` before anything else.
- **`try-event`** is the owner's first check: for each option it runs the setup, fires the event, reads, picks, reads again, and writes a table to the run folder. The options share one game, each starting from the state the one before left, so write the setup to put back what the options change, or say so when reporting. It exits 0 only when every option fired and was picked.
- **`enter-game`** makes the two clicks past the country-select screen (about a minute); **`advance N`** lets at least N days pass and pauses again. Only needed when the check needs time to pass; for one system's monthly logic, running its monthly effect from a setup (`--setup step=FILE`, `run-setup step`) tests it with the game paused, which on a slow late save is also the safe way: there `advance`'s date read can meet a running tick and crash the game (#1963; `docs/guides/python_tools.md`, "A month of one system without passing days"). It plays at most about 400 s a call (20 rounds of at most 20 s, `MAX_ROUNDS` and `MAX_WAIT_S`), then answers `stalled`, so N must fit at the speed the game loaded with: 300 days did in 1925-1948. A variable a setup set on the country-select screen survives entering (verified 2026-11-11; laws and modifiers changed there were not read afterwards). **A setup that changes a law there raises the game's "We now have …" window over the country click** (#1598). `enter-game` sees that no country got selected (it compares the lobby's side panel before and after the click) and, without clicking Start, clicks the screen's Back button instead, which enters the game as the tagged country past the window (live 2026-11-13; the window stays up in the entered game, and `advance` works under it). The reply then has `fallback: "back"` and `country_click`. The same happens when the lobby's view is not on a country: leave the mouse off the screen's edges while a session runs (the map scrolls under a cursor resting there), and expect the view to move after `press`. When the panel cannot tell (the view moved between its two looks) Start is clicked all the same, and the reply is `not_entered` with "the date stayed"; that locks nothing either, since nothing moved: `enter-game` can be run again (`advance` runs it again). Any other failure after the clicks (`not_entered` with a `cause`, `left_running`, a code such as `tag_failed`; `status` then shows `left_running: true`) means the game may be in play: `advance` and `enter-game` are refused until `stop`, while `console`, `events` and `pick` still work. A helper error on a click itself is split as `click`'s is: `click_refused` pressed nothing and locks nothing; `click_unknown` may have pressed, and on Start counts as a failure after the clicks (`left_running`). After a `click_refused` on Start the country stays selected, so a second `enter-game`'s panel check sees no change and it goes in by the Back button, as the tagged country (shown against the fakes, not yet live). **`enter-game --via back`** goes straight to the Back button (bottom left, the console shut first), which enters the game as the country played (live 2026-11-13, twice from the fresh save). Its reply's `back_shot` shows what the click did; a failure after the click needs `stop`. **`press esc`** sends one key to the game itself, for looking at what a key does (`shot` before and after); it is a probe, not a way past a window.
- **`selfchecks [--run ID]`** prints the verdicts of the mod's `TE_SELF_CHECK` lines for a run, the newest by default: `broken` names each BROKEN check once, and `checks` has a row per check and source (`name`, `verdict`, `line`, `source`), each BROKEN first, then a START whose verdict never came. `source: fixture` marks the lines of the run that made the fresh save, the only place the checks a new game logs at its setup ever appear; they are kept, with the `TE_MONUMENTS` lines, in `<backup root>/fixtures/<key>/lines.log` for as long as that save is. With a session live it flushes the game's log first (one empty read; `flushed` says whether it could, `not_flushed` why not). It needs no session, works after `stop`, and exits 0 whatever the verdicts, so read `broken`. `stop` writes the same list into `summary.md`. **It shows nothing for a `fixture` run itself** (its folder holds `fixture_debug.log`, not a session's log): read that run's verdicts in `<backup root>/fixtures/<key>/lines.log`, or, for a run that made no fixture, with `grep -a TE_SELF_CHECK` on its `fixture_debug.log`. A line is shown as the run's only where that is proved, and the reply says what that cost: `fixture.kept: false` with a `detail` (the fresh save predates this, its run did not get as far as keeping its lines, keeping them failed, or it was made again after the run asked about); `log_not_read` (or a note at `stop`) when the game had ended by itself, or could not be proved alive after its log was read, so that the lines could not be trusted to be its own; and `session.unvouched`, with `unvouched: true` on each session row, when `watch` saw another Victoria 3 process beside the run's game, which no proof rules out. Report those with the verdicts: a missing line is not an OK, and an unvouched row is not a verdict.
- **Before calling a read BROKEN**: pair every expected "no" with a read of the same form that must say "yes"; a read with `ok: false` is a form the harness cannot evaluate, not a "no" (the forms that work are in `docs/guides/python_tools.md`, "What the first play-test runs added"); and the save is 2 January 1836, so what a system seeds at the first monthly pulse is not there until February.
- **`profile start`, `profile dump [LABEL]`, `profile summary [LABEL [LABEL2]]`** measure the game as `docs/audits/late_game_performance.md` does (#1700; run live 2026-11-13 on the 1931 save, before the PR's review fixes, `docs/testing/game-qa-results-2026-11-13.md`). `start` clears the tick-task timings and turns `ScriptProfiling` on. `dump` writes both dumps and copies them into the run folder as `tt_<label>.csv` and `sp_<label>.txt` (the label defaults to the game date), each only once its size or time has changed and it has held still; a dump that fails leaves no copies. Never copy the user-data root's `ticktask_timings.csv` or `logs/` by hand: the snapshot set covers the CSV, so the restore puts the owner's back, and the session copies `dedicated_server.log` (the wall clock) into the run folder itself. `summary` needs no session and works after `stop`: one label gives the window from `profile start` to that dump, two give the window between the dumps. It reports wall time per game day and per frame type (a pause never counts), the top tick tasks, and script time by file marked mod, vanilla or `add_mod`. Read `running.seconds_per_day` as the headline: the per-type `gaps` figures leave out the frames a pause followed, often the long weekly ones (`uncounted`). No time across a break in the server log (lines lost in its rotation, a clock step) or a gap of 60 s or more counts, and the notes say when there was one. A `profile start` refused after its clear went through still cleared the timings, so no window spans it (`restarted_between`). On the live run `dump A` wrote 8,283 rows, the game's count, `summary A` gave 1.781 s a day and `summary A B` 1.25, `stop` put the owner's root CSV back, and `summary A --run <id>` worked after it. Play at speed V with panels closed, as the audit says, and `advance` across a month boundary. `log_ticktask_performance` writes nothing; don't use it. **`profile pops [LABEL]`** (#1758; needs no `profile start`; built against the fakes, not run live yet) types `logging.popstats` and copies the `logs/<id>/pop_stats.csv` it names into the run folder as `pop_stats_<label>.csv` once it holds still (a 19 MB file on the 1931 save); never copy it by hand. The game's folder stays: the restore removes no folder, so the stop's reply names it, with any other folder in `logs/` the snapshot did not list, under `left_behind`, with a note. Tell the owner, who deletes it; never delete it yourself.
- **`start --game-arg FLAG`** adds `-disable_renderframeifneeded`, `-no_notifications` or `-script_profiling` (nothing else) to the run's game; write it without the dash or as `--game-arg=-FLAG`. The fixture's run never gets it. **`start --add-mod WINDOWS_PATH`** loads a variant mod folder after the deployed mod and before the overlay, for an A/B of a fix on the same save: a drive path such as `'D:\vic3te-data\variant'` (quote it in the shell), outside the user-data folder, holding `.metadata/metadata.json`, with no link or junction on the way or anywhere inside (copy files in, never link them). ## Reading a stop

| Reply | Meaning | Do |
|---|---|---|
| `outcome: restored` | The owner's files are back as they were | Done. Run `doctor` to confirm nothing is left |
| `outcome: held` | The restore stopped for the owner to decide; `restored`, `removed` and `retimed` list what it had put back by then (for most holds, the playset at most) | Report the snapshot id and the reason; start nothing. After `retime_unverified`, name the file too (the journal's last `held` entry, `files`) and what to do about it (`docs/guides/python_tools.md`, the hardenings bullet). After `manual_save_changed`, name the saves (`manual_saves`: `changed`, `missing`): nothing can put them back, and a later `restore` of that snapshot holds again while they differ |
| `manual_saves` in a reply, or a note on saves | `new`: a save matching no harness name appeared and was left; `changed` or `missing` beside another hold's reason; `unrecorded`: the snapshot predates the sizes and times, so an overwritten save could not be told | Name each save to the owner |
| `outcome: game_left_up` | The game may still be running; nothing was restored beside it | Follow `next` exactly; ask the owner to close the game if it says so |
| `outcome: refused` | The restore would not run yet | `stop` again when `next` says so; otherwise `recover`, then `remove-overlay` |
| `overlay_kept: true` | The overlay folder was left because a playset may still name it | `remove-overlay`, once `next` allows it. Never delete the folder by hand |

## After a refusal or a crash

- `no_answer`: the verb in front may still be running. `status`, wait, never start a second session.
- **A game that crashed during `fixture`** (2026-11-16, October 1913): exit 2, `refused: fixture_failed`, `step: save`, "the run left no TEST_FAIL_te_qa_fixture_*.v3". The restore has run (`stop.outcome: restored`, `held: false`), so the owner's files are back and nothing waits on them; there is no fixture, no `lines.log` and no `timing`. The run folder's `fixture_debug.log` keeps everything up to the crash: read its self-checks with `grep -a TE_SELF_CHECK`. The crash is in the game's user data, `crashes/victoria3_<stamp>/`; `scripts/analysis/crash_stack_strings.py <that folder>` names the script it was running (the log-triage skill).
- **A crash leaves no crash reporter waiting** (#1905): every launch passes `-no_crash_reporter`, and `stop`'s restore (and `recover`'s) closes a reporter the run's own crash left up anyway, once nothing holds and right before it puts anything back, so the next run can start. The reply lists it in `reporters_closed`. A held run never has one closed. Any other reporter (it started before the run's game or long after its end, another game ran, `watch` failed a look) is left for the owner and named in `reporters_left`; if its open log then refuses the restore (`refused: error`, `Permission denied`), the detail says so: tell the owner, and once they have closed it, `recover`. `doctor`'s `crash reporter` line shows one that is up. Never end a reporter by hand (rule 2): the verbs do it.
- `watch_ended`: the game has gone or could not be proved to be the harness's own. Nothing more is typed. `stop`. A `read` that ended so after its values were evaluated carries them as `reads` (a `try-event` row keeps them too).
- `session_running`, `overlay_left`, `playset_not_restored`, an unfinished run in `doctor`: an earlier session did not finish. `stop` if its server answers; otherwise, once no Victoria 3 process runs, `recover`, then `remove-overlay`, then `doctor`.
- The session's server died: the game's watcher keeps recording by itself. Same path: no game running, `recover`, `remove-overlay`. If the game is still up, no verb ends it: ask the owner to close it, and run nothing until they have. This path has only been tested against fakes, so read each reply before the next step.
- Anything the verbs cannot finish: stop, leave the files alone, and tell the owner what `doctor` and `held` print.
