# Translations

The mod is written in English. `localization/english/` is the only loc the repo holds, and the game shows raw keys (not English) for any key missing from the player's language. So `scripts/deploy.sh` builds every other language's loc at deploy time with `scripts/generators/gen_non_english_loc.py`:

- a language **with** a folder here (`i18n/<language>/tm/`) gets its translations swapped in, key by key, with English wherever a key has no translation yet;
- every other language gets the English as it is.

None of the generated `.yml` is committed. The translation memory is.

Three languages have one: German (`german/`), Spanish (`spanish/`) and Russian (`russian/`), all machine-translated.

## What's here

| Path | What |
|---|---|
| `<language>/BRIEF.md` | The translator's instructions: markup rules, grammar conventions, voice. Every agent run reads it. |
| `<language>/terms.json` | Terms coined during runs, English → translation (the mod's recurring names that aren't loc keys of their own, plus official game terms agents kept getting wrong). `prepare` adds the ones a chunk contains to its glossary; `check-terms` finds translations that disagree. Add to it whenever a report shows two chunks rendering one term differently. |
| `<language>/tm/<file>.json` | The translation memory, one file per English loc file. Each key maps to `{"en": <the English it was translated from>, "de": <the translation>}`; the translation's field is the language's code in `TM_FIELDS` (`"de"`, `"es"`). German's declined country-name forms (`AFU_DAT`, …) have no English key of their own; they carry `"base": <key>` and sit with that key. |

## What differs by language

`scripts/i18n/translate_loc.py` keeps what differs between languages in four tables, each taken from what the base game's own loc does in that language (issue #566 has the survey):

| Table | German | Spanish | Russian |
|---|---|---|---|
| `TM_FIELDS`: the TM field, and `--field`'s default | `de` | `es` | `ru` |
| `COUNTRY_FORMS`: declined country names, reached through `GetAltName('<FORM>')` | seven forms per name (`NOM` … `NACH`), translated in the glossary chunk | none: names stay `GetName`, and merge rejects a `GetAltName` | none for now, as for Spanish: vanilla declines (`RU_CL_RP` …, issue #566), but the first run had no game files to read its forms from, so the brief phrases around the name («страна X») |
| `QUOTES`, `QUOTE_MARKS`: the marks merge rewrites the English's `\"…\"` and a stray `"` into | „…“ with ‚…‘ inside | «…» with “…” inside | «…» with „…“ inside |
| `THOUSANDS_SEPARATOR`, `CLOSED_PERCENT`: what merge writes for 1,000, and whether 10 % closes up | 1.000, 10% | 1 000 with a no-break space, 10% | 1 000 with a no-break space, 10% |

A new language needs a row in each table it differs in, a `BRIEF.md` (copy the nearest one and rewrite its grammar, number, quote and voice sections against the base game's loc in that language), and an empty `terms.json`. Pass `--language <folder>` to every command below; the default is German.

## When the English changes

A translation stays attached to the English it was made from. When that English changes, the key is **stale**:

- a small change keeps the old translation until the next run. For text of six words or more, that means the same numbers, the same `$key$` splices (one added, removed or renamed is a large change: a phrase replaced by a splice reads as a small edit, but the old translation still has the phrase) and at least 85% similarity; for shorter text (names, labels), only case, spacing or final punctuation may differ. A change of spelling only, British to American as `scripts/analysis/check_loc_spelling.py` makes it (Licence to License), is small at any length. `python3 scripts/i18n/translate_loc.py respell` re-points a translation whose English changed only that way at the new English, so `prepare` doesn't offer it to an agent again; run it before a pass.
- anything larger ships English until the key is translated again.

Renaming a script value, scripted GUI or variable that a line reads (`ScriptValue('x')`, `GetVariable('x')`) changes its English too, and the word count leaves the markup out, so a short line such as a panel row counts as short text and ships English. Make the same swap in the memory's `en` and `de`/`es` fields of each record, after checking that its `en` still matches the current English, so the translation keeps shipping with the new binding. Otherwise a small change keeps the old translation, old binding included (lunar colonization PR 3a, Next Windows lines).

The next `prepare` offers a stale key again, with the English its translation was made from and that translation as comments above the line (BRIEF.md § Updated lines), so the agent edits the translation rather than starting over. Developer test benches (`DEV_ONLY_FILES` in the script) are never offered.

`python3 scripts/i18n/translate_loc.py status` counts translated, stale and missing keys. A deploy prints the same counts whenever it rewrites a file.

## Running a translation pass

Translation uses Claude Code subagents (on the subscription, not the API). The script does everything deterministic around them:

1. `python3 scripts/i18n/translate_loc.py prepare --set names` writes the glossary chunk: the mod's names (concepts, journal entries, laws, buildings, technologies, formable countries). Translate it first, because every other chunk is given these names as fixed terms.
2. `python3 scripts/i18n/translate_loc.py prepare` writes every other pending key as chunks of about 9,000 words or 700 keys, whichever comes first (`--files te_events` to restrict, `--limit N` for the first N chunks). Each chunk file carries its own glossary: the mod terms and official vanilla German terms that occur in it, and what each referenced key inserts. Give a file family whose lines repeat a template (generated production methods, tax amendments) to a single agent, or one template comes out two ways: `prepare --files <prefix> --max-keys 2000 --chunk-words 30000` first, then the other files by name, because `prepare` doesn't skip keys an earlier chunk already holds. A generated file that repeats line templates, varying only their `$…$` references and `[…]` values, takes `--templates <prefix>` instead (`te_culture_merges_generated`, with its 32 copies of each line): its chunk lines are one example per template, each marked `# TEMPLATE` (BRIEF.md § Template lines), and an `x-NNN` manifest entry records the example of every other copy (below). Pass it to every `prepare` of the pass, since one without it offers the copies as ordinary lines.
3. One Sonnet subagent per chunk reads `i18n/<language>/BRIEF.md` and `build/i18n/<language>/chunks/<id>.txt`, and writes `build/i18n/<language>/out/<id>.NN.txt` part files. `python3 scripts/i18n/translate_loc.py prompt <id>…` prints the prompt to give it. Parts are capped at 100 lines for event prose and 200 otherwise, because an agent whose single response passes 64,000 output tokens fails outright. If one does fail, resume it (its context already holds the chunk) and ask for smaller parts. Eight agents in parallel took 20–30 minutes a wave. Single-word terms match case-sensitively, so a new system's everyday words (*draft*, *bill*, *promise*) never reach a glossary: settle them before dispatch and append them to the prompt of every agent whose chunk uses them.
4. `python3 scripts/i18n/translate_loc.py merge` checks every line's markup against the English and adds the lines that pass to the translation memory. Rejects are listed in `build/i18n/<language>/merge_report.json`. They stay pending, so the next `prepare` offers them again. Merge also repairs what it can decide mechanically: a plain `"` closing a „quotation“ (the repo's loc parser would cut the value there), English-format numbers left in the prose (2.5 → 2,5, 1,000 → 1.000) and, for German, a space before `%` and quotation marks: the English's escaped straight quotes (`\"…\"`) and a wrongly shaped closing mark („…”) become „…“, with ‚…‘ nested inside. After the merge, `python3 scripts/i18n/translate_loc.py expand` writes each `x-NNN` entry's template copies to `out/x-NNN.01.txt` from their examples' new translations, and `merge x-NNN` checks them like any chunk.
5. Read each agent's report (also saved as `out/<id>.report.md`, in case the session ends before the agent replies). Agents list the terms they coined and the lines they doubted; in the German run they surfaced most of the problems the markup check can't see: a vanilla term applied out of context, an English name kept where the game has an official German one, a guessed game term. Settle each by checking the vanilla loc, add the decision to `terms.json`, and `python3 scripts/i18n/translate_loc.py refresh <ids>` the chunks no agent has started, so they carry it.
6. At the end, `python3 scripts/i18n/translate_loc.py prepare-fixes` writes a correction chunk from every `check-terms` mismatch, plus lines matching `--note 'REGEX=instruction'` or named by `--key-note 'KEY=instruction'`. One agent rewrites those lines, changing only the flagged term, and they merge like any chunk. Where every fix is a plain word swap that keeps the inflection, a script can instead write `out/f-NNN.01.txt` from the TM's current text; merge checks it the same way.

How `--templates` works: `prepare` groups the file's pending keys by their English with every `$…$` and `[…]` blanked out. A line joins a group's example only if their tokens map position by position, with no example token mapping to two different ones, and the swap turns the example's English into the line's; otherwise it starts a group of its own. `expand` makes each copy from its example's translation by swapping the example's differing tokens for the copy's. It leaves a copy out where a swapped-out token survives, because the translation altered it (a case flag, `GetAltName`, a concept call's display text, which merge's markup check doesn't see). A copy left out stays pending, like one whose example didn't merge, and the next `prepare` offers it again. Lines of the file already in the memory are tried as examples first, so a new copy of a template (a 33rd merge) or a copy whose English changed only in its tokens expands from the memory without an agent. When the generator changes a template, all its copies go stale together: the next `prepare --templates` offers the example again, with its previous translation, and `expand` writes the copies from the new translation once it has merged, never from the old one. Run on the seventh pass's merged examples (below), `expand` reproduces all 917 copies per language as committed.

The Spanish run (October 2026) translated the whole mod in one pass: 29,120 keys and 404,500 words, half again the German first run. It took about an hour and a half: a glossary chunk of 2,323 names (18 minutes for one agent), then 45 content chunks with eight agents kept running at a time, then a correction chunk of 113 lines. Agents averaged about ten minutes and 220,000 tokens a chunk. One line was rejected, because the brief at first suggested swapping a `GetAdjective` for `GetName`, which the markup check counts as a lost call. What worked, for the next language:

- **Seed `terms.json` before the first content chunk.** The German list's English side, looked up in the base game's loc for the new language (`VanillaTerms`) or taken from the glossary chunk's own renderings, gave about 135 terms before the first content chunk. Pop types, interest groups, vanilla law names (the voting laws) and the UN agencies' acronyms (OMS, ACNUR, CIJ) were the terms agents most often got wrong without one.
- **Dispatch on a rolling basis, not in waves.** After each merge, add what the report settled to `terms.json`, `refresh` the chunks no agent has started, and send the next one, so eight stay busy and each new chunk carries every term settled so far.
- **Keep lowercase common nouns out of `terms.json`.** `check-terms` matches the English with its markup, so *peasants* inside `[GetPopType('peasants')]`, or *homeland* used loosely, flags correct lines. Dropping those entries cut 91 mismatches to 39, nearly all of them real.
- **Expect tier and band names to drift.** A system's level names (the UN authority tiers, the tradecraft tiers, nuclear readiness, the colonial bands, the monetary stance bands) sit as one-word label keys in one chunk while the prose that names them sits in others, and `chunk_glossary` leaves lone words out. Four agents rendered nuclear readiness "Recessed" four ways. The correction chunk took them back to the label keys' wording with `--key-note`s chosen by an English-and-Spanish regex pair per family, each note conditional ("if the word here means something else, keep the line").
