# Git and pull request workflow

How this repo's branches, stacks and multi-agent waves are run, and the traps
each has sprung. Read the section for what you are about to do.

## Parallel checkouts

**Parallel checkouts: sparse-exclude `gfx/`.** `git worktree add --no-checkout -b <branch> <dir> origin/main && cd <dir> && git sparse-checkout set --no-cone '/*' '!/gfx/' && git checkout <branch>` skips the 1.8 GB texture tree (a full worktree is ~1.9 GB). Only tasks that touch textures need a full checkout; a placeholder that copies an existing texture can be added from a sparse one with `git update-index --add --cacheinfo 100644,$(git rev-parse HEAD:<source>),<new path>` and then `git update-index --skip-worktree <new path>`. The game-independent checks (`python3 -m unittest discover -s . -p 'test_*.py'`, `ruff check .`, the `--strict` audits, `scripts/analysis/check_post_load_rosters.py`) all run in a sparse worktree with the dummy `VIC3_*` env vars from CI. Don't bracket a baseline check with `git stash` / `git stash pop` in a worktree: the stash list is shared by every checkout, so a stash of a clean tree saves nothing and the pop applies another checkout's entry. Compare against a commit instead (`git show <commit>:<path>`, or a scratch worktree).

## Stacked PRs must target `main`, not the parent feature branch

When opening dependent PRs (PR B builds on PR A's branch), `gh pr create --base <parent-feature-branch>` makes B *merge into the parent branch, not into main*. GitHub does NOT auto-retarget the child when the parent merges — merging B in that state lands its content in the (now-merged-and-deleted) parent branch and silently strands the changes. We've hit this twice (#87-#91, #96-#97). Two safe paths:

1. **Always use `--base main`** even for stacked work. The child's diff against main will include the parent's commits until the parent merges (diff temporarily looks bigger), but the merge target is correct from day one.
2. **Retarget the child's base to main before merging the parent**: `gh pr edit <child> --base main`. Must happen while the child is still open — `gh pr edit --base` rejects closed PRs.

Symptom of the bug: parent PR merges to main, child PRs show `MERGED` in `gh pr view`, but `git log main` doesn't include their commits and the file content on main doesn't reflect the changes. Recovery: push the latest descendant branch as a new ref and open a fresh PR to main (e.g., #98 recovered this session's #96/#97).

## Merging a stack of squash-merged PRs

Squash-merging the parent leaves the child's branch unable to see that it already contains the parent's changes, so `git merge origin/main` into the child conflicts wherever the child touched the parent's lines. Do **not** resolve those with `-X ours` (it would also drop unrelated sibling work). Per child, after its parent has been squash-merged: (1) `git merge origin/<parent-branch>` — a real merge of the parent's *final* tip, which already carries any conflict resolutions made against `main`; (2) confirm `git diff --stat origin/<parent-branch> origin/main` is empty (the squash commit's tree equals the parent tip); (3) `git merge -s ours origin/main` to record `main` as merged without changing the tree; (4) push, wait for CI, squash-merge. **Only when step 2 is empty.** If other PRs landed on `main` before the parent's squash, step 3 would silently drop them from the child. Instead: `git merge <squash>^` (main just before the squash, a real merge), then `git merge -s ours <squash>`, and confirm the child's changed lines against `<squash>` equal its own commits' (`git diff <squash> HEAD` vs `git diff <parent-tip> <child-tip>`). Used for #483 after #479/#482 landed ahead of #481. Only a stack's *first* PR needs a real `git merge origin/main`, where sibling stacks' append-at-end-of-file docs edits conflict — keep both sides. Used for #301–#312 (three stacks, ten PRs).

## Play-testing unmerged work

Build one integration branch from the stack tips, check it out in the **full** main checkout (`scripts/deploy.sh` rsyncs with `--delete` and includes `gfx/`, so deploying from a sparse worktree would delete the textures), `POST /reload`, then `./scripts/deploy.sh --apply`. Before `--apply`, confirm the branch contains `origin/main` (`git merge-base --is-ancestor origin/main <branch>`; merge it in if not) and read the dry run on its own: a `deleting` line means the deploy would roll back newer `main` content or someone else's deployed branch (2026-09-28: a stale PR branch deleted #570's art from the game folder). Make sure the launcher playset does not also enable a Steam Workshop copy of this mod: a later-loaded copy overrides same-path files and produces a half-old, half-new game. Vic3's console has **no `effect` command** (that is CK3) — run test script with `event <id>` (see `events/te_debug_un_events.txt`).

## Orchestrated multi-branch waves

Lessons from the second journal-entry-widget wave (#316–#322):
- **Brief each sub-agent to write its PR body to a file before returning, and to sign commits with a truthful `Co-Authored-By` (its own model).** Two API outages killed agents mid-run; anything not yet on disk was lost.
- **Treat premises pre-seeded in a brief as hypotheses.** A design step before implementation overturned the brief's premise in 3 of 6 systems.
- **Check the plan itself against Top gotchas and `scripting_best_practices.md` before dispatching it.** Implementers transcribe plan code verbatim. #500's plan applied state- and building-scoped `multiplier = var:` modifiers from a country pulse (the multiplier resolves against ROOT) and used `debug_log` accessors the docs mark as failing; both were caught only in review.
- **Check the UTF-8 BOM on every changed `.txt`, not just the `.gui`.** `bom_normalizer` repairs it on the next `/reload`, but the fix then lands as unexplained regeneration churn. Check there is exactly **one**, too. A script that decodes with `utf-8` (not `utf-8-sig`) and writes a BOM back doubles it. The engine strips one BOM and reads the other as part of the first token, so the file's first comment stops being a comment, every key after it shifts, and the whole file is dropped (`Duplicated key = will not be created`). That lost all 323 company buildings on 2026-10-03. `test_bom_normalizer` now fails CI on a doubled BOM, and `bom_normalizer` collapses one.
- **Merging sibling PRs that append to the same files** (`te_events_l_english.yml` `TE_DEBUG_*` sections, the tail of `scripting_best_practices.md`): dry-run the whole sequence in a scratch clone with `git config rerere.enabled true`, then squash-merge one PR at a time, refreshing each next branch with `git merge origin/main` (rerere replays the recorded resolutions), and confirm the final `main` tree equals the dry run. Re-read numbered lists git merged without conflict — the `gui_modding_guide.md` gotchas came out #23-before-#22. Resolving a both-added conflict by concatenating the two sides can unclose a block: git keeps the closing braces both sides share outside the conflict, so they close only the second block (2026-10-31, `space_race_events.110` lost its `}` and swallowed `.111`, and no audit noticed; the tests' parser did). Check `git diff <each parent> -- <file>` shows no deletions you didn't mean, and run the tests.
- **When you refresh a PR branch with `git merge origin/main`, "ours" is the branch and "theirs" is main**, the reverse of building an integration branch. A scripted conflict resolver written for one direction silently keeps stale rows in the other: the #573–#583 wave's table resolver put back a branch's old Banking rows in `gui_modding_guide.md`. Resolve each row against `git merge-base HEAD MERGE_HEAD` (keep the side that changed it). Before pushing, check that every line either side added since that base is in `HEAD`. rerere records such a mistake and replays it on the next identical conflict: `git rerere forget <path>` it, or clear `.git/rr-cache`.

## `gh pr edit --body-file` can fail silently here: verify or use the REST API

On this repo `gh pr edit <n> --body-file <file>` currently exits non-zero with only a GraphQL *Projects (classic) is being deprecated* notice and **leaves the body unchanged**; nothing else is printed, so a chained `&& echo ok` is the only tell. Verify with `gh pr view <n> --json body -q .body | grep -c <marker>`, or patch directly: `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@<file>`. `gh pr create --body-file` and `gh issue comment --body-file` are unaffected.

## A multi-issue PR needs one `Closes` keyword per issue

`Closes #161, #167, #168` auto-closes **only #161** — GitHub binds the closing keyword to the first number; the rest are mere references and stay open after merge. Write `Closes #161. Closes #167. Closes #168.` (or `closes #161, closes #167, …`). Bit us on #174, which silently left #167-172 open (recovered by manual close + a follow-up PR). Verify post-merge with `gh issue list` rather than trusting the PR body.

**The keyword also fires where it was not meant.** GitHub reads `fixed: #N`, `fixes #N`, `closes: #N` and their kin anywhere in a PR body or a squash commit's message, whatever comes before them. #1623's commit message said "Script bugs found and not fixed: #1612 to #1621", and merging it closed #1612 (reopened by hand, 2026-11-12). When a message lists issues it does not close, keep `fix`, `close` and `resolve` words away from the number: "reported in #1612 to #1621".
