# Git and pull request workflow

How this repo's branches, stacks and multi-agent waves are run, and the traps
each has sprung. Read the section for what you are about to do.

## Parallel checkouts

**Parallel checkouts: sparse-exclude `gfx/`.** `git worktree add --no-checkout -b <branch> <dir> origin/main && cd <dir> && git sparse-checkout set --no-cone '/*' '!/gfx/' '/gfx/models/' '/gfx/map/' && git checkout <branch>` skips the 1.8 GB texture tree but keeps `gfx/models/`, which holds only generated text (the state pictures' overlay copies, which `gen_state_pictures.py` writes and `test_state_pictures.py` checks), and `gfx/map/`, which holds only script (the fleet entities, and the statue defaults `test_power_bloc_statue_defaults.py` reads; CI's checkout keeps both) (a full worktree is ~1.9 GB). Only tasks that touch textures need a full checkout; a placeholder that copies an existing texture can be added from a sparse one with `git update-index --add --cacheinfo 100644,$(git rev-parse HEAD:<source>),<new path>` and then `git update-index --skip-worktree <new path>`. The game-independent checks (`python3 -m unittest discover -s . -p 'test_*.py'`, `ruff check .`, the `--strict` audits, `scripts/analysis/check_post_load_rosters.py`) all run in a sparse worktree with the dummy `VIC3_*` env vars from CI. Don't bracket a baseline check with `git stash` / `git stash pop` in a worktree: the stash list is shared by every checkout, so a stash of a clean tree saves nothing and the pop applies another checkout's entry. Compare against a commit instead (`git show <commit>:<path>`, or a scratch worktree).

## Stacked PRs must target `main`, not the parent feature branch

When opening dependent PRs (PR B builds on PR A's branch), `gh pr create --base <parent-feature-branch>` makes B *merge into the parent branch, not into main*. GitHub does NOT auto-retarget the child when the parent merges — merging B in that state lands its content in the (now-merged-and-deleted) parent branch and silently strands the changes. We've hit this twice (#87-#91, #96-#97). Two safe paths:

1. **Always use `--base main`** even for stacked work. The child's diff against main will include the parent's commits until the parent merges (diff temporarily looks bigger), but the merge target is correct from day one.
2. **Retarget the child's base to main before merging the parent**: `gh pr edit <child> --base main`. Must happen while the child is still open — `gh pr edit --base` rejects closed PRs.

Symptom of the bug: parent PR merges to main, child PRs show `MERGED` in `gh pr view`, but `git log main` doesn't include their commits and the file content on main doesn't reflect the changes. Recovery: push the latest descendant branch as a new ref and open a fresh PR to main (e.g., #98 recovered this session's #96/#97).

## Merging a stack of squash-merged PRs

Squash-merging the parent leaves the child's branch unable to see that it already contains the parent's changes, so `git merge origin/main` into the child conflicts wherever the child touched the parent's lines. Do **not** resolve those with `-X ours` (it would also drop unrelated sibling work). Per child, after its parent has been squash-merged: (1) `git merge origin/<parent-branch>` — a real merge of the parent's *final* tip, which already carries any conflict resolutions made against `main`; (2) confirm `git diff --stat origin/<parent-branch> origin/main` is empty (the squash commit's tree equals the parent tip); (3) `git merge -s ours origin/main` to record `main` as merged without changing the tree; (4) push, wait for CI, squash-merge. **Only when step 2 is empty.** If other PRs landed on `main` before the parent's squash, step 3 would silently drop them from the child. Instead: `git merge <squash>^` (main just before the squash, a real merge), then `git merge -s ours <squash>`, and confirm the child's changed lines against `<squash>` equal its own commits' (`git diff <squash> HEAD` vs `git diff <parent-tip> <child-tip>`). Used for #483 after #479/#482 landed ahead of #481. Only a stack's *first* PR needs a real `git merge origin/main`, where sibling stacks' append-at-end-of-file docs edits conflict — keep both sides. Used for #301–#312 (three stacks, ten PRs).

## A "merge main" commit whose tree came from a rebase reverts what landed in between

A branch merged `main` at X but committed the tree of a rebase onto an older `main` W. Git now takes X as merged, so every `main` commit between W and X is silently reverted by the PR's diff, and a later merge of `main` keeps the revert wherever `main` hasn't touched those lines since. #1631's "Merge main … the tree is the rebased, tested one" undid #1643's treaty audit in six files; it was caught at merge time on 2026-11-13. Before merging a PR whose branch has merge commits, list the files its diff changes that none of its own commits did: `git log --no-merges --format= --name-only origin/main..<branch> | sort -u > own`, then `git diff --name-only $(git merge-base origin/main <branch>) <branch> | grep -vxF -f own`. Any file it prints is a revert unless it was added in the merge commit itself. In a file the branch does own, look for `main`'s lines it dropped too (#1643's row in `python_tools.md`). To refresh such a branch, take `main`'s side for the reverted files and restore the dropped lines by hand.

## Play-testing unmerged work

Build one integration branch from the stack tips, check it out in the **full** main checkout (`scripts/deploy.sh` rsyncs with `--delete` and includes `gfx/`, so deploying from a sparse worktree would delete the textures), `POST /reload`, then `./scripts/deploy.sh --apply`. Before `--apply`, confirm the branch contains `origin/main` (`git merge-base --is-ancestor origin/main <branch>`; merge it in if not) and read the dry run on its own: a `deleting` line means the deploy would roll back newer `main` content or someone else's deployed branch (2026-09-28: a stale PR branch deleted #570's art from the game folder). Make sure the launcher playset does not also enable a Steam Workshop copy of this mod: a later-loaded copy overrides same-path files and produces a half-old, half-new game.

**A branch another worktree holds** can't be checked out in the main checkout (`fatal: '<branch>' is already used by worktree at …`); `git checkout --detach origin/<branch>` checks out its commit. Guard the deploy on that commit, not on a pipeline: in `git checkout <branch> 2>&1 | tail -2 && ./scripts/deploy.sh` the status is `tail`'s, so after the checkout failed the dry run went ahead on the commit already there (2026-11-16). `test "$(git rev-parse --short=9 HEAD)" = "<commit>" && ./scripts/deploy.sh` stops it. **A dry run after a round trip lists files the game folder already has.** The deploy compares sizes and times, and a checkout rewrites every file that differs between the commits it passes through. Going back to `main` from a test build through an older local `main` (`bdc33ca56`, then `81b947368`, then a pull to `abc24343b`) gave a dry run of 107 files, of which one, #1872's, differed from the deployed build: read such a list against `git diff --stat <deployed commit> HEAD`. Vic3's console has **no `effect` command** (that is CK3) — run test script with `event <id>` (see `events/te_debug_un_events.txt`).

## Orchestrated multi-branch waves

Lessons from the second journal-entry-widget wave (#316–#322):
- **Brief each sub-agent to write its PR body to a file before returning, and to sign commits with a truthful `Co-Authored-By` (its own model).** Two API outages killed agents mid-run; anything not yet on disk was lost.
- **Treat premises pre-seeded in a brief as hypotheses.** A design step before implementation overturned the brief's premise in 3 of 6 systems.
- **Check the plan itself against Top gotchas and `scripting_best_practices.md` before dispatching it.** Implementers transcribe plan code verbatim. #500's plan applied state- and building-scoped `multiplier = var:` modifiers from a country pulse (the multiplier resolves against ROOT) and used `debug_log` accessors the docs mark as failing; both were caught only in review.
- **Check the UTF-8 BOM on every changed `.txt`, not just the `.gui`.** `bom_normalizer` repairs it on the next `/reload`, but the fix then lands as unexplained regeneration churn. Check there is exactly **one**, too. A script that decodes with `utf-8` (not `utf-8-sig`) and writes a BOM back doubles it. The engine strips one BOM and reads the other as part of the first token, so the file's first comment stops being a comment, every key after it shifts, and the whole file is dropped (`Duplicated key = will not be created`). That lost all 323 company buildings on 2026-10-03. `test_bom_normalizer` now fails CI on a doubled BOM, and `bom_normalizer` collapses one.
- **Merging sibling PRs that append to the same files** (`te_events_l_english.yml` `TE_DEBUG_*` sections, the tail of `scripting_best_practices.md`): dry-run the whole sequence in a scratch clone with `git config rerere.enabled true`, then squash-merge one PR at a time, refreshing each next branch with `git merge origin/main` (rerere replays the recorded resolutions), and confirm the final `main` tree equals the dry run. Re-read numbered lists git merged without conflict — the `gui_modding_guide.md` gotchas came out #23-before-#22. Resolving a both-added conflict by concatenating the two sides can unclose a block: git keeps the closing braces both sides share outside the conflict, so they close only the second block (2026-10-31, `space_race_events.110` lost its `}` and swallowed `.111`, and no audit noticed; the tests' parser did). Check `git diff <each parent> -- <file>` shows no deletions you didn't mean, and run the tests.
- **When you refresh a PR branch with `git merge origin/main`, "ours" is the branch and "theirs" is main**, the reverse of building an integration branch. A scripted conflict resolver written for one direction silently keeps stale rows in the other: the #573–#583 wave's table resolver put back a branch's old Banking rows in `gui_modding_guide.md`. Resolve each row against `git merge-base HEAD MERGE_HEAD` (keep the side that changed it). Before pushing, check that every line either side added since that base is in `HEAD`. rerere records such a mistake and replays it on the next identical conflict: `git rerere forget <path>` it, or clear `.git/rr-cache`.

Lessons from the Workshop-feedback wave of 2026-11-14 (#1794–#1816, nine implementers at once on the owner's machine):
- **Nothing large on the WSL disk, scratch outside `/tmp`, and a pushed commit as soon as a piece stands.** WSL crashed mid-wave (the owner's reading: C: filled; two briefs sent agents to read saves without saying where copies go). `/tmp` was wiped with the shared brief, every PR body draft and the agents' notes; six worktrees held only uncommitted edits, which survived on disk by luck. Brief agents to keep save copies, extracts and any file over about 20 MB on D:, to keep notes in a durable folder, and to commit work in progress and push after the first piece.
- **Cap preflight; don't serialize everything.** `scripts/preflight.py` runs `pytest -n auto` (32 workers on that machine) and `--changed` reaches the whole suite for any content diff, about ten minutes. One machine-wide lock on every heavy command made agents queue one-file test runs behind it. What worked: a three-slot wrapper for preflight alone that capped its workers at 10, everything lighter run directly. `preflight.py --jobs N` now caps both the pytest workers and the audits run at once (#1803): when agents share a machine, brief each to pass about the core count divided by the number of runs allowed at once.
- **Every PR that rebuilds the guide PDF conflicts with `main` after each merge, and a conflicting PR gets no CI run at all.** Merge the PRs with no guide change first. Then one at a time: `git merge origin/main`, rebuild the PDF from the merged chapters, the revert check above, the system's tests and `preflight.py --quick`, push, merge. A branch that has never run CI because it conflicted needs its first run after the refresh.
- **A pipe hides a CI watcher's exit status.** `gh run watch <id> --exit-status` exits 1 on a cancelled or failed run, but `gh run watch … --exit-status | tail` exits 0 whatever the run did (the status is `tail`'s, without `pipefail`). On 2026-11-14 a run on `main` was cancelled with no newer push, the piped watcher read as a pass, and `main` was called green until the result itself was checked; the run had to be re-run. Don't pipe the watcher, and read the jobs' conclusions (`gh run view <id> --json conclusion,jobs`) before calling `main` green.
- **A sub-agent's game launch is refused by the permission system.** The coordinator runs `game_qa` itself, with the owner's go-ahead in `--permission`, from the sub-agent's runbook and variant mod. Where the harness can't click the game's own UI (opening a journal page), ask the owner to look by hand before building a probe widget: a one-shot timer probe never opened the page, and the owner's look took minutes.

Lessons from the Workshop-comments wave of 2026-11-15 (#1820–#1841, eight implementers and four reviewers over a day):
- **A wait for CI needs a short timeout for the run to start.** A PR that conflicts with `main` gets no run, and every PR that rebuilds the guide PDF conflicts as soon as another one merges. One implementer finished, pushed and then watched for a run on #1828 for three hours; its "waiting on background work" notices read as progress to the coordinator until the owner asked. Brief agents to give a run about five minutes to start, then read `gh pr view <n> --json mergeable,mergeStateStatus` and hand back if the PR conflicts. For the coordinator, a second waiting notice with no report means looking at the branch: its last commit time, and whose `preflight.py` is running (`pgrep -af preflight`, each process's `/proc/<pid>/cwd`).
- **A PDF-only refresh needs no second CI run** (owner): when CI passed on the branch's last substantive commit and the only conflict with `main` is the guide PDF, rebuild the PDF, run the revert check above and merge. That does not cover commits pushed while the PR was conflicting, which have never run CI at all.
- **Review what decides for the AI or guards against a loop, and little else.** The three break-it reviews of the day each found a flaw the author's tests passed: a rule switch that opened a second world war (#1823), a self-check whose verdict could be wrong in the era it read (#1830), and a hold that kept every policy for good once four were in force (#1841). The content and tooling PRs merged on the coordinator's read and green CI.
- **A sub-agent cannot save its report as a file**, so its final message is the only copy. Pull it out of the task's transcript into the wave's durable scratch folder as each one arrives; a later context summary keeps the gist and loses the figures.
- **Check a report's side claims and your own readings before passing them on.** A report's "leftover file the repo deleted" was a tracked file; the coordinator called an audit's range wrong from the table's literal without reading that the row follows a define, and proposed a cause for civil wars that the next measurement put at zero of 43. A claim costs one command to check and a retraction to the owner if it is not.
- **A mechanic's size is read from how it is applied, not from its static modifier.** `in_default`'s `+1` movement activism is the full-strength value: the engine ramps the whole modifier from 10% on the first day to 100% after a year (`IN_DEFAULT_MINIMUM_PENALTY_SCALE`, `IN_DEFAULT_DAYS_TO_FULL_PENALTY`; read in game 2026-11-15, +23% at 55 days). A save lists a modifier's name, and its multiplier under a separate key (`0x0cf7`).

## `gh pr edit --body-file` can fail silently here: verify or use the REST API

On this repo `gh pr edit <n> --body-file <file>` currently exits non-zero with only a GraphQL *Projects (classic) is being deprecated* notice and **leaves the body unchanged**; nothing else is printed, so a chained `&& echo ok` is the only tell. Verify with `gh pr view <n> --json body -q .body | grep -c <marker>`, or patch directly: `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -F body=@<file>`. `gh pr create --body-file` and `gh issue comment --body-file` are unaffected.

## A multi-issue PR needs one `Closes` keyword per issue

`Closes #161, #167, #168` auto-closes **only #161** — GitHub binds the closing keyword to the first number; the rest are mere references and stay open after merge. Write `Closes #161. Closes #167. Closes #168.` (or `closes #161, closes #167, …`). Bit us on #174, which silently left #167-172 open (recovered by manual close + a follow-up PR). Verify post-merge with `gh issue list` rather than trusting the PR body.

**The keyword also fires where it was not meant.** GitHub reads `fixed: #N`, `fixes #N`, `closes: #N` and their kin anywhere in a PR body or a squash commit's message, whatever comes before them. #1623's commit message said "Script bugs found and not fixed: #1612 to #1621", and merging it closed #1612 (reopened by hand, 2026-11-12). When a message lists issues it does not close, keep `fix`, `close` and `resolve` words away from the number: "reported in #1612 to #1621".
