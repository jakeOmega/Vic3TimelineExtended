# Legislated tax code: canonical state and the collection writer

The variable schema of the legislated tax code (spec: `docs/superpowers/specs/2026-09-29-legislated-tax-code-design.md`; plan: `docs/superpowers/plans/2026-10-02-legislated-tax-code-tasks.md`), the one effect that turns it into native tax settings, the scheduler that changes it on its dates, the migration that creates it from a country's vanilla tax law, and the display values that read it. Later tasks extend the schema tables and the sections below; `test_tax_code_state.py` parses the tables and checks them against the initialiser.

Everything here runs only under `te_tax_code_rule` (`te_tax_code_on = yes`). With the rule off no variable is written and no native setting is touched.

## Conventions

- **Country variables, fixed names.** The enacted code is plain numeric country variables, one per schema row. No containers, and three lists of states: the ones the enacted regional relief names (`te_tax_en_relief_states`, [Relief eligibility](#relief-eligibility)) and each package slot's (`te_tax_p<s>_relief_states`). A civil war's winner keeps no loser's list, which is why each side holds its own copies from the outbreak and the winner's own lists are the ones that apply.
- **Tokens are never removed.** "Empty" is the row's sentinel, written with `set_variable`. A winner inherits every loser variable it does not itself hold, so a removed token would come back holding the loser's value (CLAUDE.md "Top gotchas"). No file of the tax code may `remove_variable` a schema token; `test_tax_code_state.py` scans for it.
- **Indices, not rates.** Each instrument is an integer index; rate = index × `te_tax_step_<key>` (`scripts/generators/gen_tax_code.py`, `INSTRUMENTS`). Index 0 means not collected. Unset or unchanged fields of a draft, bill or package are `-1`.
- **Months are absolute.** A month is a `te_history_month_index` value (`year × 12 + month`, January = 0; `common/script_values/te_history_values.txt`). No `_y`/`_mo` variables are stored: the display values split a month into a year and a 1-based month with `floor`, which a script value can do and a GUI cannot.

## Initialisation

`te_tax_init_country` (country scope, `common/scripted_effects/te_tax_state_effects.txt`) writes every country row above that is absent, with its sentinel, and never touches one that exists (a list row is not a token: a missing list is an empty one). The per-instrument, per-good and scheduler rows come from the generated `te_tax_gen_init_instruments`, `te_tax_gen_init_goods` and `te_tax_gen_init_schedule` (`common/scripted_effects/te_tax_generated_effects.txt`). `te_tax_schema = 1` is written last, so a country holding `te_tax_schema` holds every token of that schema version. Each write has the shape `if = { limit = { NOT = { has_variable = X } } set_variable = { name = X value = <sentinel> } }`, which `je_immediate_reset_audit` accepts if a journal entry's `immediate` ever calls it. The state variables `te_tax_relief_state` and `te_tax_relief_holder` are not initialised: a state without them is named in no relief. Nor are the relief lists: a missing list is an empty one, and every list operation tests `has_variable_list` first.

Callers: the [migration](#migration) before it maps the vanilla law, and the writer below, which re-runs it each time so a later schema version's new rows are backfilled on old saves. A later schema bumps the version in a guarded `else_if` after the new rows, never by overwriting the old value unconditionally.

`te_tax_copy_token = { NAME = <token> }` copies one token from `scope:te_tax_source` to THIS when the source holds it, for the copies a new country receives ([Civil wars and new countries](#civil-wars-and-new-countries)).

## The collection writer

`te_tax_sync_collection` (`common/scripted_effects/te_tax_collection_effects.txt`) is the **only** effect that changes a rule-on country's native fiscal state. Nothing else in `common/` or `events/` (apart from the temporary probe harness, `te_debug_tax*`) calls `add_amendment` with a tax-code amendment, `add_taxed_goods`, `remove_taxed_goods`, `set_tax_level`, `set_import_tariff_level` or `set_export_tariff_level`, or adds a `te_tax_relief_*` modifier; `test_tax_code_state.py` checks this.

- **Scope.** Country, with ROOT = THIS = the country. Call it from a country event or a country hook (the dispatched monthly event `te_tax.1`, the watchdog `te_tax.2`, the post-migration `te_tax.4`), never from the global `on_monthly_pulse`, which has no ROOT. Nothing in it reads ROOT.
- **Gate.** `te_tax_code_on = yes`, `has_law = law_type:law_te_tax_code` and `has_variable = te_tax_schema`. A country still on a vanilla law is left alone. One holding the carrier without initialised tokens (a rebel before the outbreak copy) is left alone too, rather than synced to an empty code, and logged (`TE_TAX sync skipped: <country> ...` in `debug.log`).
- **At most one sync a day** (final review A-I1). Two events the engine runs in one daily tick are separate executions, and whether the first one's `add_amendment` is visible to the second is unverified; if it is not, the second would add the enacted rate amendment again, and the removal loop never removes (nor the drift check sees) a duplicate of the enacted type. Three callers can share a day: the watchdog and the processor on the 1st, a `te_tax.4` raised the day before landing on the 1st, and several `te_tax.4` from one law cascade. So inside the gate, a call when `te_tax_synced_today` holds (`te_tax_sync_day` ≥ `te_tax_today`, the date in days) writes nothing and runs `te_tax_defer_sync`: it raises `te_tax.4` for the next day unless a deferral raised today is pending (`te_tax_sync_defer_day`), and logs `TE_TAX sync_deferred`. Every sync stamps `te_tax_sync_day = te_tax_today` after its last write. A package's collections then change on the 2nd, not the 1st, when another sync ran first on the 1st. The two day variables are a guard, not schema tokens: read through `has_variable`, never initialised or copied at an outbreak.
- **Order.** `te_tax_init_country` (backfill); `save_scope_as = te_tax_country`; `te_tax_detect_drift` (counters only, [Native controls and drift](#native-controls-and-drift)); `te_tax_sync_customs` (the customs option and a market owner only, [Customs schedule](#customs-schedule): before the amendment block, so a level it adopts moves `te_tax_code_version` before the sync mark records it); `te_tax_pick_sponsor` (`scope:te_tax_sponsor`: a random interest group in government if `any_interest_group = { is_in_government = yes }`, else the one with the most clout; it branches on THIS country's groups, never on whether the scope already exists, so a sponsor saved for another country in the same execution cannot leak in); the five `te_tax_gen_sync_<key>`, only when the country has an interest group at all (otherwise one `debug_log` and the amendments stay as they were), then `te_tax_sync_version` = `te_tax_code_version`; `te_tax_gen_sync_goods`; `te_tax_sync_relief`; the tax level pinned to `medium` if it is anything else; `te_tax_sync_day` stamped.
- **Call at most once per effect execution; a second call in a later execution changes nothing.** Amendment, goods and modifier changes are not visible later in the same execution, so a second call there would act on the stale state and could add an amendment twice. Across executions it is idempotent, diff not churn: each part removes only what the code does not hold and adds only what the code holds and is missing. Within the one call no part re-reads what it has just written, and the removal loop never touches the amendment the add step checks.
- **Per-instrument sync** (generated): from `active_law:lawgroup_taxation`, `every_scope_amendment` removes each amendment for which `te_tax_amendment_is_<key>` holds and `te_tax_amendment_matches_<key>` does not; then one `if`/`else_if` branch per index adds `amendment_te_tax_<key>_<idx>` when `var:te_tax_en_<key> = idx` and the law lacks it (`has_amendment`), with `sponsor = scope:te_tax_sponsor cooldown = 0`.
- **Goods sync** (generated): per catalog good, `add_taxed_goods` when `te_tax_en_g_<good> = 1` and the good is not taxed, `remove_taxed_goods` when the flag is not 1 and it is; per good outside the catalog, `remove_taxed_goods` when it is taxed. So the native taxed set equals the enacted set for every good, vanilla and mod.
- **Relief sync**: first `te_tax_rebuild_relief_marks` derives the state marks from the enacted list ([Relief eligibility](#relief-eligibility)); then `te_tax_relief_ag_<n>` on the country for `te_tax_en_agrel = n`; on every owned state with `te_tax_relief_state = 1`, `te_tax_relief_region_<n>` for `te_tax_en_regrel = n`; the other band, or both, removed where present. Each `add_modifier` is guarded by `NOT = { has_modifier }`, each `remove_modifier` by `has_modifier`. Variables are visible at once, so the modifiers read the rebuilt marks.
- **Not touched**: tariffs and subventions under the plain rule option, and a customs-union member's under either (only the market owner's code holds customs, [Customs schedule](#customs-schedule)), Millet System / People of the Book heathen tax and `amendment_redemption_payments` (external, held at the pinned medium level), consumption-tax Authority costs.

### Engine forms

The amendment forms are the ones the tax probe used in game (`common/scripted_effects/te_debug_tax_effects.txt:20-44`; add, remove and rebuild worked in R3, `docs/testing/tax-code-probe-results-2026-10-02.md`) and are documented in the 1.14.5 engine logs: `has_amendment = amendment_type:X` (law scope), `type = amendment_type:X` in amendment scope (the `type` link, `event_targets.log`), `every_scope_amendment` from law scope, `remove_amendment = yes`, `add_amendment = { type sponsor cooldown }`. The plan's `is_amendment_type` is not an engine trigger and is not used; nor is `any_scope_amendment` (documented, but not probe-tested). R3 removed probe amendments that had no `can_repeal`. The production amendments carry `can_repeal = { always = no }`; a script `remove_amendment` is expected to ignore it, as it ignores the cooldown, but that is not verified in game. Relief and goods use `has_modifier`, `add_modifier = { name }`, `remove_modifier`, `has_consumption_tax`, `add_taxed_goods`, `remove_taxed_goods`; the level uses `tax_level` and `set_tax_level`.

## Consumption goods catalog

The goods a code can put on its taxed-goods list, derived by `gen_tax_code.py` (`consumption_catalog()`): every good a pop need buys (vanilla `vanilla_parsed/common/pop_needs.json` and the mod's `common/pop_needs/*.txt`, with `REPLACE:`/`INJECT:` applied). A good without a `consumption_tax_cost` costs the engine default (`DEFAULT_GOODS_TAX_COST = 100`, 1.14.5 `common/defines/00_defines.txt`) and is still taxable: vanilla history taxes liquor, tobacco, opium and wine, none of which sets one, and the local goods services, transportation and electricity are taxable. One `te_tax_en_g_<good>` token, one sync branch and one display value per catalog good. Every other good (`stray_goods()`, from vanilla `goods.json` plus the mod's `common/goods/*.txt`) gets only a removal branch in the goods sync. A change to the pop needs or goods files changes the catalog on the next `gen_tax_code.py` run, and `gen_tax_code.py --check` fails until it is run.

**Catalog (39 goods):** `aeroplanes`, `automobiles`, `clippers`, `clothes`, `coal`, `coffee`, `consumer_appliances`, `digital_access`, `digital_assets`, `electricity`, `fabric`, `fine_art`, `fish`, `fruit`, `furniture`, `glass`, `grain`, `groceries`, `liquor`, `luxury_clothes`, `luxury_furniture`, `meat`, `oil`, `opium`, `paper`, `porcelain`, `radios`, `services`, `silk`, `small_arms`, `steamers`, `sugar`, `tea`, `telephones`, `tobacco`, `tourism`, `transportation`, `wine`, `wood`.

**Outside the catalog (26 goods, removed by the sync if natively taxed):** `advanced_materials`, `ammunition`, `artillery`, `construction`, `dye`, `electronic_components`, `engines`, `explosives`, `fertilizer`, `gold`, `hardwood`, `iron`, `ironclads`, `launch_capacity`, `lead`, `magnetic_drive_ships`, `manowars`, `merchant_marine`, `motor_ships`, `robotics`, `rubber`, `steel`, `sulfur`, `tanks`, `tech_metals`, `tools`.

No pop need buys a good outside the catalog (`construction`, consumption-tax cost 400, is bought only by buildings), so a code never taxes one.

## Display values

Guarded reads for the GUI and loc. Each `te_tax_view_*` tests every variable it reads with `has_variable` and returns the row's sentinel when it is absent: 0 for an index, a rate, a flag or a counter; -1 for a month or a successor index. None writes a variable or iterates anything, so a panel can read them freely.

- `common/script_values/te_tax_display_values.txt`: `te_tax_view_schema`, `te_tax_view_migrated`, `te_tax_view_code_version`, `te_tax_view_last_month`, `te_tax_view_next_month`, `te_tax_view_agrel` and `te_tax_view_agrel_pct`, `te_tax_view_regrel` and `te_tax_view_regrel_pct` (band × `te_tax_relief_pct_step` = 25), and `te_tax_view_relief_state` (state scope).
- `common/script_values/te_tax_generated_values.txt` (generated), per instrument: `te_tax_view_en_<key>` (index), `_rate` (index × step), `_pct` (index × percentage-point step; wage, dividend and consumption only), `_since`, `_since_y`, `_since_mo`, `_exp`, `_exp_y`, `_exp_mo`, `_succ`, `_succ_rate`, `_succ_pct` (percent instruments). Per catalog good: `te_tax_view_en_g_<good>`. And `te_tax_view_goods_count`, the number of catalog goods the code taxes.
- For the [panels](#panels), in the same two files. Hand-written: `te_tax_view_next_month_y`/`_mo`; `te_tax_view_bl_rev`; `te_tax_view_debate_days_left` (a guarded wrapper over `te_tax_debate_days_left`). Generated: `te_tax_view_<r>_on` and `te_tax_view_<r>_due`, `_due_y`, `_due_mo` for the draft and the bill (`<r>` = `dr`, `bl`); `te_tax_view_p<s>_on`, `_state`, `_due`, `_due_y`, `_due_mo` per package slot; `te_tax_view_last_change` and its `_y`, `_mo` (the newest history entry of a kind that changed the code, 1, 2, 5 or 7, or an instrument's `_since` if later, kept with `min =`); and the history ring newest first, `te_tax_view_hist_<i>_kind`, `_inst`, `_month`, `_month_y`, `_month_mo` for position `<i>` 1 to 8, which reads entry `n = te_tax_h_head − i + 1` (wrapping past 1 to 8). A view of a record's payload (`_due`, `_state`, `_rev`) also requires the record's own token to be 1: a closed record's payload is removed, and a civil war's winner may hold a loser's.
- For the workbench, review and passage panels (plan Task 8). ## Scheduler, package slots and history

An approved package waits in slot `a` or `b` and takes effect on the 1st of its due month; an enacted value with a sunset reverts to its successor. All transitions run in `te_tax_process_month` (`common/scripted_effects/te_tax_schedule_effects.txt`), once per country per calendar month.

### Dispatch

- **Global `on_monthly_pulse`, the 1st of every month** (`common/on_actions/te_tax_on_actions.txt`, `te_tax_monthly_dispatch`). If `te_tax_code_on = yes`, it raises the hidden country event `te_tax.1` (`events/te_tax_internal_events.txt`) on every country with `te_tax_migrated > 0`; `te_tax.1` runs `te_tax_process_month` with ROOT = that country. The country pulse is not used for this: `on_monthly_pulse_country` is a 30-day timer that can skip a calendar month (`docs/guides/scripting_best_practices.md`, "`on_monthly_pulse_country` Is a 30-Day Timer, Not a Calendar Month"), which is how the tax probe commenced and expired a package in one call. A second fan-out in the same dispatch raises the migration `te_tax.3` on every country without `te_tax_migrated ≥ 1` ([Migration](#migration), self-heal); such a country's first `te_tax.1` runs the month after.
- **Watchdog: `on_monthly_pulse_country`** (`te_tax_watchdog_on_action`). When `te_tax_last_month` < the month index and 0 ≤ `te_tax_next_month` ≤ the month index, it raises `te_tax.2`, which runs `te_tax_watchdog_month`: it logs `TE_TAX watchdog`, runs the sunsets, holds as missed any awaiting package whose due month has passed, and syncs collection only if a sunset ran (`te_tax_code_version` moved, compared through a local variable), so on the 1st it does not sync a second time in the tick the processor syncs; when it syncs it also takes the economy snapshot ([Economy snapshot and estimates](#economy-snapshot-and-estimates)). It **never commences** and **never claims the month** (`te_tax_last_month`): a country's pulse can land on the 1st before the global pulse, and claiming the month there would make that day's dispatch skip the month's commencements. Sunsets are safe to run twice in one month, because an executed sunset clears its own `_exp`. A due commencement the watchdog sees becomes held_missed only once its month has passed, by the next processor or watchdog run.

### Processor rules

1. `set_variable = { name = te_tax_now value = te_history_month_index }` once; if `te_tax_last_month >= te_tax_now` stop (a second call in a month does nothing); else `te_tax_last_month = te_tax_now`, before any transition.
   1a. The [fiscal record](#the-fiscal-record) of the 1st (`te_tax_record_fiscal_month`), then, under the customs option, the customs authority (`te_tax_customs_revalidate`, [Customs schedule](#customs-schedule)), both before any transition.
2. **Sunsets first** (`te_tax_gen_sunset_<key>`). For each instrument with `te_tax_en_<key>_exp` ≠ -1 and ≤ now: if `te_tax_en_<key>_since < te_tax_now` (`_since < now`), set `te_tax_en_<key> = _succ`, `_since = now`, `_exp = -1`, `_succ = -1`, `te_tax_code_version` +1, history kind 2 with the instrument in `_inst`; otherwise leave it (it runs next month). Late sunsets catch up. A sunset whose `_succ` is -1 is corrupt: its `_exp` is reset to -1 with no version change, so it cannot hold `te_tax_next_month` in the past.
3. **Commencements** in `seq` order, lower first, slot `a` on a tie (`te_tax_gen_commence_<s>`). For a slot with `_on = 1` and `_state = 1`: if `_due = now` (equality, never `>=`): if every touched provision's `te_tax_p<s>_xver_<key>` equals the current `te_tax_xver_<key>`, and likewise `_xver_goods` when the package touches a good and `_xver_relief` when it touches relief (`te_tax_gen_package_current_<s>`), apply every touched field (`te_tax_gen_apply_<s>`: the successor below, then `te_tax_en_<key> = new`, `_since = now`, `_exp` from the package; goods; relief depths; when `_regrel_states_set = 1`, the enacted list `te_tax_en_relief_states` replaced by the states in the slot's own list `te_tax_p<s>_relief_states` that the code keeps (`te_tax_relief_listed_state_kept`: its own, or its civil-war counterpart's), whose state marks the step-4 sync then derives; the slot list is consumed), `te_tax_code_version` +1, history kind 1, `_on = 0`, `_state = 0`; else `_state = 2` (held_conflict), history kind 3, the whole package held and collections unchanged. If `_due < now`: `_state = 3` (held_missed), history kind 4; a package is never applied late. A held package keeps its slot until the player resolves it ([Held packages](#held-packages)): a missed one may be rescheduled to next month if the delay is at most three months and no later bill touched what it changes; either kind may be released. A held_conflict package can only be released: renewed approval means a new bill. **Supersession and successors happen at commencement, never at approval.** Approval (Task 6) leaves the enacted provision and its sunset alone; it only drops the provision from an earlier-approved slot whose due month is on or after the new one. When a package commences, it replaces each provision it touches, value and sunset together, captured before anything is overwritten:
   - **No sunset in the package** (`te_tax_p<s>_<key>_exp = -1`): the change is permanent; `te_tax_en_<key>_exp` and `_succ` become -1, clearing any pending sunset.
   - **A sunset in the package**: the provision reverts to the underlying permanent rate. If the provision still has a pending sunset with a successor (`te_tax_en_<key>_exp ≥ 0`; one due this month has already run, so it is a later one), that successor is kept; otherwise the rate in force (`te_tax_en_<key>`, after this month's sunsets) becomes the successor.
   - The package's stored `_succ` is never read, so a successor is always a rate that was law; and a held or missed package leaves the enacted sunset as it was.
   - The spec's examples, with 30% dividends due to revert to 15% on January 1: a bill setting 25% from February 1 gives 30% → 15% in January → 25% in February (the January sunset runs; the bill then commences with no sunset). A bill setting a permanent 25% from December 1 replaces the January expiry (commencement clears it). A bill extending 30% for 24 months from December 1 keeps the pending successor, so the rate reverts to 15% after 24 months; had it been held, 30% would still revert to 15% on January 1. Commencement does not check the carrier law: the canonical code changes either way, and `te_tax_sync_collection` writes collection only while the country holds `law_te_tax_code`.
4. **Policy obligations** (`te_tax_obl_check_month`, [Policy obligations](#policy-obligations)): every binding obligation is checked once, after the commencements above have started theirs and before the sync. The processor is its only caller.
5. `te_tax_sync_collection` once, every processed month, whether or not anything changed: it applies the month's transitions and re-asserts the code over any native change since the last month, which `te_tax_detect_drift` counts first when the month changed nothing in the code ([Native controls and drift](#native-controls-and-drift)).
6. `te_tax_take_snapshot` once: the economy snapshot the estimates are dated by, of the code just written ([Economy snapshot and estimates](#economy-snapshot-and-estimates)).
7. `te_tax_recompute_next_month`: `te_tax_next_month` = the earliest enacted `_exp` ≥ 0 and awaiting slot `_due`, or -1.
8. With a bill under debate, `te_tax_refresh_support` (the monthly support refresh).

**Operative interval.** The store refuses a package whose sunset would fall before `_exp ≥ _due + 1`. A package's provisions start with `_since = now`, and rule 2 needs `_since < now`, so a package's own sunset can never run in its commencement call; every package is in force for at least one calendar month. The only same-call pair is the sunset of one enacted value followed by the commencement of a different package, in that order.

**Debug lines.** Each processor branch writes one `debug_log` line, `TE_TAX <branch> … month=<index> date=<game date> country=<name>`, with `<branch>` one of `dispatch` (global, date only), `process`, `skip`, `sunset`, `sunset_deferred`, `sunset_dropped`, `commenced`, `held_conflict`, `held_missed`, `watchdog`, `stored`, `store_refused`, `snapshot`, and the collection writer's `sync_deferred` (a second sync in one day, [The collection writer](#the-collection-writer)). `process`, `skip` and `snapshot` are written for player countries only (every migrated country runs the processor monthly); every transition line is written for every country. The month comes from `[SCOPE.ScriptValue('te_history_month_index')|0]`, which printed `month=22032` from the tax probe's country event, and the date from `[TimeKeeper.GetCurrentDate.GetString]`, which vanilla 1.14.5's election lines print (for example "January 8, 2069").

### Storing a package

`te_tax_store_package = { SLOT = a|b }` (Task 6's pass calls it, after dropping the bill's provisions from an earlier-approved slot due on or after it; the enacted provision is superseded at commencement, not here) writes a package from the bill record if `te_tax_can_store_package = { SLOT }` (`common/scripted_triggers/te_tax_triggers.txt`) holds: the rule is on; the country has `te_tax_schema`; `te_tax_p<s>_on = 0`; `te_tax_bl_due` exists and is after the current month; and `te_tax_gen_bill_sunsets_valid`: every touched provision's offset `te_tax_bl_<key>_sun` is 0 (no sunset) or ≥ 1, which is `_exp ≥ _due + 1` for `_exp = _due + _sun`. Otherwise it logs `TE_TAX store_refused` and writes nothing.

- **Bill fields read** (Task 6 writes them; none is a schema token): `te_tax_bl_due`; `te_tax_bl_<key>`, `te_tax_bl_<key>_sun` (0, 6, 12, 24, 36 or 60), `te_tax_bl_xver_<key>`; `te_tax_bl_g_<good>`, `te_tax_bl_xver_goods`; `te_tax_bl_agrel`, `te_tax_bl_regrel`, `te_tax_bl_xver_relief`; the country state list `te_tax_bl_relief_states` (copied from the draft's, Task 11), read only if present.
- **Written** (`te_tax_gen_store_<s>`): every payload field, including `_due0` (the approved month) and `_pver_<group>` (the planned versions after this approval), which only the held-package reschedule reads. `_seq` = one above both slots' `_seq`. `_<key>_exp = due + sun` and `_<key>_succ` only for a touched provision with `sun ≥ 1`, else both -1. `_<key>_succ` is a **display preview** for the review (Task 8's "reverts to X"), not law: commencement decides the successor then (rule 3). The preview applies rule 3 at store time: the enacted provision's pending successor if it has a sunset (one before the due month will have run, a later one is still pending; either way the successor is the underlying rate), else its value; overridden the same way by the other slot's package when that slot is awaiting with an earlier due month and touches the provision. A held other slot is ignored. If an earlier package is later held, the preview can be stale, but the successor that takes effect cannot.
- **Regional-relief states**: the slot's list `te_tax_p<s>_relief_states` is emptied; if `te_tax_bl_regrel ≥ 0` the package restates the state set (`_regrel_states_set = 1`) and the bill's states (`te_tax_bl_relief_states`) are copied into it; commencement replaces the enacted list `te_tax_en_relief_states` with the ones the code keeps. The slot list is a country list, not marks on the states: a civil war's winner keeps none of the loser's lists, so a loser's wartime package can never commence under the winner, and a pre-war package names its whole set on both sides. Each state the enacted list names is stamped with the country (`te_tax_relief_holder`) when the sync derives its mark, so a change of owner can reset the mark of a state whose new owner's code did not name it ([Relief eligibility](#relief-eligibility)).
- `_state = 1` and `_on = 1` are written last, then `te_tax_recompute_next_month`. The store does not touch the enacted code or collection and does not record history: the pass records kind 6 (approved), and kind 8 (superseded) for the slot it supersedes.

### History

`te_tax_history_push = { KIND = <1..17> SLOT = a|b|none }` advances `te_tax_h_head` (1 to 8, then back to 1) and overwrites that entry with the month (`te_history_month_index`), the kind, the slot as `te_tax_slot_id_<SLOT>` and `te_tax_code_version`. Sunsets write through the generated `te_tax_gen_history_write = { KIND SLOT INST }` to record their instrument; every other caller uses the push, which records `_inst = 0`. The scheduler writes kinds 1 to 4; migration (Task 5) writes 5, the pass (Task 6) 6 and 8, the civil-war repair (Task 10) 7, the held-package commands (Task 6) 9 (rescheduled) and 10 (released), the policy obligations (Task 12) 11 (fulfilled), 12 (breached), 13 (renegotiated) and 14 (released: the promises bound to a dropped or emptied package, or released by the civil-war repair, one entry per event), and the customs schedule (Task 15) 15 (a market level adopted into the code, one entry per sync however many goods), 16 (the market lost) and 17 (the market gained).

### Other entry points

`te_tax_recompute_next_month` refreshes the watchdog's cache. There is no public apply: commencement calls the generated `te_tax_gen_apply_<s>` directly, inside the processor, which has set `te_tax_now`.

### Scheduler retest (owner, in game)

The steps are in `docs/testing/tax-code-capability-ledger.md`, "Scheduler retest". Steps 2, 3, 5 and 6 need a stored package, which the pass (`te_tax_cmd_pass`, [Draft, bill and passage](#draft-bill-and-passage)) creates, from the Pass button of the Bill Under Debate panel ([Panels](#panels)). Step 4 is `event te_tax.1` twice from the console in one month: the second logs `TE_TAX skip`.

## Migration

Nothing in the tax code runs for a country until it is migrated: the monthly dispatch processes only countries with `te_tax_migrated > 0`. `te_tax_migrate_country` (`common/scripted_effects/te_tax_migration_effects.txt`) turns the active vanilla taxation law, the native tax level and the consumption-taxed goods into an enacted code with the same rates, and installs the carrier `law_te_tax_code`. It runs from the hidden country event `te_tax.3`, so ROOT is the country.

**Hooks** (`common/on_actions/te_tax_on_actions.txt`; every handler checks `te_tax_code_on = yes` first):

- **Game start**: `on_game_started_after_lobby` raises `te_tax.3` on `every_country`. Not `on_game_started`: that fires while the players are still in the lobby, where the rule can still change (`docs/guides/scripting_best_practices.md`, "Convert what history placed after the lobby"); a migration there followed by the rule turned off in the lobby would leave every country on the carrier in a rule-off campaign.
- **Formed country**: `on_country_formed`, whose scope is the new country, raises `te_tax.3` on it. A formation keeps the forming country's variables, so a migrated country is left alone.
- **Released country**: the four `on_country_released_as_*` hooks (`_independent`, `_own_subject`, `_overlord_subject`, `_company_subject`) run in the releasing country. `te_tax_on_country_released` saves it as `scope:te_tax_source` and runs `te_tax_init_released_country` in `scope:target`: a parent holding the carrier law passes on its enacted code ([Civil wars and new countries](#civil-wars-and-new-countries)); any other parent's released country gets `te_tax.3`. Whatever runs as a country event is dispatched to the new country, never run in the parent (`te_monetary_on_actions.txt`, "THE UPDATE IS DISPATCHED, NOT CALLED").
- **Uprising**: `on_revolution_start` and `on_secession_start` are not migration hooks. The shared `te_civil_war_on_start` copies the original's code to the rebels (`te_tax_on_uprising`); only an original without a code leaves them to `te_tax.3`.
- **Self-heal**: the monthly dispatch raises `te_tax.3` on any country without `te_tax_migrated ≥ 1`.

**Order inside `te_tax_migrate_country`.** Gate: the rule is on and `te_tax_migrated` is absent or below 1, so a second run changes nothing. Then: `te_tax_init_country`; `te_tax_migration_discrepancy = 0`; `te_tax_gen_migrate_rates` (generated: one branch per law and native level, 25 in all, each writing all five `te_tax_en_<key>`); `te_tax_gen_migrate_goods` (generated: per catalog good, `te_tax_en_g_<good>` = 1 if `has_consumption_tax`, else 0; `te_tax_xver_goods` +1); `te_tax_gen_migrate_provisions` (generated: per instrument, `_since` = the month for a nonzero index and -1 for a zero one, `_exp` and `_succ` -1, `te_tax_xver_<key>` +1); `activate_law = law_type:law_te_tax_code` unless the country already holds it; `te_tax_last_month = -1`; `te_tax_code_version` +1; history kind 5 (`te_tax_history_push = { KIND = 5 SLOT = none }`); one `TE_TAX migrated wage=… div=… land=… head=… cons=… goods=…` line in `debug.log`; `te_tax.4` raised for the next day; `te_tax_migrated = 1` last.

**Collection.** The migration never calls `te_tax_sync_collection`. Whether `activate_law` is visible later in the same execution is not verified in game (amendment and modifier changes are not), and if it is not, the writer would still see the vanilla law and attach the amendments to it. The hidden `te_tax.4`, raised by the migration with `days = 1`, runs the writer the next day, when the carrier is in place; without it the country would collect nothing until the 1st of the next month. `te_tax_last_month = -1` hands the country to the next global dispatch, whose `te_tax.1` syncs again (a later execution, so nothing changes). Migration never raises `te_tax.1` and never claims a month.

**Mapping** (`MIGRATION` in `scripts/generators/gen_tax_code.py`, checked against `vanilla_parsed/common/laws.json` by `test_tax_code_migration.py`; values from 1.14.5 `common/laws/01_taxation.txt`, by level very low / low / medium / high / very high; an instrument a law does not set is 0):

| Law | wage | div | land | head | cons |
|---|---|---|---|---|---|
| Consumption-Based | 0 | 0 | 0 | 0 | 0.15/0.20/0.25/0.30/0.35 |
| Land-Based | 0 | 0 | 0.40/0.55/0.70/0.85/1.00 | 0 | same ladder |
| Per-Capita | 0.05/0.075/0.10/0.125/0.15 | 0 | 0.20/0.275/0.35/0.425/0.50 | 0.40/0.55/0.70/0.85/1.00 | same ladder |
| Proportional | 0.10/0.15/0.20/0.25/0.30 | 0.025/0.05/0.10/0.15/0.20 | 0 | 0 | same ladder |
| Graduated | 0.10/0.125/0.15/0.175/0.20 | 0.10/0.15/0.20/0.25/0.30 | 0 | 0 | same ladder |

Every value is an exact index (rate ÷ step: wage, dividends and rural assessment step 0.025; head tax and consumption 0.05). The level is read with `tax_level = <level>`; the writer then pins it to medium.

**Discrepancies.** A country on any other taxation law (the probe carrier, another mod's law) migrates as all zeros, with `te_tax_migration_discrepancy = 1` and the line `TE_TAX migration_discrepancy no mapping for the active taxation law…`. A country that already holds `law_te_tax_code` without migration tokens (a rebel or released country that inherited the carrier from its parent) migrates the same way with its own line, `…holds law_te_tax_code without migration tokens…`, and the carrier is not activated again; the next sync then removes any amendments it arrived with. Uprisings and the released countries of a parent holding the carrier never reach this branch: they receive a copy instead.

## Civil wars and new countries

Spec §10: at a revolution's outbreak both sides receive the operative code and the approved future changes with their original dates; each side legislates on its own during the war; at reunification the winner's complete code applies, never a mixture of both. A civil war's winner inherits every loser variable it does not hold itself, but no modifier and no variable list (`docs/guides/scripting_best_practices.md`, "What a Civil War's Winner Inherits"), and the merge keeps the winner's own value wherever both hold one. So the code lives in plain country variables, and the rule reduces to: both sides hold every token from the outbreak on. Everything here is in `common/scripted_effects/te_tax_civil_war_effects.txt`, gated on `te_tax_code_on`; `test_tax_code_civil_war.py` pins it.

### Outbreak

- **Hook.** The shared `te_civil_war_on_start` (`common/on_actions/te_civil_war_on_actions.txt`; `on_revolution_start` and `on_secession_start`, THIS = the original, `scope:target` = the uprising) calls `te_tax_on_uprising` after `te_civil_war_record_start`, so the rebels already carry `te_cw_origin`. `te_tax_on_actions.txt` no longer hooks the uprising: same-name on_actions are unioned across files in no known order, and a second handler would race the copy with a migration.
- **Copy.** If the original's code is in force (`te_tax_code_in_force`), it is saved as `scope:te_tax_source` and `te_tax_copy_code` runs in the rebels: `te_tax_copy_token` for every country token of the [schema](#schema), through the generated `te_tax_gen_copy_code` (the per-instrument and version tokens, the taxed goods, the clock, the package-slot headers and the history ring) and, for each occupied slot (`te_tax_p<s>_on = 1` on the original), `te_tax_gen_copy_slot_<s>` (every payload field `te_tax_gen_store_<s>` writes, `_due0`, `_pver_*` and `_xver_*` included), so a held or awaiting package keeps its dates and state. Then `te_tax_init_country` backfills anything the original lacked, and the rebels' own values: `te_tax_bl_on = 0` and `te_tax_dr_on = 0` (unfinished bills and drafts stay with the government that wrote them), commitments released (`te_tax_gen_reset_commitments`), pending promises released (`te_tax_obl_release_pending`; binding ones were copied with their clocks by `te_tax_gen_copy_obligations`, [Policy obligations](#policy-obligations)), `te_tax_sync_version = -1`, the original's whole list of named states copied (`te_tax_copy_relief_states`, the states the original still holds included) and the rebels' marks rebuilt from it (`te_tax_rebuild_relief_marks`), and `te_tax_migrated = 1` last. One `TE_TAX uprising_copy` line. The variables are written at the moment of the outbreak, in the hook: `set_variable` does not depend on ROOT. An original without a code (not yet migrated) leaves the rebels to `te_tax.3`.
- **Carrier and first sync.** The rebels then get the hidden `te_tax.6` (`te_tax_adopt_copied_code`): `activate_law = law_type:law_te_tax_code` if they do not hold it, and `te_tax.4` the next day, which writes their collection from the copied code. It is a country event, so it runs with the rebels as ROOT; whether it fires before or after the engine has finished setting their laws is unread, and either order ends with the carrier (next point). Its two lines (`TE_TAX adopted … activated the tax code law` or `… already in place`) say whether the carrier arrived with the rebels; whether its amendments did is the unrun probe P15, and the stateless sync makes either answer safe.
- **A taxation law on the rebels after the copy** (a revolutionary movement's) fires `on_law_activated` in a migrated country, so `te_tax.5` puts the carrier back ([Native controls and drift](#native-controls-and-drift)): both sides keep the code, as spec §10 asks, and the movement's taxation law does not take effect.
- **Decisions.** The history ring and the drift counters are copied: the rebels continue the nation's record, so a rebel winner keeps both. `te_tax_last_month` is copied (through `te_tax_copy_token`; only the processor claims a month): a month the original has processed is not processed again. `te_tax_sync_version` is set to -1, not copied (the plan said copy): the rebels' writer has never synced their carrier, so their first sync is a fresh one and whatever the carrier arrived with is not counted as drift. The payload of a free slot is not copied: nothing reads it while `_on` is 0.
- **During the war** each side drafts, debates, passes and commences on its own; the scheduler processes both. Each collects from its own states: the writer touches only owned states.

### Reunification

- **Hook.** `te_civil_war_on_won` calls `te_tax_repair_after_civil_war` (THIS = the winner after the merge) between `te_civil_war_resolve_sides` and `te_civil_war_clear`. It runs when the winner's code is in force and two codes met: the rebels won a revolution (`te_cw_rebels_won = 1`) or the original government won (`te_cw_role = 1`). A seceder that won is a new nation, nothing merged into it, and it keeps its code untouched (`TE_TAX civil_war_repair_skipped`), as `cr_repair_after_civil_war` branches. A winner whose own `te_cw_role` an earlier win cleared, and which inherits the loser's role 2 at a second concurrent war, is skipped the same way (the shared layer's known limit).
- **Nothing is copied from the loser.** Both sides held every token from the outbreak, so the merge kept the winner's value of each, and no loser-only token, package or sunset can surface. The loser's payload of a record or slot the winner holds closed may arrive; every read checks the record's own token first, so it stays unread.
- **No `te_tax_xver_*` bump.** The packages the winner approved during the war are its own and valid; a bump would hold every one of them as conflicting.
- **What it does.** Closes the bill (`te_tax_bill_close`: commitments released, payload removed, `te_tax_bl_on = 0`) and the draft (`te_tax_draft_close`); without one, the commitments are reset and the token written 0 all the same (spec §10: pending bills are revalidated; the reunified country reintroduces its reform). Rebuilds the relief marks of every state it owns from its **own** list of named states (`te_tax_rebuild_relief_marks`; lists are not inherited, so the loser's list cannot leak in, and a state's marks from the loser's side are reset unless the winner's list names it). `te_tax_last_month = -1`, so the next dispatch processes it. History kind 7 (`te_tax_history_push = { KIND = 7 SLOT = none }`). `te_tax.6`: the carrier if missing, and collection rebuilt from the winner's variables the next day, since no modifier survives the merge. One `TE_TAX civil_war_repair` line.
- **What it never does.** It commences nothing, runs no processor, moves no version token or `te_tax_code_version`, grants no interest-group approval and adds no modifier.
- **Obligations** (plan Task 12): after the bill and the draft are closed, `te_tax_repair_obligations_after_civil_war` reassesses the winner's obligations ([Obligations in civil wars and new countries](#obligations-in-civil-wars-and-new-countries)): it never marks one fulfilled, never breaches one and never resets a clock.

### Releases and formations

- **Release from a parent holding the carrier** (`te_tax_init_released_country`, in the released country with the parent as `scope:te_tax_source`; the parent's code in force and `has_law = law_type:law_te_tax_code`): the generated `te_tax_gen_copy_enacted` copies the parent's enacted provisions, each instrument with its `_since`, `_exp` and `_succ` (a temporary rate stays temporary), the taxed goods and the two relief depths. Then `te_tax_init_country`; `te_tax_bl_on`, `te_tax_dr_on`, `te_tax_p<s>_on` and `te_tax_p<s>_state` written 0 (in case a revived tag still holds tokens from an earlier life); every obligation slot freed and every group's trust reset (`te_tax_gen_clear_obligations`: the promises are the parent's); its package slots' state lists (`te_tax_p<s>_relief_states`) emptied, since the packages stayed with the parent; the parent's list of named states copied (`te_tax_copy_relief_states`) and rebuilt (`te_tax_rebuild_relief_marks`), which keeps only the states it now owns and marks them as its own (the parent's own rebuild drops them from the parent's list); `te_tax_last_month = -1`; `te_tax_recompute_next_month` (the copied sunsets need the watchdog's cache); `te_tax_migrated = 1`; then `te_tax.6`, which needs the code in force (an event raised without `days` may run at once; the outbreak likewise raises it after the copy has written `te_tax_migrated`). One `TE_TAX release_copy` line. Nothing changed in the code, so no history is recorded and `te_tax_code_version` keeps its sentinel. The parent's packages, bill, draft and commitments stay with the parent. A released country may inherit the carrier law, and the migration would then record all zeros ([Migration](#migration), "Discrepancies"); the copy is what keeps its rates.
- **Release from a parent without the carrier**, and every **formation** (`on_country_formed`; a formation keeps the forming country's variables): `te_tax.3` migrates from the country's own active law.
- **Secession** starts like a revolution (the outbreak copy); a seceder that wins keeps its copy and is not repaired.

### Relief eligibility

- **The list is canonical.** The states the enacted regional relief names are the country list `te_tax_en_relief_states`, at most three (controller ruling, Task 11). Commencement replaces it when its package restates the states (`te_tax_gen_apply_<s>`); nothing else adds to it but the copies below. The state marks `te_tax_relief_state` are derived from it.
- **Rebuild** (`te_tax_rebuild_relief_marks`, `te_tax_civil_war_effects.txt`; country scope, saves `scope:te_tax_country`). The relief sync calls it before the modifiers, and so do the outbreak copy, a release and the civil-war repair. (1) **Prune**: a listed state the list no longer keeps leaves it. `te_tax_relief_listed_state_kept` (`te_tax_triggers.txt`) is `te_tax_relief_stays_with_code`'s rule with the list's country as the holder: the state's owner is the country, shares its `country_definition`, or is its civil-war counterpart (`var:te_cw_origin` either way). The states to drop are collected with `add_to_temporary_list` and removed in a second pass, never while the persistent list is iterated (the homeland and covert precedent). (2) Every owned state with a mark the list does not name loses it. (3) Every owned state the list names is marked and stamped with the country (`te_tax_relief_holder`). A package's states are its slot's own list, filtered by the same keep rule when it commences; they carry no mark.
- **Copy** (`te_tax_copy_relief_states`, scope:`te_tax_source` the country whose code is copied). The outbreak copies the original's whole list to the rebels, the states the original still holds included; a release copies the parent's whole list. The rebuild that follows keeps what the new code holds.
- **During a civil war** each side keeps the states the other holds (the counterpart test), so the list a side wins with still names its pre-war states. At reunification the repair rebuilds the marks from the **winner's own** list: lists are not inherited, so the loser's cannot leak in, and a state that comes from the loser's side keeps a mark only if the winner's list names it. The mixture Task 10 left open is closed by the list model: the enacted marks are rebuilt from the winner's own list, never inherited, and a package's states are its own slot list (the winner's packages carry the winner's sets; the loser's lists, wartime packages included, are not inherited). What a list can still name is a state its country does not own: the keep rule leaves a counterpart-held state in place while the war lasts, and the next rebuild or commencement drops any other.
- **Stamp.** A state's mark (`te_tax_relief_state`) is a state variable and travels with the state. The country whose code set it is stamped on the state (`te_tax_relief_holder`) when the rebuild sets the mark.
- **Owner change.** `on_state_owner_change` (ROOT = the state, new owner only) runs `te_tax_on_state_owner_change`, gated on the rule, which calls `te_tax_relief_follow_owner`: for a state with a mark it saves the state (`scope:te_tax_relief_moved`), `scope:te_tax_owner_new` and, from the stamp, `scope:te_tax_owner_holder`; unless `te_tax_relief_stays_with_code` (`te_tax_triggers.txt`) holds, every mark is reset to 0, the state leaves the holder's list, and `TE_TAX relief_cleared` is logged. The marks stay when the new owner has no code yet (a released country or an uprising about to receive a copy), is the holder, shares the holder's `country_definition` (a revolution's rebels share the original's), or is the holder's civil-war counterpart (`var:te_cw_origin` either way; a dead loser still reads). Any one test suffices, so the result does not depend on whether a transfer fires before or after the copy or the repair (the Strategic Reserve hub's rule, `st_res_hub_stays_within_nation`, plus the new tag). No stamp and a new owner with a code counts as a capture. A state the hook misses (no stamp) leaves the list at the holder's next rebuild, whose prune applies the same rule.
- **Modifiers** are left to the new owner's next sync, which removes `te_tax_relief_region_<n>` from a state without the mark: only `te_tax_sync_collection` writes collection. A captured state may keep its relief for up to a month.

## Native controls and drift

Under the rule nothing outside the code may change what a country collects for longer than it takes the code to be re-asserted (plan Task 9). Three mechanisms, by path:

- **The player's vanilla controls are greyed.** Two read-only scripted GUIs in `common/scripted_guis/te_tax_native_sguis.txt` are ANDed into the `enabled` of every vanilla control that changes a collection, keeping vanilla's own condition: `And( GetScriptedGui('<gate>').IsValid( GuiScope.SetRoot( GetPlayer.MakeScope ).End ), <vanilla> )`. `te_tax_native_controls_sgui` (valid while `te_tax_code_on` is not true and the probe lock `te_tp_lock` is absent) gates the tax level's five buttons and the consumption-tax "+" in `gui/budget_panel.gui`, the add menu's items in `gui/add_consumption_tax_menu.gui`, the four Tax/Untax items of the goods right-click menus in `gui/right_click_menu.gui`, and the type `consumption_tax_button_toggle` in `gui/goods_panel.gui`. The last two files are new full-file overrides of vanilla 1.14.5, vanilla's text plus `### MOD: Tax Code` blocks (`test_fixtures/vanilla_gui/` holds vanilla's copies; `test_tax_code_bypass.py` fails on any other change). Gating the type covers vanilla's `goods_state_panel.gui:207,219` and `custom_tooltip.gui:4785,4797` too, which instantiate it: their first instance already overrides `block "enabled"` with `enabled = no` and the second takes the type's, so neither file is overridden. `te_tax_native_tariff_controls_sgui` (valid while `te_tax_customs_on` is not true and no probe lock) gates the 14 tariff and subvention buttons of `budget_panel.gui`'s two `set_level_bar` types, which the market, goods and right-click views share; under the plain rule option tariffs stay native and usable. With the rule off both are the probe gate they replaced, so a rule-off game is unchanged. A gate binds only the player's buttons: the AI and script write the native state directly.
- **A vanilla taxation law activated by script is replaced by the carrier again.** The five vanilla laws cannot be enacted under the rule (`common/laws/te_tax_vanilla_law_gates.txt`), but `activate_law` ignores `can_enact`. `on_law_activated` fires for script activation too, so `te_tax_on_law_activated` (`common/on_actions/te_tax_on_actions.txt`; ROOT is the law) dispatches the hidden country event `te_tax.5` to the owner when the rule is on, the law is in `lawgroup_taxation` and is not `law_te_tax_code`, and the owner is migrated. `te_tax.5` runs `te_tax_reassert_carrier` (`common/scripted_effects/te_tax_migration_effects.txt`): if the country does not hold the carrier, `activate_law = law_type:law_te_tax_code`, `te_tax_last_month = -1` (the next dispatch processes it; only the processor claims a month), `te_tax.4` a day later to write collection onto the fresh carrier, and one `TE_TAX reasserted …` line. The enacted code is untouched: it was never changed. This covers vanilla's `restore_peruvian_constitution` (1.14.5 `common/scripted_effects/00_victoria_scripted_effects.txt:2930-2935`, Per-Capita whenever the country lacks it), the law-consistency cascade and a taxation law the engine gives an uprising after the outbreak copy, without editing a vanilla file. Hungary's Per-Capita button is not a live path: it activates Per-Capita only from Land-Based taxation (1.14.5 `common/scripted_buttons/05_hungary_buttons.txt:229-237`), which no country holds under the rule. Cultural Hegemony's law pressure (`cultural_hegemony.16`, mod content) leaves `lawgroup_taxation` out of its pools under the rule.
- **Every other native write is put back by the monthly sync, and counted.** The AI changes its tax level and taxed goods in engine code, with no per-country switch (`docs/testing/tax-code-capability-ledger.md`, row 13), and events can call `set_tax_level` (vanilla's negotiation option 7). `te_tax_sync_collection` overwrites both each month. Before it writes, `te_tax_detect_drift` (`common/scripted_effects/te_tax_collection_effects.txt`) counts what differs from the code: `te_tax_drift_level` +1 if the level is not `medium`, `te_tax_drift_goods` +1 per good taxed or untaxed against the enacted list (`te_tax_gen_count_goods_drift`, `te_tax_gen_goods_drift`), `te_tax_drift_amend` +1 per instrument whose carrier amendments differ from its enacted index (`te_tax_gen_amend_drift_<key>`, which tests every amendment of the family both ways), (the counts are `te_tax_count_drift`) and logs one `TE_TAX drift … totals level=… goods=… amend=…` line, every time for a player's country and the first time only for an AI's, since the AI may move its level every month the code pins it back. It runs only while `te_tax_sync_version` equals `te_tax_code_version`, that is, while the code has not changed since the amendments were last synced: a sunset, a commencement or the migration changes the code before the following sync, so the native state then differs by law, and whatever else drifted in such a month is put back uncounted. The first sync after a re-assert does count the carrier's lost amendments. The counters only grow; the guarded `te_tax_view_drift_level`, `_goods` and `_amend` read them.
- **Vanilla objectives and mod content are reconciled.** Three vanilla journal entries complete only on Per-Capita, Proportional or Graduated taxation: `je_great_reforms_bureaucratic`, `je_portugal_regeneration` and `je_imperialism_of_promise`. `common/journal_entries/te_tax_vanilla_je_overrides.txt` holds `REPLACE:` copies of the 1.14.5 entries whose taxation `OR` becomes `trigger_if = { limit = { te_tax_code_on = yes } OR = { <vanilla's laws> <counts-as lines> } }` plus a `trigger_else` with vanilla's `OR`, so with the rule off the entry and its tooltip are vanilla's. The counts-as triggers (`common/scripted_triggers/te_tax_triggers.txt`) need the rule and the carrier: `te_tax_code_counts_as_per_capita` (head and wage tax indices ≥ 1), `te_tax_code_counts_as_proportional` (wage index ≥ 4, i.e. 10%; dividend index ≥ 1, 2.5%), `te_tax_code_counts_as_graduated` (wage index ≥ 4, dividend index ≥ wage index; the two share a step, so indices compare as rates do). Each reads the enacted index variables behind `has_variable`, never a script value on the left (Task 9 review, Task 11). Traditionalism, which disallows those three laws by name, holds a bill to no wage and no dividend tax (`te_tax_draft_ready`, so both introduce and revise): the draft's own index on the left, `var:te_tax_dr_<key> = 0` or `var:te_tax_dr_<key> <= te_tax_dr_zero_limit_<key>`, where the limit is −1 when existing law in the draft's month levies no such tax and −2 when it does, so an untouched provision (−1) passes exactly when that law levies none. The mod's `re_spectrum_auction` (`tax_dividends_add`) becomes, under the rule, `te_tax_spectrum_auction` (its legitimacy cost) plus `te_tax_spectrum_auction_proceeds` (`country_tax_income_add = 1` × `sv_money_flow_event_small`). What stays inert or dead (gates that need the absence of a vanilla tax law, party weights, negotiation option 7 and `je_negotiate_taxes`) is listed in `docs/testing/tax-code-capability-ledger.md`, "Vanilla content under the rule". `event te_tax_debug.1` (`events/te_tax_debug_events.txt`, console only) activates Per-Capita over the carrier to test the re-assert.

## Draft, bill and passage

One editable draft and at most one bill under debate per country (spec §3, "one tax bill under debate per country, plus one editable draft"). A draft changes nothing. Introducing it copies it into the bill and starts debate; interest groups commit to the bill's current revision; passing it stores an approved package in a free slot, which the [scheduler](#scheduler-package-slots-and-history) commences on its due month. A withdrawn bill or a discarded draft leaves the enacted code and the approved packages exactly as they were. The passage rule is the spec's fallback (§7.4, §8): IG commitments weighted by clout, legitimacy, and a debate period. It does not simulate seats or chambers.

### Records

`<r>` is `dr` (the draft) or `bl` (the bill). The two tokens are in the [schema table](#schema); everything else here is payload: written in full when the record opens, read only while its token is 1, and removed when it closes (`te_tax_gen_draft_clear`, `te_tax_gen_bill_clear`, the only removals in the tax code). A civil war's winner may inherit a loser's payload for a record it holds closed; it stays unread.

Whether accepting commits the group is not stored: it is read from the group's score at acceptance. Reset with the commitments (`te_tax_gen_reset_commitments`: `_kind` 0, `_rev` -1); the rest is read only while `_kind` is above 0.

### Commands

Every command `te_tax_cmd_<c>` (`common/scripted_effects/te_tax_bill_effects.txt`) runs only inside `if = { limit = { te_tax_can_<c> ... } }` (`common/scripted_triggers/te_tax_triggers.txt`), the trigger a GUI button uses as its `is_valid`, so the button's tooltip and its click cannot disagree. Each says what it does with a `custom_tooltip` (`te_tax_tt_cmd_*`), because variable writes show nothing in a tooltip, and each condition of its trigger is a `custom_tooltip` line (`te_tax_tt_*`), so a disabled button lists every failing condition. A condition that reads a record's payload sits behind `trigger_if = { limit = { te_tax_draft_active = yes } ... }` (or `te_tax_bill_active`), whose `trigger_else` shows "a draft is open" / "a bill is under debate", so a closed record is never read. Every trigger starts with `te_tax_code_in_force`: the rule is on, the country has `te_tax_schema` and `te_tax_migrated ≥ 1`. Commands are effects for clicks and AI decisions; none runs from a GUI read.

| Command | Valid when | Does |
|---|---|---|
| `te_tax_cmd_draft_new` | no draft is open | opens a draft: a copy of the bill if one is under debate, else every field untouched and `due` = now + `te_tax_default_due_offset` (3) |
| `te_tax_cmd_draft_step = { KEY DIR }` | a draft is open; DIR 0: the target (or baseline) is above 0; 1: below `te_tax_max_<key>`; 2: not already 0; 3: not already the maximum; 4: the draft touches the provision | DIR 0 one step down, 1 one step up, 2 zero, 3 maximum, 4 untouched (`_sun` 0, `_pver` -1). An untouched provision starts from `te_tax_base_dr_<key>`, the rate in force under existing law in the draft's due month. The first touch records `_pver` |

### Relief in a bill

Agricultural wage relief (`agrel`) and regional relief (`regrel`) are bands, 0 none, 1 (−25%), 2 (−50%); `te_tax_max_<relief>` = 2. A draft steps them like a tax (`te_tax_cmd_draft_relief`, `te_tax_relief_<relief>_sgui`, ops 0–4); they have no sunset. Regional relief also names its states, at most three, in the draft's country list `te_tax_dr_relief_states`; a draft that changes the band restates the same states, because the first change copies existing law's. Choose States (`te_tax_cmd_draft_relief_choose`) is the only thing that builds the candidate list `te_tax_dr_relief_candidates`, from the incorporated owned states; the workbench's rows over it pass each state as the saved scope `te_tax_st` to `te_tax_relief_state_sgui` (the Grand Monuments rows' shape, unverified in game for a state). The bill copies the list; the store copies it into the slot's own list (`te_tax_p<s>_relief_states`); commencement replaces the enacted list ([Relief eligibility](#relief-eligibility)). The relief group has one planned version (`te_tax_pver_relief`, `te_tax_dr_relief_pver`) and one external version (`te_tax_xver_relief`). Labels say only what the capability ledger verified (rows 8 and 9): agricultural relief "halves (or cuts by a quarter) the wage tax for workers in agricultural buildings"; regional relief "reduces all taxes collected from pops in the named states". Neither is said to reach dividends (`test_tax_code_goods_relief.py` checks every relief key).

### Passage

`te_tax_can_pass`, one `custom_tooltip` line per condition, the payload lines inside `trigger_if = { limit = { te_tax_bill_active = yes } }`:

1. `te_tax_code_in_force`;
2. a bill is under debate (`te_tax_bl_on = 1`; the `trigger_else` line);
3. `te_tax_committed_share > te_tax_passage_share` (0.5);
4. `legitimacy >= te_tax_passage_legitimacy` (25, the edge of vanilla's Illegitimate tier);
5. `te_tax_debate_days_left <= 0`: `te_tax_debate_days_major` (30) days since the last material revision, `te_tax_debate_days_minor` (15) for a minor bill;
6. `te_tax_bl_due > now`, i.e. `due ≥ now + 1`;
7. a free slot (`te_tax_pa_on = 0` or `te_tax_pb_on = 0`);
8. `te_tax_gen_bill_current`: every provision group the bill touches still has the external version it had at introduction;
9. `te_tax_gen_bill_sunsets_valid`: every sunset gives `_exp ≥ _due + 1`;
10. `te_tax_bill_changes_something` (Task 15 fix round 1, defensive): the bill changes something from existing law in its month: an instrument's rate, an expiry it sets or a pending one it replaces (`te_tax_gen_bill_changes_instruments`; a restated rate with a new expiry is an extension), a taxed good, agricultural relief, regional relief's band or states, or a customs level (Task 13's change counts, never a mere restatement); force-through repeats it;
11. `te_tax_can_store_package` for slot `a` or `b`, the store's own check, so the two cannot drift apart. It fails only together with an earlier line.

### Pass

`te_tax_cmd_pass`: slot `a` if `te_tax_pa_on = 0`, else `b` (`te_tax_pass_into = { SLOT OTHER }`). Everything below runs only inside `if = { limit = { te_tax_can_store_package = { SLOT } } }`, so history, reactions and closing the bill happen only when the package is stored: the store checks exactly that trigger, and nothing before it in the sequence changes what it reads (supersession writes only the other slot, the bump only `te_tax_pver_*`). The check sits before the store, not after it, so the Pass button's tooltip, rendered while the slot is still empty, keeps the per-group disapproval lines. Otherwise nothing changes and `TE_TAX pass_refused` is logged. In this order:

1. **Supersession at approval** (`te_tax_gen_supersede_<OTHER>`). Only the other approved slot is touched, and only if it is on (any state) and its `_due >= te_tax_bl_due`: every instrument the bill touches is dropped from it (`<key>`, `_exp`, `_succ` = -1), and likewise every good (`_g_<good>` = -1) and relief depth (`_agrel`, `_regrel` = -1, `_regrel_states_set` = 0) the bill touches. One history entry, kind 8. A package left touching nothing is withdrawn (`_on` = 0, `_state` = 0); its state list `te_tax_p<s>_relief_states` is emptied, as it is when the bill drops its regional relief. **The enacted provision and its sunset are never touched at approval**; the package supersedes them when it commences (`te_tax_gen_apply_<s>`, [Processor rules](#processor-rules) rule 3). A slot due earlier than the bill is left alone: it commences first and the bill then replaces it.
2. `te_tax_gen_bump_pver`: `te_tax_pver_<key>` +1 for every instrument the bill touches, `te_tax_pver_goods` if it touches a good, `te_tax_pver_relief` if it touches relief. A draft written against the old baseline then needs a rebase.
3. `te_tax_store_package = { SLOT }` ([Storing a package](#storing-a-package)): `seq` one above both slots; the review's "reverts to" text reads the stored `te_tax_p<s>_<key>_succ` preview.
4. History kind 6 for the slot.
5. `te_tax_gen_oppose_approval`: each group with score below 0 that is not committed to this revision gets `ig_approval_effect = { IG = ig_<ig> MODIFIER = ig_approval_negative_modifier DAYS = te_tax_opposed_approval_days }` (−3 interest-group approval, decaying over 180 days; the mod's shared "Disapproves of Policy" modifier).
6. A draft identical to the bill (`NOT = { te_tax_gen_draft_differs_from_bill = yes }`) is discarded; a different one stays.
7. The bill closes: commitments released, payload removed, `te_tax_bl_on` = 0. Each step logs `TE_TAX passed` / `superseded` / `stored` in `debug.log`.

### Support model v1

Refreshed by `te_tax_refresh_support` (rule on and a bill open) on introduction, revision and rescheduling, and monthly by the processor (`te_tax_process_month`, last, after the month's transitions and obligation checks, while `te_tax_bl_on = 1`). Never from a GUI: opening the panel shows the last snapshot. Each reason is clamped to −40…+40 and the score to −100…+100. The arithmetic is in generated values (`te_tax_generated_support_values.txt`, from `EXPOSURE`, `LEVEL_STEPS` and `TAX_LAW_PROGRESSIVENESS` in `gen_tax_code.py`) and `te_tax_support_values.txt`.

- **Baseline.** Each provision's baseline is the index in force under existing law in the bill's due month (`te_tax_base_bl_<key>`): the enacted value, its successor if its sunset falls in or before that month, then each awaiting package due earlier, in commencement order, with its own sunset preview. A package due on or after the bill is superseded at approval, so it is not part of the baseline. In the spec's example (30% dividends reverting to 15% in January, a bill for 25% from February), the baseline is 15% and the bill is a rise.
- **Change in tax levels.** `ΔL_<key>` (`te_tax_dl_<key>`) = (bill index − baseline index) × step ÷ level step, 0 if the bill leaves the provision alone. One vanilla tax level: wage 0.05, dividends 0.05, rural assessment 0.15, head tax 0.15, consumption 0.05 (`te_tax_level_step_<key>`).
- **Material** (`te_tax_mat_<ig>`): −10 × (Σ ΔL_channel × exposure(ig, channel) + ΔL_goods × exposure(ig, cons)) + the relief points, clamped to −40…+40 as a whole (Task 11).
  - **Goods** (`te_tax_dl_g_<good>`, summed in `te_tax_dl_goods`): (bill flag − flag under existing law in the bill's month, `te_tax_base_bl_g_<good>`) × 0.2 × the good's category weight, for each good the bill touches: `staple` 1.0, `industrial` 0.3, `luxury` 0.2, `military` 0.2 (`aeroplanes` and `small_arms` reach pops only through the leisure need). From the goods file's `category` (`GOODS_CATEGORY_WEIGHT`, `gen_tax_code.py`, which fails on a catalog good with another category). One value per good so that the customs task can zero a single good's term (spec §6: exempting a good while raising its import duty earns no affordability bonus). Only the material reason sees goods: the fiscal reason's direction (`te_tax_dl_total`) and the progressivity (`te_tax_dl_prog`) read the five instruments only.
  - **Relief**, in points, scaled by what the relief reaches (spec §7.2: coverage matters, not just nominal rates; Task 11 fix round 1). These values are read only by the support refresh (`te_tax_gen_refresh_support`), never by a panel: the population shares iterate a state list.
    - **Agricultural**: rural_folk +8, landowners +3, times `te_tax_bl_agrel_scaled` = the bands the bill moves it from existing law (`te_tax_bl_dstep_agrel`) × `te_tax_bl_agrel_wage_factor` = min(1, effective wage index ÷ `te_tax_agrel_ref_wage_idx` (4, i.e. 10%)), the effective wage index being the bill's if it changes the wage tax, else existing law's in its month (`te_tax_base_bl_wage`). Relief on a wage tax of 0 scores nothing.
    - **Regional**: +4 for every group, and −2 on top for industrialists and petty_bourgeoisie (net +2), times `te_tax_bl_regrel_coverage` = (bill band × `te_tax_bl_relief_pop_share` − existing band × `te_tax_base_bl_relief_pop_share`) ÷ `te_tax_regrel_ref_share` (0.25), 0 if the bill leaves regional relief alone. A share is Σ `state_population` of the named states the country still owns ÷ `total_population`; existing law's set in the bill's month is an awaiting package's list that restates it before then (the last in commencement order), else the enacted list. One band over a quarter of the population, where there was none, scores the full +4; the same band over one small state, a fraction of it.
- **Ideology** (`te_tax_ideo_<ig>`): 5 × P(ig) × ΔProg. P(ig) (`te_tax_ideo_p_<ig>`) = Σ over the vanilla taxation laws of stance × progressiveness ÷ 100, the stance read with `law_stance = { law = law_type:<law> value > approve }` and so on (strongly approve +2, approve +1, neutral 0, disapprove −1, strongly disapprove −2; strongest bucket first). Per-Capita has progressiveness 0 and is skipped, so P lies in −6…+6. ΔProg (`te_tax_dl_prog`) = (ΔL_wage + ΔL_div) − (ΔL_land + ΔL_head + ΔL_cons) − Σ `te_tax_dl_g_<good>` over the staples: taxing a staple is regressive (Task 13).
- **Fiscal** (`te_tax_fiscal_reason`, the same for every group): with a deficit recorded on the 1st (`te_tax_fisc_rec_deficit`, the [fiscal record](#the-fiscal-record), `net_fixed_income < 0` when the processor read it), +8 for a bill that raises revenue and −8 for one that cuts it; with a record and no deficit, −4 and +4; with no record yet (before the country's first processed month), 0. The live budget is never read (final review A-I2): a budget slider moved for a few days, then restored, would otherwise move every group at once, and a group committed to the revision stays committed. The direction is the sign of `te_tax_dl_revenue` (Task 13, from the Task 11 review): Σ ΔL of the five instruments (`te_tax_dl_total`) plus the goods the bill taxes (`te_tax_dl_goods`), less the relief it grants in tax levels forgone, `te_tax_agrel_revenue_levels` (0.25) per scaled band of agricultural relief and `te_tax_regrel_revenue_levels` (0.25) per unit of regional coverage. A sign heuristic, not an estimate; read only by the refresh, since the coverage iterates a state list.
- **Customs** (Task 15, the customs option only; in points, inside the material reason's clamp): per level step the bill raises a good's level from existing law in its month (`te_tax_bl_dstep_<d>_<good>`), summed per category (`te_tax_bl_dcu_<d>_<category>`), times `CUSTOMS_POINTS`: raising an **import** level on a staple, rural_folk +4 and landowners +4 (domestic producers), trade_unions −4 and petty_bourgeoisie −2 (consumers); on an industrial good, industrialists +3, trade_unions −1; on a luxury, petty_bourgeoisie −1 and intelligentsia −1. Raising an **export** tariff on a staple: trade_unions +2, landowners −4. Military goods score nothing. Subventions are the same scale below zero, so a step down mirrors the signs. Combined incidence (spec §6): `te_tax_dl_g_<good>` of a good in both catalogs is held at 0 or above when the bill raises its import level, so exempting it from consumption tax earns no affordability bonus (nor counts as a staple untaxed for progressivity); a tax the bill adds is never zeroed. The fiscal reason does not read customs (tariff receipts depend on trade volumes; no sign heuristic yet). The offers' "leaves a bill" tests count a changed level (`te_tax_bl_customs_changed`).
- **Government** (`te_tax_gov_<ig>`): +10 if `is_in_government`.
- **Trust** (`te_tax_trust_reason_<ig>`, Task 12): 10 × `te_tax_trust_<ig>`, the group's kept less broken promises, so −10 per broken promise and +10 per kept one, within the reason's −40…+40 ([Policy obligations](#policy-obligations)). Shown on the group's card as Kept Promises.
- **Promises** (`te_tax_prom_<ig>`, Task 13): recomputed at every refresh from the promises accepted under this bill, never accumulated. The group's own accepted promise counts `te_tax_offer_points` (20), or `te_tax_offer_points_maint` (8) if it only maintains what held when it was recorded (the obligation's `_maint_only`, the test `te_tax_obl_is_maintenance` makes), and only while its pending obligation is live (`te_tax_offer_prom_live`: a slot pending for the current revision with the same kind, arg and group). Another group's institution promise counts −3 per step of this group's stance on the law with none of that institution (`law_no_schools`, `law_no_health_system`, read with `law_stance` as the ideology reason does; strongly ±6): a group that wants the institution welcomes it, one that wants none resents it. The balance promises have no side effect. Shown on the group's card as Promises.
- **Commitment.** A group committed to the current revision stays committed whatever its score. Otherwise its score decides: ≥ `te_tax_commit_threshold` (20) commits (`com` 1, `com_rev` = `rev`), ≤ `te_tax_redline_threshold` (−40) is a red line (−1), anything between is persuadable (0).
- **Committed share** (`te_tax_committed_share`) = Σ `ig_clout` of committed groups ÷ Σ `ig_clout` of all groups, both sums over groups with `ig_counts_as_marginal = no` (vanilla's scripted trigger: clout below the marginal threshold with a voting franchise, else `is_marginal`), unrolled over the eight `ig:ig_<ig>`. A group the country lacks counts in neither; the share is 0 when no group is eligible. A marginal group can hold a commitment, but it counts only once it is no longer marginal. The share is read live (clout moves), the commitments from the snapshot.

### Offers

Spec §7.2–7.4 and §8 steps 1–4; plan Task 13. Hand-written parts in `common/scripted_effects/te_tax_offer_effects.txt` and `te_tax_triggers.txt`; per-group parts generated (`te_tax_gen_offer_select`, `te_tax_gen_offer_apply`, `te_tax_gen_offer_repropose`, `te_tax_gen_offer_feasible`). `test_tax_code_offers.py` pins it.

- **Selection** (`te_tax_gen_offer_select`, the last step of `te_tax_gen_refresh_support`, never a panel). A group committed to the current revision withdraws its offer. Any other group that exists, is not marginal (`ig_counts_as_marginal = no`) and has made no offer for this revision (`te_tax_off_<ig>_rev`) makes at most one, from its top negative reason: when its material reason is below 0 and no other reason is lower, a clause first, then a promise; otherwise (another reason lowest, or none negative) a promise first, then a clause. A group at its red line (`te_tax_com_<ig>` = −1) is offered promises only. An offer is made only when it can be carried out; one recorded stays for the revision.
- **Catalog**, per group, preferred first:

| Group | Clauses | Promises |
|---|---|---|
| trade_unions | soften its top-grievance raise; take back an added staple | health system one level up |
| rural_folk | soften its top-grievance raise; take back an added staple; agricultural relief one band up | schools one level up |
| devout, intelligentsia | soften its top-grievance raise | schools one level up |
| petty_bourgeoisie | soften its top-grievance raise | bureaucracy balance |
| industrialists | soften its top-grievance raise | bureaucracy balance; fiscal balance |
| landowners | soften its top-grievance raise | fiscal balance |
| armed_forces | soften its top-grievance raise | — |

  A clause only softens what the bill changes, or adds relief (controller ruling, Task 13 pre-review); a group whose top grievance is not a raise of the bill or a staple it adds is offered a promise, or nothing.
  - **Grievance** (`te_tax_bl_grief_<ig>_<key>`, generated, per instrument the group pays any of): the bill's raise in tax levels times the group's exposure (`te_tax_dl_<key>` × `EXPOSURE`), 0 unless the bill raises the instrument above existing law in its month (`te_tax_bl_dstep_<key>` > 0); `te_tax_bl_grief_<ig>_goods` the same for the goods the bill taxes, on the consumption channel, 0 unless they add to the burden. The largest is the group's top grievance.
  - **Soften a raise** (code 1, arg = the instrument as `te_tax_h<n>_inst` codes it): the top grievance among the instruments (the first in `INSTRUMENTS` order on a tie, and at least the goods grievance) is lowered one index step, never below existing law (`te_tax_offer_cut`: `clamp_variable` with `min = te_tax_base_bl_<key>`; a raise taken back to existing law leaves the provision alone). Offered and accepted only while the bill still raises it and the cut leaves the bill changing something from existing law (`te_tax_offer_cut_leaves_a_bill`: the raise stays above it, or the bill changes another instrument, a good or relief). Only real changes count, never a restatement: instruments and goods by their change from the baseline (`te_tax_bl_changed_provisions`, `te_tax_bl_goods_changed`), agricultural relief by its band change (`te_tax_bl_dstep_agrel`), regional relief by `te_tax_bl_regrel_differs` (another band, or another set of named states than existing law's list in the bill's month, `te_tax_bl_relief_states_match`).
  - **Agricultural relief** (code 2): one band more than the bill's (or existing law's) band (`te_tax_bl_eff_agrel`), below the deepest, while there is a wage tax to relieve (`te_tax_bl_eff_wage`). Adding relief is allowed whatever the grievance.
  - **Take back an added staple** (code 3, arg = its place in `staple_order()`): when the goods are the top grievance (strictly above every instrument's), the first staple the bill adds to the taxed list (`te_tax_dl_g_<good>` > 0: taxed by the bill, not by existing law), in `staple_order()`: vanilla's `consumption_tax_cost` descending (vanilla prices a good's tax Authority by its yield), then base price, then name, so grain first. The bill leaves the good alone again (−1). Only while that leaves the bill changing an instrument, relief or another good from existing law (`te_tax_offer_untax_leaves_a_bill`, the same change counts).
  - **Promises** (kind 10 + the obligation kind; Task 12's adapters): schools or health system at today's delivered level + 1 (`te_tax_obl_inst_next_<arg>`), offered only if `te_tax_obl_feasible_1`; no bureaucracy deficit (kind 2); a fixed-budget surplus (kind 4). Each only if `te_tax_can_obl_propose` holds (no identical pending or binding obligation, a free slot) and the group accepted no promise under this bill. `_maint` records `te_tax_obl_is_maintenance`.
- **Acceptance** (`te_tax_cmd_accept_offer = { IG }`, the Accept button on the group's card). In order: whether the group commits, read from its score now (`te_tax_sup_<ig>` ≥ 0, persuadable: spec §7.3, the offer is its condition for commitment; an opposed or red-lined group takes the concession and opposes the bill less, and commits only if the refreshed score reaches the threshold), into a local variable; the offer applied (`te_tax_gen_offer_apply`): a clause to the bill and to the draft (`te_tax_offer_cut`, `te_tax_offer_agrel`, `te_tax_offer_untax`; the draft takes the bill's new value, replacing any edit the player made there to the same instrument or good, and the tooltip says so, so a later revision from it keeps the concession; relief the bill takes up here records the relief group's planned and external versions as they stand), recorded in `te_tax_bl_got_<ig>_<code>`; a promise recorded in `te_tax_bl_prom_<ig>_*`; `te_tax_bl_rev` + 1; `te_tax_bill_open_revision` (the debate clock and class restart, commitments released and offers withdrawn, pending promises released); `te_tax_gen_offer_repropose`; the group committed to the new revision if it was persuadable; a support refresh, in which the others re-commit if they reach the threshold and make new offers. Every acceptance is a new revision (spec §8 step 3), so the debate restarts.
- **Re-proposal** (`te_tax_gen_offer_repropose`): each promise recorded on the bill is proposed again (`te_tax_obl_propose` with its kind, arg, target and group) on the new revision; one that cannot be (the same promise already binding, no free slot) is dropped from the record and logged (`TE_TAX offer_promise_dropped`).
- **Anti-farming.** One offer per group per revision; a clause a group gained in this bill is never offered to it again; one promise per group per bill; no promise identical to a pending or binding obligation is offered or accepted, and the promises reason counts only live pending obligations. A revision from the draft (`te_tax_cmd_revise`) writes the records empty: the player rewrote the bill, so its bargains go with it, and the groups offer afresh.
- **The card** (`te_tax_ig_card`): Promises as a sixth reason; while the group has an offer for this revision (`te_tax_disp_ig_offer` above 0), what it asks (`InterestGroup.GetCustom('te_tax_ig_offer')`, an interest-group-scope customizable localization over the guarded `te_tax_disp_ig_offer*` values; maintenance promises say "keep"), what accepting gives, by the group's stance now (persuadable: it commits; opposed: it opposes the bill less; red line: its score rises; both commit only at the threshold) and Accept (`te_tax_cmd_accept_offer_sgui`, the card's group passed as the saved scope `te_tax_ig` with `AddScope( 'te_tax_ig', InterestGroup.MakeScope )`, dispatched by `is_interest_group_type` to `te_tax_can_accept_offer = { IG }`; no scope, no type match: it fails closed).

### Force through

Spec §7.4: bypass options integrate legislative override capacity and expose Authority costs and political consequences. `te_tax_can_force_through` (one `custom_tooltip` line each): the code in force; a bill; it lacks the committed support to pass on its own (`NOT = { te_tax_committed_share > te_tax_passage_share }`); committed share ≥ `te_tax_force_share` (0.35); `"modifier:country_legislative_override_capacity_add" >= 2`, the raw modifier sum, as the forced-law event reads it; `produced_authority > forced_law_through_event_authority_cost_medium`, the event's medium tier's own gate; then every other line of `te_tax_can_pass` repeated verbatim (legitimacy, debate, due month, a free slot, no outside change, sunsets, the store's own check). `te_tax_cmd_force_through` picks slot a or b as the pass does; `te_tax_force_into`, only when the store will accept the bill, adds the medium option's two modifiers of `minor_events_timelineextended.2` (`forced_law_through_event`, five years, decaying, `multiplier = forced_law_through_event_authority_multiplier_medium`; `forced_law_through_event_consequences_medium`, five years, decaying: opposition approval −3, legitimacy −5, movement radicalism and attraction, override capacity −2), logs `TE_TAX forced_through` and runs `te_tax_pass_into`. Nothing new is defined; the event's enactment modifier is left out, since only a law under enactment takes one. The multiplier resolves against ROOT: the Force Through button's scripted GUI roots on the player; any other caller (the AI in package 6) must run with the country as ROOT.

### Interest-group views of the code

Plan Task 13 (controller ruling, pre-review): no ideology takes a stance on the carrier law, so without more a group would lose the approval it took from its stance on the country's taxation law. Instead each group's approval follows its own vanilla stance toward the vanilla taxation law the enacted code is equivalent to, at vanilla's magnitudes.

- **Equivalent law** (`te_tax_code_equivalent_<law>`, `te_tax_triggers.txt`; exactly one holds for a rule-on country holding the carrier, none without it): Graduated if `te_tax_code_counts_as_graduated`; else Proportional if `te_tax_code_counts_as_proportional`; else Per-Capita if `te_tax_code_counts_as_per_capita`; else Land-Based if the rural assessment index is at least 1; else Consumption-Based. Every migrated (law, level) row of the five vanilla laws maps back to its own law (`test_tax_code_offers.py` evaluates the counts-as triggers' own comparisons on `MIGRATION`), so the migration changes no group's approval.
- **Band** (`te_tax_ig_band_<ig>`, generated support values; reads no variable): the group's `law_stance` toward the equivalent law, strongest bucket first: strongly approve +2, approve +1, strongly disapprove −2, disapprove −1, else 0 (also 0 without the carrier).
- **Modifiers** (`common/static_modifiers/te_tax_generated_modifiers.txt`, generated): `te_tax_ig_view_<ig>_<band>`, band `m2 m1 p1 p2`, each with only `interest_group_ig_<ig>_approval_add`: the approval vanilla gives for an active law the group takes that stance on, `IG_APPROVAL_FROM_LAW` = 1 and `IG_APPROVAL_FROM_LAW_STRONG_STANCE` = 2 (1.14.5 defines; `test_tax_code_offers.py` checks the installed game's when present). `lawgroup_taxation`'s `ideological_opinion_impact` (0.5) is not applied: it scales the legitimacy penalty for governing groups that disagree on a law, not this approval (`docs/vanilla/vanilla_politics_reference.md` §2.4; inferred from the defines, not observed; if a play test shows the approval halved for taxation laws, the fix is the two constants in `gen_tax_code.py`). Band 0 has no modifier. Static, no multiplier. Names in the group's approval breakdown: (Strongly) Opposes / (Strongly) Endorses the Tax Code. One residual difference: vanilla caps a group's total approval from laws at ±5 (`MIN/MAX_IG_APPROVAL_FROM_LAWS`), and these modifiers sit outside that cap.
- **Refresh** (`te_tax_refresh_ig_views`, `te_tax_offer_effects.txt`; rule-gated; two call sites, each once per execution: `te_tax_process_month` (`te_tax.1`) after the obligations and before the sync, and `te_tax.4` after its sync, so after a migration, a re-assert or a copied code the groups hold their taxation-law approval from the day the carrier is in place, not from the next 1st): `te_tax_gen_ig_views` reads each group's band once into a local variable and keeps at most one of its four modifiers: the band's added only where missing, every other removed only where present (all of them at band 0), so an unchanged band changes nothing. A code that changes enough to count as another law changes the groups' approval at the next 1st of the month, as enacting that law would change the standing part of vanilla's approval.

### Debate clock

`game_date` used as a value is the date as a day count with 365-day years: a save made on 1 March 2069 stored the construction market's `te_construction_market_last_pulse_date` (written `value = game_date`) as 755244 = 2069 × 365 + 59, and three consecutive autosaves differ by 28 and 31 days. So `te_tax_debate_days_elapsed` = `game_date` − `te_tax_bl_day` is in days, and `te_tax_debate_days_left` = required − elapsed (never below 0; 0 without a bill). The construction market's day arithmetic (`te_construction_market_pulse_values.txt`) is the precedent.

### Decisions

- **Supersession covers goods and relief** as well as instruments: a bill's good or relief depth replaces a later-approved package's, as an instrument does. A package emptied by supersession frees its slot instead of commencing with nothing.
- **A new draft copies the bill under debate**, so "revise from draft" starts from the bill; with no bill it starts untouched, commencing in three months (30 days of debate fit before it).
- **The bill carries `_pver`** (copied from the draft) so a draft reopened from it keeps its baseline marks.
- **Rescheduling is not a revision**: commitments stay. The debate clock restarts only if the new due month changes the minor/major class (the baseline moved, so the steps did), because the class sets the debate length.
- **Every revision is material** in v1: all commitments are released and debate restarts. Spec §3's "minor revisions reopen affected commitments" (only some) is not modelled.

### Held packages

Spec §3: "missed commencement dates require explicit rescheduling and review, with renewed approval where timing materially changes the bargain". A package the scheduler holds (rule 3) keeps its slot until the player resolves it with one of two commands (controller ruling, Task 6 fix round 1):

- **Reschedule** (`te_tax_cmd_package_reschedule = { SLOT }`), for a missed package (`_state` 3) only. Valid while `te_tax_due_earliest − _due0 ≤ te_tax_reschedule_max_delay` (3), written `_due0 ≥ te_tax_package_reschedule_floor`: a delay of at most three months is not material. Also valid only while `te_tax_gen_package_unsuperseded_<s>` holds: every provision group the package changes still has the planned version recorded at its approval (`_pver_<group>`). A later bill touching the same provision moves `te_tax_pver_*` past the mark, and rescheduling would then let the older package commence after it and restore the replaced law. The check fails closed for a package stored without the marks. It sets `_due` = now + 1 and `_state` = 1, records history kind 9, and recomputes `te_tax_next_month`. It does not re-record `xver`: a missed package has no conflict to accept, and one that meets an outside change at its new commencement holds as conflicting. The approved expiry months (`_<key>_exp`) stand: with a delay of at most 3 months and every sunset at least 6 months after `_due0`, each still falls at least 3 months after the new commencement.
- **Release** (`te_tax_cmd_package_release = { SLOT }`), for a missed or conflicting package (`_state` 2 or 3). It sets `_on` = 0 and `_state` = 0, empties the slot's state list `te_tax_p<s>_relief_states`, records history kind 10, and recomputes `te_tax_next_month`. Nothing the package would have changed takes effect. A held_conflict package can only be released: renewed approval means a new bill. So can a missed one delayed more than three months, or one a later bill has touched.

## Policy obligations

Spec §7.2 ("Policy commitment catalog and lifecycle") and §8 steps 2 to 6; plan Task 12. A promise an interest group extracts in a bargain (plan Task 13 makes the offers) becomes an obligation: a typed duty with a baseline, a deadline, a maintenance term, a monthly check and one outcome, whose consequence applies once. An obligation records what was promised and checks what happened; it never executes the policy, and a broken one never repeals the tax bill (spec §8 step 6). The effects are in `common/scripted_effects/te_tax_obligation_effects.txt`, the verifiers, feasibility and command triggers in `common/scripted_triggers/te_tax_triggers.txt`, the terms in `common/script_values/te_tax_obligation_values.txt`; the variables are in the [schema](#obligation-slots-and-trust). `test_tax_code_obligations.py` pins it.

### States

| `_state` | `_on` | Meaning |
|---|---|---|
| 0 | 0 | free: never used, or released (it lapsed with its bill or package) |
| 1 | 1 | pending: recorded on the bill under debate, for the revision in `_rev` |
| 7 | 1 | bound: the bill passed; waits for its package (slot `_slot`) to commence |
| 2 | 1 | delivering, until `_deadline` |
| 3 | 1 | maintaining, until `_maint_end` |
| 4, 5, 6 | 0 | fulfilled, breached, renegotiated: the outcome, recorded as the slot is freed |

A bound obligation has its own state (7), not state 1 with a slot, so every reader tells a promise that binds from one that waits on a bill by `_state` alone. An outcome frees the slot at once: the panels list only `_on = 1` slots, and the history ring records the outcome.

### Kinds

| Kind | Delivered when (`te_tax_obl_delivered`, `te_tax_obl_holds`) | Deadline, from commencement C | Kept for (breached at `te_tax_obl_grace_<kind>` consecutive failing checks) | Offered only if (`te_tax_obl_feasible_<kind>`) |
|---|---|---|---|---|
| 1 institution level | `var:te_tax_o<N>_target <= te_tax_obl_inst_level_<arg>` while `has_institution = <x>` (`te_tax_obl_inst_met_<arg>`; the level value reads `institution:<x>` `investment`, 0 without the institution; the variable leads, as in `je_space_race.txt`) | C + 12 × max(0, target − level at C) + 6, plus a month for each month of bureaucracy deficit while delivering | 24 months (1) | `has_institution`; target ≤ `te_tax_obl_inst_cap_<arg>` (`investment_max`, the cap with its modifiers); target ≤ `te_tax_obl_inst_reach_<arg>` (today's level + `te_tax_obl_max_levels` = ⌊(60 − 6) / 12⌋ = 4), so the deadline falls within 60 months |
| 2 bureaucracy balance | `bureaucracy >= 0` (maintenance test: the fiscal record's `te_tax_fisc_rec_bur_ok`) | C + 12 | 24 months (3) | always |
| 3 military wage action | `military_wage_level <= <level>` (sampled monthly: no hook fires on a wage change) | C + 1 | 24 months (1) | the level set now is above the promised one (`te_tax_obl_wages_above_<arg>`): a cut, not a restraint |
| 4 fiscal balance outcome (maintenance test: the fiscal record's `te_tax_fisc_rec_surplus`) | `net_fixed_income > 0` at `te_tax_obl_surplus_months` (6) consecutive monthly checks (`_streak`) | C + 24 | 12 months, `net_fixed_income > 0` each month (3) | always |

- **Kind 1 reads the delivered level** (`investment`, "current investment level"), never the level requested, and never `NOT = { expanding_institution }`, which would fail a country at its target that starts growing further (capability ledger row 28: **pending P16**). Nothing in the tax code sets an institution's level (`set_institution_investment_level`, `change_institution_investment_level`): native expansion time and costs stay in force.
- **A bureaucracy deficit never breaches a kind-1 promise**: its verifier does not read bureaucracy, and each monthly check that finds a delivering kind-1 promise undelivered in a deficit (`bureaucracy < 0`) moves its deadline a month later before the deadline is tested (`TE_TAX obl_paused`, once per obligation and month): an institution does not grow during a deficit, so the deficit pauses the clock.
- **Kind 4's measure is vanilla's own fixed balance**: construction is not a fixed expense, loan interest is; one favourable month never delivers it, and a deficit month resets the streak.
- **Maintenance grace** (spec §7.2 "beyond their grace period", §8 "sustained failure"): during the term a check that holds resets `_fails`; a failing one adds one (`TE_TAX obl_failing`), and the obligation breaches once `_fails` reaches `te_tax_obl_grace_<kind>` (`te_tax_obl_grace_reached`): 1 for a level or an action (kinds 1 and 3, the government's own doing), 3 consecutive months for an outcome (kinds 2 and 4). The row then reads "Failing n of N months".
- **Maintenance promises** (spec §7.2: existing provision may be promised protection, labelled maintenance): `te_tax_obl_write` records `_maint_only = 1` when what the promise asks for already holds at proposal, by the test the offer was priced with (`te_tax_obl_is_maintenance = { KIND ARG TARGET }`; for kind 1, the delivered level at or above the target). For kinds 2 and 4 that test, and the baseline `te_tax_obl_record_baseline` writes, read the [fiscal record](#the-fiscal-record) of the 1st, never the live budget (final review A-I2): a deficit has to last over a 1st to make a promise to end it a new one (20 points and trust when kept) rather than maintenance (8, no trust); with no record yet it is maintenance. The row reads "Maintain:" instead of "Reach:", and keeping it earns approval but no trust. `te_tax_obl_is_maintenance = { KIND ARG TARGET }` (`te_tax_triggers.txt`) is the same test before a slot exists, for Task 13's pricing; its kind helpers take both parameters and use what their kind needs (an unused parameter has a mod precedent, `st_res_policy_set_by_hand_base`).
- `_baseline` records the measure when the clock starts (and at proposal, for the panel).

### Lifecycle

- **Propose** (`te_tax_obl_propose = { KIND ARG TARGET IG }`, Task 13's accepted promise). Runs only if `te_tax_can_obl_propose = { KIND ARG }` holds, one `custom_tooltip` line per condition: the code is in force, a bill is under debate, no pending or binding obligation has the same kind and argument (dedupe: one promise cannot buy support twice; two military wage promises never coexist, whatever their levels), a slot is free. Fills the lowest free slot through `te_tax_obl_write`: every payload field, `_rev` = `te_tax_bl_rev`, the baseline, `_state` 1 and `_on` 1 last. KIND and ARG are literal (they name helper triggers); TARGET and IG may be any value (`te_tax_obl_inst_next_<arg>` for "one level more"; `te_tax_ig_id_<ig>`). Whether the promise can be delivered is the offer's question: Task 13 asks `te_tax_obl_feasible_<kind>` before offering (`te_tax_obl_feasible_1 = { ARG TARGET }`, `te_tax_obl_feasible_2 = yes`, `te_tax_obl_feasible_3 = { ARG }`, `te_tax_obl_feasible_4 = yes`); the propose does not.
- **Released with the text it was made for.** `te_tax_bill_start_debate` (introduction and every revision) and `te_tax_bill_close` (withdrawal, passage after the binding, the civil-war repair) call `te_tax_obl_release_pending`: every pending obligation is freed (`_on` 0, `_state` 0), with no consequence and no history entry, as commitments are released. Task 13 offers again after a revision. Rescheduling the bill keeps them (the same revision). There is no defeat in v1: a bill is withdrawn, passed or closed by the repair.
- **Bind** (`te_tax_obl_bind = { SLOT }`, from `te_tax_pass_into` right after the package is stored, while the bill is still open): each pending obligation of the passing revision (`_rev` = `te_tax_bl_rev`) becomes bound (7) to the slot (`_slot` = `te_tax_slot_id_<SLOT>`); one recorded for an earlier revision is released.
- **Start** (`te_tax_obl_start = { SLOT }`, called only from `te_tax_gen_commence_<s>`'s apply branch, inside the processor): the package's bound obligations record their baseline, set their deadline from this month (`te_tax_now`) and start delivering (2). A held package's obligations wait, bound; a rescheduled one's start at its new month.
- **Lapse** (`te_tax_obl_release_slot = { SLOT }`): a package dropped while held (`te_tax_cmd_package_release`) or emptied by a later bill's supersession (`te_tax_gen_supersede_<s>`) releases its bound obligations with no breach and no approval effect; one history entry (kind 14) if any were bound.
- **Monthly check** (`te_tax_obl_check_month`, processor step 4: after the month's commencements, before the sync; never from a GUI or the watchdog). First trust recovery (below). Then per slot, `te_tax_obl_check_one`: a delivering obligation (kind 4 first counts its streak) is delivered → maintaining (`te_tax_obl_begin_maintenance`, `_maint_end` = now + term, `_fails` 0); else a kind-1 one in a bureaucracy deficit has its deadline paused a month; else, undelivered in its deadline month or later, breached. A maintaining one whose condition holds resets `_fails` and, at the end of its term, is fulfilled; one whose condition fails counts a failure and breaches at its kind's grace. The processor claims the month before any transition, so each obligation is checked once a calendar month.
- **Outcomes, once each.** Each outcome effect runs inside `if = { limit = { <the state it leaves> } }`, writes the outcome state and `_on` 0 first, and no other code writes those states (`test_tax_code_obligations.py`), so a consequence cannot repeat:

| Outcome | From | Approval of the beneficiary (`te_tax_gen_obl_approval`, the shared `ig_approval_effect`, decaying over `te_tax_obl_approval_days` = 180) | Trust | History |
|---|---|---|---|---|
| fulfilled (`te_tax_obl_fulfil`) | 3, at `_maint_end` | +3, `te_tax_obl_kept_modifier` ("Kept Tax Promise") | +1, none for a maintenance promise | 11 |
| breached (`te_tax_obl_breach`) | 2 past its deadline, or 3 at its grace | −5, `te_tax_obl_broken_modifier` ("Broken Tax Promise") | −1 | 12 |
| renegotiated (`te_tax_cmd_obl_renegotiate = { N }`) | 2 or 3 | −2, `te_tax_obl_renegotiated_modifier` ("Renegotiated Tax Promise") | −1 | 13 |

The three modifiers are the obligations' own (`common/static_modifiers/te_tax_obligation_modifiers.txt`), so the group's approval breakdown names the tax promise.

- **Renegotiation** is a command (`te_tax_cmd_obl_renegotiate = { N }` behind `te_tax_can_obl_renegotiate = { N }`: the code in force, `te_tax_obl_active`, i.e. delivering or maintaining), the Renegotiate button of a promise in force (`te_tax_cmd_obl_renegotiate_sgui`, op = the slot). It differs from a breach only in the approval it costs: the slot is freed, the group disapproves less (−2 against −5) and its trust falls a step, so it is no trust-free exit. A pending promise changes with the bill; a bound one waiting for its bill's commencement lapses only if that package is dropped.

### Trust

`te_tax_trust_<ig>` (a schema token, 0): +1 for every promise kept with the group (not a maintenance one), −1 for every one broken or renegotiated (`te_tax_gen_obl_trust`), held within −4..4 by `clamp_variable` with both bounds; each change records its month in `te_tax_trust_<ig>_month`. **Recovery**: the monthly obligations pass first runs `te_tax_gen_trust_recover`, which moves a trust unchanged for `te_tax_obl_trust_recover_months` (24) one step toward 0 and records that step as its change, so an old record fades a step every 24 months. The support model's trust reason is `te_tax_trust_reason_<ig>` = 10 × trust, so −10 per broken promise, within the reason's ±40 ([Support model v1](#support-model-v1)); a group card shows it as Kept Promises.

### Obligations in civil wars and new countries

- **Outbreak** (spec §10: binding obligations follow the copied code). `te_tax_gen_copy_code` copies every slot header and every group's trust with the month it last changed; `te_tax_gen_copy_obligations` copies the whole payload of each slot whose obligation binds the original (`te_tax_obl_binding`: 7, 2 or 3), so it binds the rebels with its original dates; then `te_tax_obl_release_pending` frees a slot copied pending, since the bill stays with the government that wrote it. Each side's processor checks its own obligations during the war.
- **Win repair** (`te_tax_repair_obligations_after_civil_war`, called by `te_tax_repair_after_civil_war` after the bill and the draft are closed). Both sides held every obligation token from the outbreak, so the merge kept the winner's own. It reassesses deliverability: it releases a pending obligation (defensively; the closed bill released them), a bound one whose package no longer waits in its slot (`te_tax_gen_obl_slot_gone`), and a delivering or maintaining one whose beneficiary group the reunited country no longer has (`te_tax_gen_obl_ig_exists`); one history entry (kind 14) if any. It never marks one fulfilled or breached and never resets a clock: the next monthly check verifies the rest. Trust is the winner's own (the merge).
- **Release** (`te_tax_init_released_country`): `te_tax_gen_clear_obligations` frees every slot and resets every group's trust; the parent's obligations stay with the parent.

### Obligations and the AI

The same rules apply to every country: the monthly check runs in `te_tax.1` for every migrated country, and `te_tax_cmd_obl_renegotiate` is an effect an AI decision may call. AI countries legislate only from package 6, so none holds an obligation yet.

### Obligations in the panels

The **Promises** section (`te_tax_obligations_section`, `te_tax_politics_widget.gui`, after the passed bills; open, flag `te_tax_obligations_closed`; shown while a slot is on, `te_tax_show_obligations_sgui`): one `te_tax_obligation_row` per slot while `te_tax_view_o<o>_on` is 1, the group it was made to (`te_tax_obl_ig_<o>`, the group's own name), what it promises (`te_tax_obl_what_<o>`; kind 1 `te_tax_obl_inst_<o>` at level `_target`), and where it stands (`te_tax_obl_state_<o>`: pending; binds when its bill takes effect; deliver by year.month; kind 4 "n of 6 months in surplus, by year.month"; failing n of N months; delivered, keep until year.month), each a generated customizable localization that reads only the guarded views; the promise is prefixed "Reach:" or "Maintain:" (`te_tax_obl_mode_<o>`, from `_maint_only`); and Renegotiate once it is in force (state 2 or 3). - **Callers**, and only these, each at most once per execution: the monthly processor, once, inside the month it claims, after the collection write (rule 6); the watchdog, only in the branch where a sunset made it sync, after the sync (controller ruling, fix round 1: estimates are not wrong until the 1st); `te_tax.4`, after its sync and the groups' views, so a migration, a re-assert and a copied code (an uprising's, a release's, a civil-war repair's) are snapshotted the next day (controller ruling, fix round 1); and `te_tax_bill_open_revision`, last, after `te_tax_bl_on` = 1, so the snapshot records the revision every caller has just moved on: introduction, revision and an accepted offer (Task 13 ruling: accepting any offer is a new revision; the controller brief named introduce and revise). Never a GUI, a scripted GUI's `is_shown`/`is_valid`/`effect`, or loc (`test_tax_code_estimates.py`).
- **Not schema tokens.** They are a display cache: each call writes all of them, nothing removes them, and the views read them only through `has_variable`. They are not initialised or copied at an outbreak. A civil war's winner may inherit a loser's snapshot variable it lacks; the repair's `te_tax.6` raises `te_tax.4` the next day, which takes the winner's own, and the code-version and month tests below mark an inherited one out of date meanwhile.
- One `TE_TAX snapshot` line per call, for player countries only.

**Current or out of date** (`te_tax_view_snap_current`, 1 or 0): current while the snapshot was taken this calendar month (the processor retakes it every 1st, so an older one means a month was skipped), under the code in force (`te_tax_snap_code_version = te_tax_code_version`: every writer of the code is followed by a snapshot, a migration by `te_tax.4`'s the next day, so this catches that gap and a snapshot inherited across a civil war) and, while a bill is open, for its current revision. Otherwise every estimate is printed with "Estimate out of date". Before the first snapshot (the day a country's taxes come under the code: `te_tax.4` takes the first the next day) the review's label and the offers' note say no snapshot has been taken yet, and every changed line has no current base.

### The fiscal record

`te_tax_record_fiscal_month` (`te_tax_snapshot_effects.txt`; final review A-I2) records the budget as it stood on the 1st: `te_tax_fisc_deficit` (1 if `net_fixed_income` < 0, else 0), `te_tax_fisc_surplus` (1 if `net_fixed_income` > 0) and `te_tax_fisc_bur_ok` (1 if `bureaucracy` ≥ 0). Its only caller is the monthly processor, once, after it claims the month and before any transition (rule 1a), so a record is never taken from a panel, a command or a sync. Readers go through `te_tax_fisc_rec_deficit`, `te_tax_fisc_rec_surplus` and `te_tax_fisc_rec_bur_ok` (`te_tax_triggers.txt`): the fiscal reason ([Support model v1](#support-model-v1)) and the maintenance test and baseline of the bureaucracy and budget promises ([Policy obligations](#policy-obligations)). With no record yet (a country before its first processed month), no deficit is recorded and a budget promise counts as maintenance. Like the snapshot, a refreshed cache, not schema tokens: every call writes all three, nothing removes them, and they are not initialised or copied at an outbreak; a civil war's winner may inherit a loser's record for a variable it lacks until its own next 1st. The monthly obligation check (`te_tax_obl_holds`) still reads the live budget, in the processor, on the day the record is taken.

### The estimates

Per Budget line (`CHANNELS`, `gen_tax_code.py`): Income (`GetIncomeTaxIncome`, the wage tax), Dividends (`PredictDividendsTaxes`), Poll (`GetPollTaxIncome`, rural assessment and head tax together) and Consumption (`PredictConsumptionTaxes`, the consumption tax rate). Generated, in `te_tax_generated_values.txt`, all reading the draft only while it is open:

- `te_tax_est_r_<key>_law` and `_bill`: existing law's index in the draft's month (`te_tax_base_dr_<key>`) and the draft's (`te_tax_dr_eff_<key>`), each over `te_tax_snap_<key>`; 0 when that is not above 0, the only guard a division by a snapshot index has. `te_tax_est_d_<key>` = bill − law.
- `te_tax_view_est_<line>_on`: the draft changes a tax of the line. `_nobase`: a tax of the line not collected at the snapshot is collected under existing law or the draft in its month. Dividing zero receipts by a zero rate gives no base, so the line prints "No current base — estimate unavailable" instead of a figure.
- `_law`, `_bill`, `_delta`: the line's receipts under each schedule, and the change, as multiples of today's. The GUI prints `Multiply_CFixedPoint( GetPlayer.<getter>, GetPlayer.MakeScope.ScriptValue('te_tax_view_est_<line>_<part>') )` a week.
- **Poll** is one line for two taxes, and today's receipts do not say how they divide. While both collect at the snapshot (`te_tax_view_est_poll_shared`), `_<part>_lo` and `_hi` are the lower and the higher of the two taxes' multiples: any split falls in between, so the panel prints a range. While at most one collects they are equal, the collecting tax's own multiple.
- **Offers** (`te_tax_view_est_cut_<key>`, while a bill is open): a cut lowers the bill's index by one step, −1 over the snapshot's index; the card multiplies the instrument's Budget line by it, prints a range from it to nothing for rural assessment or head tax while both collect, and "no current base" for a tax not collected at the snapshot. Agricultural relief and a staple get a label, a promise no line.
- **Regional relief** (`te_tax_view_est_regrel_state`, state scope): a band n is `state_tax_collection_mult` −0.25 n, so a state keeps (4 − n)/4 of its taxes. The view is (keep under the draft − keep under existing law in its month) over keep now, the state's band now rather than at the snapshot (its revenue is today's too), and the review prints `State.GetTaxationRevenue` times it on each state the bill names, and on each state existing law names that the draft drops. Other collection modifiers are taken as unchanged.
- **Labels, no number**: taxed goods ("the effect depends on how much pops buy of these goods"; `Goods.CalcPotentialConsumptionTaxAmount` exists but the generated goods rows have no `Goods` context), agricultural relief ("reduces collections from agricultural wages": no getter gives the wage tax of agricultural workers).

**What the estimate assumes**, on the review's hover (`te_tax_est_header_tt`) and, shorter, the offers' note (`te_tax_pol_est_tt`): pops, wages, prices and purchases as today; receipts counted where the law collects them, as part of a tax may pass on through prices and wages (spec §5: legal payer, not incidence); other collection modifiers unchanged; taxes outside the code on the same Budget line (a religious tax, redemption payments) scaled with the rest; bringing in or removing rural assessment or head tax moves some of the other's payers; and receipts can lag a new rate for some days after a commencement. Nothing here feeds the AI or the support model, which use rate deltas (Task 6).

**Engine forms.** `Multiply_CFixedPoint` of two getters is in the mod (`te_trade_partner_tooltips.gui`); CFixedPoint arithmetic on a `ScriptValue` is in the history charts (`Subtract_CFixedPoint( GetPlayer.MakeScope.ScriptValue(...), ... )`); `Divide_CFixedPoint` and the `|+K` format are in vanilla 1.14.5's loc. A getter times a `ScriptValue` has no exact precedent: a play-test item.

## Customs schedule

Spec §6 and §11; plan Task 15. Under the experimental rule option `te_tax_code_enabled_customs` (`te_tax_customs_on`) every tradeable good's import and export level is a provision of the market owner's code; under `te_tax_code_enabled` tariffs stay native, nothing customs-specific is written, the 14 tariff and subvention buttons stay usable and the workbench's Customs section says so. `test_tax_code_customs.py` pins it, including that every customs write is reachable only behind `te_tax_customs_on`, `te_tax_customs_eligible` or `te_tax_customs_authority`.

**Customs catalog (60 goods):** `advanced_materials`, `aeroplanes`, `ammunition`, `artillery`, `automobiles`, `clippers`, `clothes`, `coal`, `coffee`, `construction`, `consumer_appliances`, `digital_assets`, `dye`, `electronic_components`, `engines`, `explosives`, `fabric`, `fertilizer`, `fine_art`, `fish`, `fruit`, `furniture`, `glass`, `grain`, `groceries`, `hardwood`, `iron`, `ironclads`, `launch_capacity`, `lead`, `liquor`, `luxury_clothes`, `luxury_furniture`, `magnetic_drive_ships`, `manowars`, `meat`, `merchant_marine`, `motor_ships`, `oil`, `opium`, `paper`, `porcelain`, `radios`, `robotics`, `rubber`, `silk`, `small_arms`, `steamers`, `steel`, `sugar`, `sulfur`, `tanks`, `tea`, `tech_metals`, `telephones`, `tobacco`, `tools`, `tourism`, `wine`, `wood`.

`customs_catalog()` in `gen_tax_code.py`: every good, vanilla and mod, that is neither `local = yes` (services, transportation, electricity, digital access: never traded between markets) nor `tradeable = no` (gold). The workbench groups them by their goods-file category (`customs_by_category()`: staple, industrial, luxury, military).

### Levels

One signed scale per good and direction, vanilla's: −3 `max_subventions`, −2 `high_subventions`, −1 `low_subventions`, 0 `no_tariffs_or_subventions`, 1 `low_tariffs`, 2 `high_tariffs`, 3 `max_tariffs` (`CUSTOMS_LEVELS`). A subsidy is a negative level: selecting a tariff clears a subvention, as in the Budget panel. The rate a level charges is its fraction of the applicable maximum (`state_tariff_*_add`, `state_subvention_*_add`, set by the trade policy law and the retained adjustments research C lists), which the code does not legislate. The per-good rate and level-bound modifier families are not used: the game's load rejected them as unknown modifier types (capability ledger row 14). A draft, bill or package field leaves a provision alone at −99 (`CUSTOMS_UNTOUCHED`), since −1 is a level.

### Authority

Only the market owner sets tariff levels (vanilla's `SET_TARIFF_LEVEL_NOT_MARKET_OWNER`); a junior customs-union partner, a subject pact included, trades in its senior's market and may not. `te_tax_owns_market` (`te_tax_triggers.txt`): `exists = market`, `market.owner = this` (vanilla's form, `china_buttons.txt`), `is_junior_in_customs_union = no`. `te_tax_customs_eligible` adds the customs option; `te_tax_customs_authority` adds a code in force that has taken its customs up (`te_tax_customs_held = 1`). The records are read, synced and drafted only under the last.

- **Migration** (`te_tax_migrate_country`, for an eligible country only): `te_tax_migrate_customs` (`te_tax_migration_effects.txt`) runs the generated `te_tax_gen_migrate_customs`, which reads each good's native level in both directions through the capital's state goods (`te_tax_gen_customs_read_native_<d>`: `capital ?= { sg:<good> = { <direction>_tariff_level = <key> } }`, one branch per level, vanilla's `je_set_up_grain_import` form; the engine default, low tariffs, when no capital can be read) into `te_tax_en_<d>_<tg>`, drops any pending re-assert and blocked mark, writes `te_tax_customs_held = 1` and moves `te_tax_xver_customs`. The migration's own history entry (kind 5) covers it.
- **Revalidation** (`te_tax_customs_revalidate`, gated on the customs option and a code in force): at every month's start, in the processor, after the month is claimed and before any transition (so a package touching customs holds in the month the market was lost, rather than commencing), and in the hidden `te_tax.7`, raised a day after `on_merge_markets` (to the dissolving market's owner and the absorbing market's), `on_create_market` (its owner), `on_become_subject` (the subject and its overlord) and `on_become_independent` (`te_tax_on_actions.txt`). A country that owns its market and does not hold its customs migrates afresh from the market's native levels, `te_tax_code_version` +1, history kind 17. A country that holds them and no longer owns its market keeps its records frozen (`te_tax_customs_held = 0`; nothing is removed), `te_tax_xver_customs` +1 (a package touching customs holds), its failed re-assert counts dropped, history kind 16. An open draft's and bill's customs levels are dropped to −99 so both stay usable (controller ruling): the draft keeps its other changes and its `te_tax_dr_customs_dropped` = 1 makes the review say "Customs changes dropped: the market is no longer ours" (reset when a market is gained); the bill, whose text changed, opens a new revision as an accepted offer does (`te_tax_bill_drop_customs`: commitments released, promises proposed again, support refreshed), unless it changed only customs and so would now change nothing from existing law (`te_tax_bill_changes_something`): then it is withdrawn as `te_tax_cmd_withdraw` withdraws (`te_tax_bill_close`, pending promises released) with a `TE_TAX customs_bill_withdrawn` line (fix round 1); one `TE_TAX customs_dropped` line and history kind 18, `_inst` 1 when the bill was withdrawn ("Customs changes dropped and the bill withdrawn: the market is no longer ours"). A member's records are never written: it has none until it owns a market.
- **Releases** take none of the parent's customs: `te_tax_init_released_country` writes `te_tax_customs_held = 0`, and the released country takes up its own market's levels at its first revalidation. **Uprisings** copy the customs tokens and records with the code (`te_tax_gen_copy_code`); a rebel country that does not own a market freezes them at its first revalidation. The **win repair** drops failed re-assert counts (`te_tax_gen_customs_clear_retries`) so the winner counts afresh.

### Sync and drift

`te_tax_sync_customs` (`te_tax_collection_effects.txt`) runs in the collection writer after the drift count and before the amendment block, only under `te_tax_customs_authority`. Per tradeable good and direction (`te_tax_gen_sync_customs`), when the market's level differs from the code's (`te_tax_gen_customs_matches_<d>`, which tests the record's value first so only one branch reads the market):

- **Re-assert:** the code's level is set again (`te_tax_gen_customs_set_native_<d>`: `set_<direction>_tariff_level = { goods = g:<good> level = <key> }`) and, on the month's first customs sync, the failed re-asserts are counted (`te_tax_cretry_<d>_<tg>` +1).
- **Adoption** (controller ruling): once `te_tax_customs_adopt_after` (4, `te_tax_support_values.txt`) monthly re-asserts in a row have not taken, because a treaty forbids the level (`no_tariffs`, `no_subventions`) or the 3-month tariff cooldown (`TARIFF_LEVEL_COOLDOWN_MONTHS`) kept refusing it, the next month's first sync adopts the market's level into the code (`te_tax_gen_customs_read_native_<d>`), removes the counter and marks the direction `te_tax_cblock_<d>_<tg>` = 1, which the review shows as "Imports (Exports) blocked by a treaty or the tariff cooldown". Re-asserts in months m … m+3 that all fail lead to an adoption in month m+4, so a refusal by the cooldown after a recent change is retried, not adopted. After the loop, if any level was adopted: `te_tax_xver_customs` +1 (a change made outside legislation), `te_tax_code_version` +1 and **one** history entry, kind 15, carrying the number of levels adopted in its `_inst` (`te_tax_gen_history_write = { KIND = 15 SLOT = none INST = local_var:te_tax_cu_adopted }`; each history row prints it through its own key, `te_tax_hist_kind_customs_adopted_<i>`, with the threshold spliced in from `te_tax_customs_adopt_after`). The drift counter keeps the per-good detail. The `TE_TAX customs_adopted` line is written every time for a player's country and the first time only for an AI's (`te_tax_customs_logged`), as `te_tax_detect_drift` logs.
- **Levels match:** the counter is removed; if it stood (a re-assert took), so is the direction's blocked mark (fix round 1). A plain match does not clear the mark: an adoption makes the code equal the market, so the mark would otherwise last only until the next month.

Only the first customs sync of a calendar month counts or adopts (`te_tax_customs_month`, the month it last ran): `te_tax.4` and the watchdog may sync again in a month, and those syncs only re-assert, so the count is of consecutive monthly syncs and kind 15 is written at most once a month. Kinds 16 and 17 cannot repeat: each needs the opposite standing first.

The counter, the blocked mark and the month guard are transient flags, not schema tokens: written when set, removed when cleared (the counter by a match, an adoption, a commencement that sets the good, a migration, the loss of the market, a release or a reunification; the blocked mark by a re-assert of that direction that took, a commencement that sets it or a migration), and not copied at an outbreak, so the rebels count afresh. Whether the setters obey the market-owner rule, a treaty ban and the cooldown is unobserved (capability ledger row 15, P10); the adoption is what keeps the code equal to the market either way.

**Drift.** `te_tax_detect_drift` also counts, under `te_tax_customs_authority`, every good and direction off the code's level (`te_tax_gen_customs_drift`, `te_tax_gen_count_customs_drift` → `te_tax_drift_customs`; `te_tax_view_drift_customs`), with the same rule as the other counts: only while the code has not changed since the last full sync.

### Customs in a bill

Under the customs option a draft, a bill and a package carry a field per tradeable good and direction (−99 to leave the level alone) and a customs marker (`te_tax_<r>_customs_pver`, `te_tax_p<s>_pver_customs`) written with them; every customs read of a record tests its marker first, so the plain option writes and reads none. `te_tax_gen_draft_init` writes them under `te_tax_customs_on`; `te_tax_gen_bill_from_draft` copies them with `te_tax_bl_xver_customs` when the draft has them; `te_tax_gen_draft_from_bill` copies them back; the clears remove them behind the marker; `te_tax_gen_store_<s>` writes them into the slot with `_xver_customs` and `_pver_customs`; the outbreak's slot copy carries them (`slot_payload`).

- **Drafting.** `te_tax_cmd_draft_customs` (above): only while the code holds the country's customs, so a customs-union member and every country under the plain option has no editor. Existing law in a record's month (`te_tax_base_<r>_<d>_<good>`, `te_tax_generated_support_values.txt`): the enacted record while the code holds the customs, else vanilla's default (low tariffs), then each awaiting package due earlier that sets the level, in commencement order. `te_tax_dr_eff_<d>_<good>`: the draft's level, or that baseline.
- **Readiness.** `te_tax_draft_ready` holds a draft that changes a level to `te_tax_customs_authority` (one `custom_tooltip` line), at introduction and at every revision. A bill that changes a level is never minor.
- **Versions.** The customs group has one planned version (`te_tax_pver_customs`, bumped at passage by `te_tax_gen_bump_pver`; a draft written against an older one needs a rebase, `te_tax_cmd_draft_rebase = { KEY = customs }`) and one external version (`te_tax_xver_customs`: the customs migration, an adopted market level, a market lost). `te_tax_gen_bill_current` holds a bill touching customs to the external version it recorded; `te_tax_gen_package_current_<s>` holds a package touching customs at commencement (held_conflict) the same way, so a market lost or a level adopted since the approval holds it.
- **Supersession and commencement.** A bill drops each level it sets from a later-approved package (`te_tax_gen_supersede_<s>`, −99); `te_tax_gen_package_empty_<s>` counts customs. At commencement `te_tax_gen_apply_<s>` writes each level the package sets into `te_tax_en_<d>_<tg>`, only while the code holds the customs, and drops the good's pending re-assert and blocked mark; the sync in the same processor run sets the market.

**Native controls.** The 14 tariff and subvention buttons are greyed under the customs option only (`te_tax_native_tariff_controls_sgui`, [Native controls and drift](#native-controls-and-drift)); the AI, treaties and events still write the market's levels, which the sync re-asserts or adopts.

## Balance decisions

- **Consumption-Based Taxation's non-rate effects are dropped.** Its `modifier` block (`state_bureaucracy_population_base_cost_factor_mult = -0.25`, `country_consumption_tax_cost_mult = -0.50`) goes with the law. The code has no instrument for either, so a country migrated from Consumption-Based pays full bureaucracy cost for its population and full Authority for its taxed goods.
- **Millet System and People of the Book keep their heathen tax, and `amendment_redemption_payments` its land tax, outside the code.** They stay native and are not migrated: external adjustments at the pinned medium level (heathen tax 0.50, redemption payments 0.09).
- **`amendment_short_term_tax_cuts` is dropped.** Vanilla's temporary tax cut (`state_tax_collection_mult` −0.10) lists the four vanilla taxation laws in its `allowed_laws`, not the carrier, so the carrier swap at migration takes it away from a country that had it, and none can be added under the rule. The code has no instrument for an across-the-board cut; a bill with a sunset is its replacement.
- **A natively taxed good outside the catalog is not carried.** The migration reads only catalog goods; the first sync removes a consumption tax on any good outside the catalog. Vanilla 1.14.5 history taxes only catalog goods (`coffee`, `grain`, `liquor`, `luxury_clothes`, `luxury_furniture`, `opium`, `tea`, `tobacco`, `wine`; `belle_epoque_events.8` adds `automobiles`, also in the catalog), so this affects only goods a player or the AI taxed before the rule took effect.
