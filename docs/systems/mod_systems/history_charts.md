# History Store and Charts

Part of the [mod systems reference](../mod_systems.md), which indexes every system.

## History Store and Charts

A bounded, save-persistent store of monthly samples, plus a reusable column chart that renders them inside a journal entry. The banking system is its first consumer; the reserve and UN series are meant to be added with a sampling call and a chart instance and nothing else.

### Files

| File | Role |

| `common/scripted_effects/te_history_effects.txt` | generic country and global recording/pruning helpers |

| `gui/te_popups.gui` | the popups root, which instances `te_chart_popups` (the viewers) |

### Data model

**One script container per (country, month), not per metric.** Each container carries:

| Variable | Meaning |
|---|---|
| `te_hist_i` | monotonic month index (`te_history_month_index` = `year * 12 + month`, Jan = 0) |
| `te_hist_y` / `te_hist_mo` | calendar year and month 1–12, display only (the GUI has no integer division) |
| `te_hist_v_<METRIC>` | one per metric recorded that month |
| `te_hist_mk` | number of markers that month — its presence is what draws the marker pip |
| `te_hist_mk_<MARK>` | one per distinct marker recorded that month |

Tags are `te_hist te_hist_sample` (plus `te_hist_global` for the global series); the parent is the recording country, so the engine culls the history when the country stops existing. The country holds `te_hist` (the capped list), `te_hist_cur` / `te_hist_cur_i` (the current month's container and its index — the once-per-month guard), `te_hist_now_i`, and `te_hist_since_y` / `te_hist_since_mo`.

Sharing one container between all of a month's metrics is what makes the store affordable: 240 containers per tracked country covers *every* series rather than 240 per series, and a month's markers land on the same container as its readings, so the chart never has to search for them. A metric that was not recorded in a month simply has no `te_hist_v_<METRIC>` variable there — that is how the charts tell **missing data from a genuine zero**, and why a country that drops out of eligibility leaves a visible gap rather than a run of zeroes.

`te_history_month_index` is stateless: the same arithmetic on the current date, identical for every country and for the global series. Nothing has to be seeded on an existing save, two pulses in one month resolve to the same container, and there is no counter that can drift.

### Caps and eligibility

- **Cap:** `te_history_sample_cap = 240` — twenty years of monthly samples, defined once (also written as the literal `241` in both pruners). One sample is added per month and `te_history_prune_samples` evicts exactly one when the list goes over, using `ordered_in_list { position = 0 order_by = te_history_sample_order }` so the oldest goes regardless of how the engine orders the list. `te_history_sample_order` **negates** the month index, because Jomini's `ordered_*` iterators sort descending — ordering by the raw index would put the *newest* sample at position 0 and the pruner would destroy the container it had just created. (`un_resolution_age_order` negates for the same reason.) The evicted container is `destroy_container`ed after `remove_list_variable`, never before, so the list never holds a dead reference.
- **Re-sorting after eviction:** `remove_list_variable` fills the removed slot with the list's *last* element instead of shifting, so one eviction moves the newest sample to the front of the list — and the chart draws raw `GetList` order. Confirmed from a 1865 save: every store at the cap held `[the newest k months][the oldest 240 - k]`, one break, while every store still under the cap was chronological. `te_history_prune_samples` therefore calls **`te_history_sort_samples`** after each eviction, which rebuilds the list oldest-first. It builds the sorted copy into `te_hist_tmp` and clears `te_hist` only once that copy is provably complete (`count >= 240`, exact because the pruner runs at precisely the cap) — clearing first would strand 240 containers no list points at. `te_history_sort_global_samples` does the same for the global series. Check any save with `python3 scripts/analysis/check_save_history_order.py`. **A store that stops recording keeps whatever order it froze in** — the re-sort only runs on an eviction, and a country that has dropped out of eligibility never evicts again. Since the sort runs after every eviction, a store that stops now is already in order; the only ones out of order were scrambled before the sort existed (#356) and never evicted since. Those were unreachable while the charts lived on the country's own journal entry; National Info (the Census Data window) shows another country's charts, so an old-save repair, `te_repair_history_order` (`common/on_actions/te_old_save_repairs.txt`), sorts every store once, and the checker fails on any store out of order, `frozen` (the label stays) or live. It reads Demographics' yearly `te_dg_hist` as well, on its own clock.
- **Eligibility:** `te_history_country_is_tracked` = `is_player = yes` OR `country_rank >= rank_value:major_power`. Identical for AI and human countries. `unrecognized_major_power` (rank_value 5) is deliberately out — those countries are numerous and rarely run the charted systems.
- **Dropping out:** a country that falls below the bar stops sampling and **keeps** its stored history; nothing prunes it early. It is bounded at 240 containers and dies with the country, so stale history costs at most one country's worth of samples. Re-entry resumes recording and the gap renders empty. An empty chart says which it is: the type's empty text asks `te_history_tracked_sgui` (`te_history_country_is_tracked`, on the host's `Country`), so a country that keeps no history says so (`te_history_untracked`, "History is kept only for played countries and major powers") rather than "nothing recorded yet"; the Demographics charts use the same gate and key.
- **System gating:** a series also gates on its own system. `te_history_record_banking_samples` requires `te_banking_system_on = yes` and `has_journal_entry = je_banking_cycle`, so a country with banking switched off records no banking metrics at all. Under `banking_system_simplified` the three cycle series and the two rate series are still sampled; `mon_inflation` and `mon_fx` are not (they would flatline), and their two charts are hidden on the same trigger.

### Markers

`te_history_record_marker = { MARK = <key> }` sets `te_hist_mk_<key>` on the month's container and bumps `te_hist_mk`. The banking markers are recorded at the single shared site each policy already has — the `banking_effect_<button>` helpers, which both the AI's journal-entry buttons and the dashboard call — plus `banking_cycle_check_and_execute_crash` (`crash`) and `banking_contagion_crash_check` (`crash_contagion`).

The tooltip is built in script, not in `.gui`: `te_history_marker_tooltip` is a `scope = country` scripted GUI with `saved_scopes = { te_hist_sample }` whose effect is nothing but `custom_tooltip` lines, rendered from loc with `[GetScriptedGui('te_history_marker_tooltip').ExecuteTooltip( GuiScope.SetRoot( JournalEntry.GetCountry.MakeScope ).AddScope( 'te_hist_sample', ScriptContainer.MakeScope ).End )]`. Its policy branches print the policy's name, one line under "adopted" or "withdrawn" (GUI audit BNK-4, 2026-10-27). They used to quote the dashboard's whole `banking_dash_tt_<button>` tooltip, which put today's Requires line and live figures under a bar from years ago, and five of those keys read `JournalEntry`, which a bar's tooltip does not have. A verb-named button is named by its modifier ("Bank Holiday"). The three cycle charts' bars name that month's band (phase, momentum band, bubble band) with an `AddLocalizationIf` chain over the stored reading; `test_banking_layout.HistoryBandTest` holds the chains to the overview's words. `is_valid`/`ai_is_valid` are `always = no`, so neither a player nor the AI can ever execute it.

### Opening the GUI never writes state

Every recording helper body is wrapped in `hidden_effect`. That matters because the `banking_effect_<button>` helpers are also rendered as button tooltips; during a tooltip render the engine resolves scope links but never creates containers, so an unwrapped call would both spray text into the policy tooltip and read a scope that was never set. The chart itself has no effect at all: the only click targets are the collapse header and the three range buttons, and both write GUI-variable-system values that never reach the save.

### The chart

`plotline` cannot be used. Its `plotpoints` property only accepts the output of `GetTrendPlotPoints` / `GetTrendPlotPointsNormalized` / `GetDynTrendPlotPoints`, all of which take an engine-side `DataTrend`; no global function in the 1.14 data-type docs returns a `DataTrend`, and no `DataTrend` exists for a mod variable. So the chart is one vertical `progressbar` per stored month, over `datamodel = "[JournalEntry.GetCountry.MakeScope.GetList('te_hist')]"`.

- **Width.** The plot is a horizontal flowcontainer of fixed-width items, one per sample: each range's `te_history_plot` sets its bar width (`bar_size`, 40 / 8 / 2 px for 12 / 60 / 240 months), anchored at the right, so a partial history leaves space on the left instead of stretching its last bar. Switching to 1 year widens the bars instead of leaving 228 empty slots. At the 20-year end the 480px plot is split 240 ways — 2px a bar, so the series reads as a shape, not as countable months. An out-of-range item pays for its `visible` test and nothing below it, so the short ranges stay as cheap as they were before the cap doubled.
- **480 is not a round number, it is a divisible one.** Bar widths are integer pixels, and whatever the division leaves over the layout hands to the last item, i.e. to the newest month. 480 divides all three full-store bar counts exactly (240 / 60 / 12 → 2 / 8 / 40px), so no range leaves a remainder. The plot was 484px until #366, which is 4px over in all three cases: the newest month drew 6px against every other month's 2px on the 20-year view, three times as wide as its neighbour, and 12px against 8px on the 5-year one. Changing the plot width or adding a range means re-checking that `plot_width % bar_count == 0` for every range. A chart whose full ranges come to another width sizes its frame to them with the optional `plot_size` block (the 496px default is 480 + the plots' 8px right margin + 8). Cultural Hegemony's annual chart draws 5 / 20 / 100 years at 80 / 20 / 4px, 400px in all, in a 456 × 180 frame: a 48px column for its axis labels, then the bars to the right margin. Left at 496 it showed ~90px of empty frame on the left of a full 100 years. `test_cultural_hegemony_history.test_full_ranges_fill_the_frame` checks the arithmetic.
- **Ranges.** `GetVariableSystem` holds `te_hist_range` = `1`, `5` or `20`; unset means 20 years, which is the whole store, so the default view needs no per-bar test to pass. Each bar's `visible` compares `te_history_month_index` (now) minus its own `te_hist_i` against 12 / 60.
- **Signed series.** `te_history_bar_signed` stacks two half-height bars around a zero axis. The lower one uses vanilla's `double_direction_progressbar` "REVERSE HACK": swap `progresstexture` and `noprogresstexture` and give the bar a `min .. 0` range, so the coloured part is drawn from the far end and hangs down from the axis. Both halves clamp their value with `Max_CFixedPoint`/`Min_CFixedPoint`, so a positive month draws nothing below the axis and vice versa.
- **Two signed series deliberately do *not* use it** — the digital-currency policy-rate chart (−3…12) and the inflation chart (−4…12). `te_history_bar_signed` splits the plot 50/50 whatever its two ranges are, so on an asymmetric range a −2% month draws taller than a +2% one: a scale discontinuity at exactly the line those charts exist to watch. Both instead use `te_history_bar_unsigned` over **one linear span** with a manually drawn 0% line (a `zero_axis` blockoverride positioned from the plot margin plus the zero fraction of the plot height), and one colour above and below it — `te_history_bar_signed`'s green/red split would say deflation is the opposite of a problem. The offsets (23px and 27px) cannot be checked from the files; both are on the in-game checklist. If a new series is signed and its range is asymmetric, copy the inflation chart, not the momentum one.
- **An axis that follows the data.** A progressbar's `max` and `min` take an expression, so a chart whose figures have no fixed top reads its axis from script: Demographics' five (`te_demog_history_axes`, [demographics.md](demographics.md), "The history charts' axes span what they show") store the largest sample, rounded up to a round number and never under a floor, once a census, and the bars' range, their floor and cap (as fractions of the axis: `Multiply_CFixedPoint( <axis>, '(CFixedPoint)${thin:0.02}' )`) and the axis's label (`raw_text = "[<axis>|0]"`) read one script value that falls back to the floor while the variable is missing. Every other chart here has a fixed axis. Most are indexes from 0 to 100 that cannot pass it; the monetary ones can (the policy rate's dial reaches 60 on a 0 to 12 axis, inflation is held to −10 to 100 on −4 to 12) and stop at the frame, and the asymmetric ones among them would need their hand-placed zero line to move with the axis, which a fixed `position` cannot.
- **Banded colour.** One chart does not use `te_history_bar_unsigned`: the banking cycle-value column is `te_history_bar_cycle_phase` (declared in `banking_history_widget.gui`, its only consumer), which draws the month in the colour of the phase its reading falls in. A progressbar's `color` *can* be an expression, but the only way to produce a `CVector4f` is `Select_CVector4f` over two colours that already exist as engine getters, and there is no `CVector4f` literal to nest into it — so the six colours are six progressbars in the same slot, each `visible` only inside its band, over one shared dark cover. Bands are the phase ladder from `banking_cycle_effects.txt` (10 / 25 / 40 / 60 / 75 / 88); the RGB values are vanilla's named text colours from `gui/textformatting.gui`, so a bar is literally the colour the phase's name is printed in.
- **Marker key.** `te_history_marker_legend` (in `te_history_chart.gui`) is a two-row key for the pips: the `information.dds` pip, drawn on any month with a marker, and the `warning.dds` pip, drawn on a crash. The crash row is a `block` with a default body, so a series that never records a crash overrides `"crash_marker"` to nothing.
- **Empty state.** `IsDataModelEmpty` on the same list shows "nothing recorded yet" — what an existing save sees until its first monthly pulse. `te_hist_since` prints the oldest retained sample's date.
- **Open by default.** Every history section opens with its charts (the owner's rule since play-test round 2); its header toggles a flag named for the *closed* state (`banking_dash_history_closed`, …), and a closed section pays for no bars.

### One chart, two sizes

Each history chart is written once, in `scripts/generators/gen_te_history_charts.py`, and drawn at two sizes: the panel's and the full-screen viewer's (spec `docs/superpowers/specs/2026-11-02-charts-help-national-info-design.md` § 4.3).

- **The registry.** `CHARTS` has a line per chart: its id, its system (the window tab's key), its kind (`monthly`, `annual`, or `annual_pips`, Demographics' annual charts with a pip lane above the bars), its fragment, the journal entry the viewer reads (`None` for Demographics, which reads `Country`), the viewer's gate (the tab's scripted GUI) and its range variable (`RANGES`: each variable's three values, button labels and button width, as the sections draw them). A chart drawn only for some countries (Banking's policy-rate pair, inflation and the exchange rate) also records its own `visible` as `shown`; the section's instance of the wrapper carries it, and a test holds the two together.
- **The fragment.** `scripts/generators/te_history_charts/<system>.gui.in` holds each chart's `te_history_chart` instance as its section had it, after an `@fragment <name>` line, dedented, with each size a placeholder: `${frame}`, `${bars_<value>}`, `${bar_h}`, `${box_h}` (Demographics), `${zero_y:<fraction>}` for a hand-placed zero line, and `${thin:<x>}` (or `${thin:<min>+<x>}`) for a cap or floor in the axis's units. The Strategic Reserve's nine goods share one fragment through `${good}`.
- **The two sizes.** `SMALL` is the panel's (480 px of monthly bars in a 496 × 96 frame, 400 px of annual ones), the chart type's own defaults, so at `SMALL` the generator only substitutes, then adds the open button beside the title and narrows the title to 456 beside it (see **The full-screen viewer** below), and gives an annual chart its width, 488 (`chart_width`, see **The wrappers**): the panel's charts are otherwise their fragments' text. `LARGE` is the viewer's: a 1200 px plot for every chart (bars of 100 / 20 / 5 px for 12 / 60 / 240 months, 240 / 60 / 12 px for 5 / 20 / 100 years), 336 px tall. At `LARGE` the generator adds the frame, the bars and the title, legend and empty-state widths a monthly fragment leaves to the type, the widths an annual one does, and every chart's own width (`chart_width`: 1216 or 1256); it thins every `${thin:…}` by the height ratio, so a 4-point cap draws 3 px, not 13; and it leaves out the fragment's comments, which describe the panel's size. The zero lines move with the bars: 6 + 0.2 × 336 = 73 px and 6 + 0.25 × 336 = 90 px up.
- **The wrappers.** `gui/te_history_charts_generated.gui` holds `te_hist_<id>` and `te_hist_<id>_large` for every chart, each a plain flowcontainer holding its `te_history_chart` instance inline. That is the shape that draws: a type derived from `te_history_plot` drew nothing (`gui_modding_guide.md` gotcha #37), and this is no derived type. The wrapper is a centered vertical column of the chart's fixed width (`Dims.width`: the frame, or the text over it where that is wider: 496 for a monthly chart, 488 for an annual one, 1216 and 1256 in the viewer), and the chart is fixed at the same width (block `chart_width`). Neither the chart nor its title-and-legend column is anchored: each sits at the left of its parent, and only the wrapper centers. C1's wrapper was sized by its content, and in game it was centered at the width of the chart's text alone, so each chart sat right of the next by half its plot's excess over its text and ran out of the panel (gotcha #46). A chart's own `visible` sits on the section's instance of the wrapper, so a hidden chart leaves no spacing.
- **Kept manual.** The generator is not a post-load regenerator (as `gen_te_systems_window.py`); `--check` exits 1 when the file is stale, and `test_te_history_charts.py` fails then, on a hand-written `te_history_chart` instance left in `gui/`, and on a size literal left in a fragment.

### The full-screen viewer

Each chart opens alone at full size (charts PR C2, spec `docs/superpowers/specs/2026-11-02-charts-help-national-info-design.md` § 4.2): the round button beside a panel chart's title, `te_chart_open_button` (`te_history_chart.gui`, a placeholder icon listed in `docs/systems/te_systems_window_gui_icons.md`), sets the client-side key `te_popup` to `chart_<id>`, and that chart's popup shows. One popup is open at a time, and Escape, its close button or a click outside closes it (`te_ui_popup`, the shell every popup in `gui/te_popups.gui` derives from).

- **The button.** The chart type's title shares a row with a `chart_open` block. Each panel wrapper fills it with the button and narrows `chart_title_width` (484 by default, the title's alone; the legend keeps `chart_text_width`) by the button's 24 and the row's 4, to 456. The viewer's wrapper leaves both, so the large chart has no button. Every chart's slot holds two buttons, one showing at a time (spec § 4.4, PR F1): for the player's own country (`visible = "[Country.IsLocalPlayer]"`, `OWN_COUNTRY_ONLY`) it sets `te_popup`, the player's viewer; for another country, in National Info (`OTHER_COUNTRY`), it sets `te_ni_chart`, the viewer the window holds under its own Country (`te_ni_chart_<id>_popup`, below). The slot is a horizontal `ignoreinvisible` flowcontainer, so it is one button wide either way.
- **The popup.** `te_chart_<id>_popup`, generated with the charts. Its header is the chart's title, but for the Strategic Reserve's nine, whose shared "Fill by Month" sits in the good's row on the panel: their headers name the good (`te_chart_st_res_<good>_title`, "Strategic Reserve: Grain"). Its list holds the chart's range buttons, the large wrapper and the key its section draws, which is a type the section shows too (`KEYS`): Banking's marker legend, Demographics' pip legend and Cultural Hegemony's fifteen models.
- **The range stays shared.** The range row, `te_chart_range_row_<var>`, is generated as the sections draw their buttons (`test_te_history_charts.ViewerTest` holds the two equal), and sets the same variable, so the viewer opens at the panel's range and changing it changes both.
- **Whose chart.** The popup reads the player: a `GetPlayer` datacontext (the Country the Demographics charts read) carries the tab's scope-free gate, and under it a `GetPlayerJournalEntry('<entry>')` child supplies the JournalEntry the others read (gotcha #29). With the gate shut, the entry gone under an open viewer, one line says so.
- **The gate and nothing else.** A panel also hides a chart or its section on conditions of its own, and the viewer leaves them out: each only ever turns on (Banking's cycle start, the first warhead for the taboo, a reserve good's unlock, Demographics' first census) or is a game rule (Banking's inflation and exchange-rate charts), and the button lives on the chart, so no viewer opens before its chart shows. The two policy-rate charts take turns on the Digital Currency law; a law change under an open viewer leaves the chart drawing on the axis it was opened with. `test_te_popups.ChartPopupTest` holds every popup to its gate alone.
- **Size.** The popup is the large frame plus the shell's margins, the list's and a scrollbar: 1320 wide for a monthly chart, 1360 for an annual one, and as tall as its rows, 580 to 760 (Cultural Hegemony's, with its key). Every one fits a 1600 × 900 screen at UI scale 1; `_validate` refuses one that doesn't.
- **Another country's viewer (PR F1).** `te_ni_chart_<id>_popup`, generated for every chart beside the player's, shows on `te_ni_chart = <id>` and closes on it (`te_ui_popup`'s `popup_close` block, both close buttons). It holds the player's viewer's title, size, range row, large chart and key, under National Info's own Country and with no gate, since another country has no entry (`test_national_info.ForeignViewerTest` holds a public tab's viewers to Country reads). `te_ni_chart_viewers` holds the 34; the window instances it once at its own level, up only while `te_ni_chart` exists, and its `_show` state clears `te_ni_chart`, so a viewer left open never reopens with the window.

### How to add a series

1. **Sample it.** From the system's own monthly pulse, in country scope:
   `te_history_record_sample = { METRIC = res_stock VALUE = var:st_res_stock_grain }`
   Wrap it in the system's own gate (game rule + journal entry) the way `te_history_record_banking_samples` does. For a world-level series use `te_history_record_global_sample` instead; it writes to the global list and needs no eligibility trigger.
2. **Chart it.** Write the chart as a fragment in its system's `scripts/generators/te_history_charts/<system>.gui.in` (see **One chart, two sizes** above), add its `Chart` line to `CHARTS`, run the generator, and instance `te_hist_<id> = {}` in the section. The generator writes the chart's viewer with it; a section whose charts need a key under them names that type in `KEYS`. The fragment is a `te_history_chart` instance with blockoverrides for `chart_title`, `chart_legend`, `bar_tooltip` and `bar_body`. Use `te_history_bar_unsigned` for a one-sided metric (override `values` with `min`/`max`/`value` and `color`), `te_history_bar_signed` plus a `zero_axis` override for a signed one whose range is **symmetric** — for an asymmetric signed range use `te_history_bar_unsigned` over the whole span with a drawn zero line instead (see the two exceptions under **The chart** above). The bar body's `visible` must be `[ScriptContainer.HasVariable( 'te_hist_v_<METRIC>' )]` so months without that metric stay empty.
3. **Localize it.** A title, a legend, a `…_row` line and a tooltip key modelled on `te_hist_tt_bank_value` — the tooltip key is where the date line and the marker block are composed.
4. **Mark it, if the series has turning points.** `te_history_record_marker = { MARK = <key> }` at the single site the event already has, plus one branch in `te_history_marker_tooltip`.
5. **If it has no markers of its own, hide the pips.** Markers live on the month's shared sample container, so every chart of a country's store draws every system's pips (the banking policy "i" and crash "!" icons). A series whose tooltip does not explain them should add `blockoverride "marker_pips" {}` to its fragment's `te_history_chart` instance. The UN authority, global-warming and colonial charts do; the banking charts, which record and explain their own markers, do not. Cultural Hegemony now uses its separate annual model history without markers.

Nothing else. The store, pruning, ranges, marker pips, empty state and "available since" line are all shared. **Do not** add a second store, a per-metric container list, or a parallel chart implementation.

### Cost

Per tracked country: up to 240 containers (the cap), each with 3 bookkeeping variables plus one per recorded metric (3 for banking today), plus 6 country variables. The Strategic Reserve adds up to nine metrics (one per unlocked good) for a tracked country with a reserve, so its containers carry up to nine more variables each; the reserve adds no containers. Per month per tracked country: one container create, one destroy, ~6 `set_variable`, and two 240-element ordered scans. GUI cost is paid only while the section is open: 240 items per chart, each running one script-value evaluation for the range test.
